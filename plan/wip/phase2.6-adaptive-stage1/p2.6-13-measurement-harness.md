# P2.6-13 — On-device measurement harness (S1-L / S1-N prerequisite)

**Phase:** 2.6 · **Depends on:** — · **Blocks:** p2.6-10, p2.6-11 · **Model:** Opus

## Goal

The probe container, the on-device load generator, the on-device mock upstreams
and the veth they run on exist, are documented as a repeatable procedure, and
have carried one end-to-end trial repetition — so suites S1-N and S1-L have a
harness instead of an assumption.

## Ordering

Numbered 13 but **runs before p2.6-10 and p2.6-11**. The phase appends
late-discovered work rather than renumbering (p2.5-10, p2.5-11, p2-13, p2-14 did
the same); renumbering would break every cross-reference in the phase's review
files. The selector's `NN` order does not express this dependency — the phase
table does, and the owner sequences it.

## Context

Suite S1-N and S1-L arms L.1, L.2, L.4a and L.4b all run in a probe container on
the RB5009 against mock upstreams, driven by a load generator. None of it
exists:

- No probe container image and no probe container on the device.
- `veth3` is disabled with nothing attached ([routeros-traps.md](../../../docs/routeros-traps.md) §Topology).
- No DNS load generator anywhere in the repository or on the dev box.
  [p1-11-review.md](../../../docs/code-review/phase1/p1-11-review.md) records
  that throughput was never measured for want of one.
- No on-device mock upstreams.

Benchmarks §S1-N pins the L.1 workload to "whatever served p2.5-09's on-device
forward load — the same tool and the same host". p2.5-09 ran no on-device
forward load; its device work was the V4 list drill and the V6 memory soak. The
tool must therefore be **chosen and frozen here**, not inherited.

The protocol these components must serve is frozen in
[p2.6-10-null-ab-review.md](../../../docs/code-review/phase2.6/p2.6-10-null-ab-review.md)
§Frozen measurement protocol, and its plumbing is already validated on the dev
box (K = 4, `ABAB`, all six required checks passed). This task moves that
validated shape onto the device; it does not redesign it.

## Scope

- **Probe container.** Cross-compile to `aarch64-unknown-linux-musl`, pack as a
  single-layer OCI tar, convert to a docker-archive with skopeo (RouterOS cannot
  import OCI layout), place it on the Kingston store, and add it on its own veth
  with its own `root-dir`, mounts and config. Procedure per
  [routeros-traps.md](../../../docs/routeros-traps.md) §On-device measurement
  needs its own container and §Build and deploy pipeline.
- **veth.** Establish which veth the probe uses and what enabling it requires.
  `veth3` (`172.17.0.4`) is the documented scratch interface and is currently
  disabled.
- **Mock upstreams.** Two healthy mocks the probe container can reach, answering
  a forward zone at a short TTL and a control zone at a long TTL — the two
  streams the L.1 workload needs. Decide and record where they run (on the
  device, or on a LAN host) and what routing or firewall that requires.
- **Load generator.** Choose one, freeze it, and record the exact invocation.
  It must offer a fixed rate, report offered against achieved rate and loss, and
  reach the probe container's DNS port. Where it runs is part of the decision.
- **One end-to-end trial repetition** through the frozen protocol, proving the
  harness carries a measurement before a K ≥ 6 session is booked.
- **Teardown.** The probe container is removed; the production container is
  never stopped, reconfigured or restarted.
- Results file:
  `docs/code-review/phase2.6/p2.6-13-measurement-harness-review.md`.

## Router discipline

**Every router command is proposed; the owner executes it.** The agent runs
nothing on the RB5009.

Read-only first, and the write commands are not written until these are back —
mount names, `root-dir` and the veth are deployment-specific and must not be
guessed:

```text
/system/resource/print
/container/print detail
/container/mounts/print detail
/interface/veth/print detail
/ip/route/print
/ip/firewall/filter/print where chain=forward
/file/print where name~"kingston"
```

Constraints that hold throughout:

- No `/container set|add|remove|start|stop`, no `/ip` or `/ipv6` firewall edit,
  no `/disk set`, no `/system` anything executed by the agent.
- A firewall rule is never proposed as a bare `add` — the chain is read first and
  placement is decided, because `add` appends behind any final drop.
- `memory-high` is not proposed for the probe container. It once OOM-killed the
  live resolver.
- `root-dir` carries the `kingston/` prefix. Without it the image lands on the
  internal NAND.
- `logging=yes` is not the default and is the only channel that reports the
  probe's generated API key.
- `scp` needs the owner's permission for each use.

## Acceptance criteria

- The probe container starts on its own veth, answers on its own DNS port and
  its own API, and its `GET /api/v1/config` reports the intended probe
  configuration — including `history.sample_interval_seconds` fine enough to
  yield several perf rows per repetition (the production container's 360 s
  yields one or two per 10 minutes).
- Two mock upstreams answer the probe container, one zone short-TTL and one
  long-TTL, and the probe's `upstreams[]` shows attempts against them.
- The load generator sustains a declared fixed rate and reports achieved rate
  and loss. The rate it can actually hold against the probe container is
  measured and recorded — not assumed to be 10 000 QPS.
- One trial repetition completes end-to-end through the frozen protocol, with
  every metric populated: `forward` count and mean, `cache_hit` count and mean,
  total upstream attempts, attempts per forward, server QPS, and enough perf
  rows to read the latency percentiles.
- The procedure is written down as a repeatable command sequence, each command
  with its effect and when it takes effect.
- The probe container is removed afterwards and the production container is
  shown untouched.

## Out of scope

- Running the K ≥ 6 null A/B — that is p2.6-10, which resumes once this task is
  approved and implemented.
- Running the `adaptive` binary or any S1-L failure arm.
- Any change to runtime code.
- Any change to the production container.
- Any change to the S1-G2 acceptance rule or the S1-N metric order.

## Open items for the owner

- **Where the harness scripts live.** The dry run's collector, analyser and
  generator are validated but sit in a scratchpad. Committing them to the
  repository is a repository change and needs an explicit yes, including where
  they land.
- **Generator choice and host.** On the device as a second container, or on a
  LAN host driving the probe across the container bridge. The second needs the
  route and the forward chain read before anything is proposed.
- **Mock upstream host.** Same decision, same constraint.
