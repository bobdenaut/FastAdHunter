# P2.6-11 — Opt-in Deploy and Soak

**Phase:** 2.6 · **Depends on:** p2.6-06, p2.6-08, p2.6-09, p2.6-10 · **Model:** Opus

## Goal

`adaptive` runs opt-in on the RB5009 for the 7-day soak, and the deployment
tier of the gates — S1-G2 tiers 2–3, S1-G4, S1-G5 — is decided from
on-device evidence and recorded. This task ends `AWAITING SOAK` until the
window closes.

## Context

Spec §Stage 1 acceptance gates (tier table), S1-G2 tier 2 invariants and
tier 3 as frozen by `p2.6-10`, S1-G4 (run-length distribution read as a
`failure_runs` delta over the window, with the concurrency-splitting caveat),
S1-G5 (rejection routes), S1.9 (flattening counters are the feature working),
S1.14 (binary first, config second). docs/routeros-traps.md for every router
fact.

## Scope

- Merge gate check first: S1-G1 #1–#17 green, S1-G2 tier 1 and S1-G3 files
  written. If any is missing, stop.
- M.8 re-run (`upstream/forward_udp_answered{,_adaptive}`, dev box), judged
  against the corrected three-clause rule, with **K pre-declared in writing in
  the review file before the first measurement** — the condition p2.6-08 F1
  names as its closure. It is a dev-box bench, kept in its own acceptance
  table, separate from the probe-container arms (L.1/L.2/L.4) and from the
  soak. It runs before any deploy proposal is executed.
- Release: version bump, image build, deploy proposal. Opt-in via the
  container env override from `p2.6-01`, not a TOML edit inside the
  container. **Every `/container`, `/ip`, `/system` command is proposed with
  its effect and timing; the owner runs it.**
- Tier 2 pass/fail in L.1 vs L.2 (probe container): `penalties == 0`,
  attempts per forward `(Σ attempts − (swr.completed + swr.failed)) /
  cache_misses == 1.000`, `penalties`/`probes` deltas == 0 on the `adaptive`
  arm, `swr.failed == 0` and `swr.dropped == 0` in both arms.
- SWR arm **L.1s** (probe container), pre-declared before the first L.1/L.2
  run. L.1 produces zero SWR activity by construction — unique forward names
  are never re-queried — so its `swr.*` zeroes are an artefact of the workload
  and prove nothing about the ~69 % of deployed upstream attempts SWR owns.
  L.1s is L.1 with a bounded name set re-queried past its TTL, so stale hits
  enqueue refreshes continuously. Reports `swr.enqueued`, `swr.completed`,
  `swr.failed`, `swr.dropped` and `upstreams[].attempts`, and keeps SWR
  traffic separate from client-visible forwards through the identity
  `Σ attempts − (swr.completed + swr.failed) == cache_misses` — the same
  identity tier 2 uses, whose subtraction term L.1 never exercises. Its own
  acceptance table; its counts are **not pooled** into the tier-3 comparison,
  which stays on L.1 vs L.2 at the frozen threshold.
- Soak, 7 days (L.3): RSS half-to-half drift over the final third of each
  24 h window < 2 MB is the pass/fail; `penalties` (G4 false-penalty
  definition) and `swr.*` are reported, from `/telemetry` and
  `/history/perf`.
- Tier 3, if it survived `p2.6-10`: the named metric against the frozen
  threshold, same session as a `fallback` arm — both arms in the probe
  container, no production env change for them.
- S1-G4: `failure_runs` over the `fallback` window since the p2.5-06
  deploy, summed per process across restarts; state whether runs of ≥ 2
  exist; choose `penalty_failures` from the data or state that the window
  must be extended.
- `upstreams[].attempts` is not compared across the opt-in flip: `adaptive`
  excludes `resolve_host` attempts (spec S1.8).
- Perf-history disk growth (p2.6-06 F3): the seven telemetry fields add
  ~123 B per endpoint per 60 s sample, none of them `skip_serializing_if`.
  Calculated, never measured: 0.35 MB/day at two endpoints, 1.4 MB/day at
  the 8-endpoint cap; ~10 MB / ~43 MB retained at the default
  `history.retention_days = 30`. Measure actual `/data` growth on the
  RB5009 across the 7-day soak (`/file print` or `du` on the volume, first
  and last day) and record measured-vs-calculated in the results file.
  Bounded by retention, not by uptime or traffic — a figure above the
  calculated one is the finding.
- S1-G5: both rejection routes evaluated and written down.
- Results file: `docs/code-review/phase2.6/p2.6-11-optin-deploy-soak-review.md`,
  rewriting docs/project-state.md only with approval.

## Acceptance criteria

- Deployed build and deploy time recorded; opt-in confirmed via
  `GET /api/v1/config`.
- Each tier 2 invariant stated with its measured value.
- M.8 carries its own pre-declaration (K, ordering, warm-up, duration,
  stopping conditions) written before the first run, its own acceptance table
  with all three clauses measured, and an explicit statement of whether
  p2.6-08 F1 is closed.
- L.1s carries its own pre-declaration and acceptance table, with a stated
  decision on whether SWR needs an acceptance criterion of its own, and with
  `swr.completed > 0` demonstrated — otherwise the arm did not exercise SWR
  and reports no result.
- S1-G4 and S1-G5 each carry a decision and the evidence behind it.
- The table cell in the phase `CLAUDE.md` names what flips `AWAITING SOAK`.

## Out of scope

Changing the default (`p2.6-12`); any router change executed by the agent.
