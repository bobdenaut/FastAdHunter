# P2.5-05 — Outcome Telemetry: Client-Visible Failure and Endpoint Attribution

**Phase:** 2.5 · **Depends on:** — · **Model:** Opus

## Goal

A served SERVFAIL is countable, and a forwarded query's event names the
endpoint that answered — the two observability gaps that would otherwise
make Stage 1's benefit unmeasurable.

## Context

Reconciled §5.6: a forward failure with no stale entry synthesizes SERVFAIL
(`crates/fah-dns/src/pipeline.rs:405-418`) whose event is indistinguishable
from an ordinary pass (`verdict=Pass, cache_hit=false, upstream_used=false`)
— during a real outage the operator cannot measure how many clients saw
errors, and a before/after judgment of Adaptive DNS has no numerator.
Likewise `QueryEvent.upstream_used` is a bare `bool`
(`crates/fah-model/src/query_event.rs:34`); which endpoint answered is
recorded nowhere per query, which blocks per-endpoint attribution the
moment selection stops being "always the primary".

Constraint (p2-09 stands, on-device-verified): no query-log revival, no
Prometheus. Everything rides `/telemetry`, the WS event stream, and
`/history/perf`'s existing series.

## Scope

- Count client-visible failure: synthesized-SERVFAIL-served as its own
  counter in `/telemetry`; relayed upstream `SERVFAIL`/`REFUSED`
  distinguishable in aggregate from genuine answers. Persist via the
  existing perf-sample series if the addition is cheap; otherwise live-only.
- Endpoint attribution on the event: replace/augment `upstream_used` with
  the answering endpoint's identity (index into the configured set plus its
  address string — smallest stable shape). The no-answer case is explicit.
- Wire through: pipeline → `fah_model::Event` → fan-out → stats/metrics/WS.
  `hits + misses == pass + allow` and the stale identity invariants from the
  0.2.12 soak must survive or be consciously restated in the review file.
- API.md and tui-monitor field updates are listed for the owner's approval
  at execution time; the wire change itself must be `#[serde(default)]`-safe
  for the deployed tui-monitor (version-skew rule).

## Acceptance criteria

- Test: forward failure with no stale entry increments the SERVFAIL-served
  counter and the event says no endpoint answered.
- Test: a forwarded answer's event names the answering endpoint; a cache
  hit's event names none.
- Test: relayed SERVFAIL distinguishable from synthesized in aggregates.
- Invariant tests still green; gates green.

## Out of scope

Failure run-length tracking (p2.5-06); per-client failure attribution;
histogram changes; any persisted per-query record.
