# Plan — p2.5-07 SWR Claim Lease vs Worst-Case Upstream Walk

## Summary

The refresh claim lease becomes a constructor parameter the **binary**
derives from the upstream config — the cache keeps its documented refusal
to know upstream configuration (cache.rs:78-79), and the lease provably
exceeds the honest worst-case walk.

## Decisions (all fixed)

| Decision | Value |
| --- | --- |
| Worst-case walk bound | `3 × servers.len() × timeout_ms` — the per-server worst chain is failed send (≤ T) + reconnect connect (≤ T) + retry send (≤ T) on the pooled non-timeout-error path (`encrypted.rs:84-96`, connect timeout at :158-160); plain UDP's TC→TCP retry also fits inside 3T |
| Lease formula | `lease = max(5 s, 2 × 3 × N × T)` where N = `config.dns.upstreams.servers.len()`, T = `timeout_ms` |
| Shipped-defaults consequence | 2 × 800 ms → lease 9.6 s (was 5 s) — deliberate; a longer lease only delays reclaiming an abandoned claim and strengthens duplicate-refresh suppression (cache.rs:74-77 rationale); it can never produce a wrong answer or an unrefreshable entry |
| Parameter path | `DnsCache::new(config: &DnsCacheConfig, refresh_claim_lease: Duration)` (cache.rs:443) and `Pipeline::new(rules, forwarder, blocking_ttl, cache_config, refresh_claim_lease: Duration, events)` — sixth parameter, before `events` |
| Default for tests/benches | `pub const DEFAULT_REFRESH_CLAIM_LEASE: Duration = Duration::from_secs(5)` exported from `crates/fah-dns/src/cache.rs` (pub because `crates/fastadhunter/benches/pipeline.rs` constructs a Pipeline); the private `REFRESH_CLAIM_LEASE` const is deleted in favor of the stored field |
| Derivation site | `crates/fastadhunter/src/main.rs`, one expression at Pipeline construction, from the already-parsed `config.dns.upstreams` |
| Config validation | none added — no boot-failure path for any servers×timeout combination (deliberate: the `deny_unknown_fields` migration-trap class) |
| Rejected alternative | recorded here once: config-load rejection of large walks — turns a working config into a boot failure for something a derived lease absorbs silently |

## Implementation units

**U1 — parameterize.** `DnsCache` stores `refresh_claim_lease: Duration`;
`lookup_and_claim_refresh` and every lease-expiry comparison read the
field. Constructor signatures per the table; call-site sweep:
`Pipeline::new` in main.rs (derived value), the ~6 in-crate test sites
and `crates/fah-dns/benches/cache.rs` + `crates/fastadhunter/benches/pipeline.rs`
(pass `DEFAULT_REFRESH_CLAIM_LEASE`). The stale const-rationale comment
block at cache.rs:69-80 is **deleted** (hook permits deletion only; the
mechanism is recorded in the review file).

**U2 — derivation.**
`let lease = Duration::from_millis(6 * servers.len() as u64 * timeout_ms as u64).max(Duration::from_secs(5));`
in main.rs at pipeline construction.

**U3 — record for S1.9.** Review file states: bound `3NT`, lease
`max(5 s, 6NT)`, guarantee "lease ≥ 2 × worst-case walk, floor 5 s", and
the 5 s → 9.6 s defaults change — so the Stage 1 spec's S1.9 section can
cite it verbatim.

## Invariants (must hold before and after)

- Lease ≥ 2 × (3 × N × T) for every constructible config, and ≥ 5 s
  always.
- `REFRESH_FAILURE_COOLDOWN` (30 s), `STALE_SERVE_TTL`, `MAX_STALE`, SWR
  worker count and queue bounds, and drop-not-backpressure (ADR-0005) are
  unchanged.
- Claim/dedup semantics unchanged — only the expiry duration is
  parameterized.

## Tests (all objectively checkable)

1. Derivation unit test (in fastadhunter, next to the expression or as a
   pure fn): (2, 800) → 9.6 s; (8, 800) → 38.4 s; (1, 100) → 5 s.
2. Cache lease test parameterized: constructed with a 50 ms lease, a
   claimed entry is re-claimable after 60 ms and not after 10 ms (proves
   the field is consumed; replaces the const-based expiry test).
3. All existing SWR/claim/cooldown tests green with
   `DEFAULT_REFRESH_CLAIM_LEASE`.

## Out of scope (closed paths)

- No SWR EDNS change; no 8-endpoint config cap (Stage 1); no worker or
  queue changes; no config key for the lease; no per-entry lease.
- No change to how the walk itself is timed or bounded.
