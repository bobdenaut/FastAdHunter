# P2.5-01 — Listener Resilience and a Real Healthcheck

**Phase:** 2.5 · **Depends on:** — · **Model:** Opus

## Goal

A transient socket error no longer kills a DNS listener permanently, and the
container healthcheck detects a dead listener instead of only re-parsing
config.

## Context

The GAR's highest-impact operational finding (Reconciled §5.1): the UDP
receive loop and the TCP accept loop `warn` and `return` on any socket error
(`crates/fah-dns/src/udp.rs:24-31`, `crates/fah-dns/src/tcp.rs:31-38`). No
task supervision exists (`Engine.tasks` is abort-only), the healthcheck only
re-validates config parse, RouterOS has no auto-restart, and the router's
netwatch failover masks a dead resolver as *unfiltered* resolution. The API
accept loop already shows the correct pattern — tolerate transient errors
with sleep-and-continue (`crates/fah-api/src/server.rs:115-124`).

## Scope

- Retry-with-backoff in both DNS listener loops, modeled on the API accept
  loop: a transient error (EMFILE/ENFILE, ECONNABORTED, transient recv
  failures) sleeps and continues; the loop never returns while the process
  lives. If a class of error is provably unrecoverable, it must escalate
  loudly (process exit is acceptable — a dead process is restartable and
  visible, a dead task inside a green process is neither).
- Happy path untouched: changes live on the error path only; no new work per
  datagram/accept.
- Healthcheck (`--healthcheck`) exercises the DNS path: one UDP query against
  the configured listen address with a short timeout, in addition to the
  config parse. A process with a dead listener must fail the healthcheck.
- This loop shape becomes the template future listeners (Phase 3 DoT/DoH,
  SNI) inherit.

## Acceptance criteria

- Test: an induced transient accept/recv error does not terminate the
  listener loop; subsequent queries are served.
- Test: healthcheck fails when no listener answers on the configured port,
  passes against a live one.
- DNS benches unchanged (error-path-only claim verified).
- Gates green.

## Out of scope

Task supervision/respawn framework (heavier design — GAR ADR candidate 4);
RouterOS-side auto-restart (owner's device); TCP connection-count cap
(recorded GAR assumption, separate concern).
