# P1.5-05 — Byte-Aware Cache Cap + Sustained Throughput

**Phase:** 1.5 · **Depends on:** phase1 (`fah-dns` cache) · **Model:** Opus

## Goal

Bound the DNS cache by **bytes**, not just entry count, so the worst-case
memory ceiling respects the 128 MB budget under adversarial input — and take
the sustained-throughput measurement deferred from p1-11.

## Context

The ~91h soak (docs/code-review/p1-11-soak.md) proved the cache is bounded but
by **entry count**: under `test_aleator.py`'s worst-case mix (7 query types ×
1M unique domains → millions of large TXT/SOA/NXDOMAIN answers) the *byte*
ceiling reached ~230 MiB on-device — 80% over budget — while real traffic sits
at ~55 MiB. Still bounded, never near OOM, but it's a mild DNS-water-torture
surface. The O(1) FIFO eviction (`crates/fah-dns/src/cache.rs`) and the byte
estimator built for `GET /api/v1/debug/memory` already exist — this task turns
the estimator into an *enforced* cap. Do **not** change caching semantics
beyond eviction (root CLAUDE.md hard rule #3; the earlier O(1) work preserved
semantics — keep that invariant).

## Scope

- Add a configurable byte budget for the cache (e.g. `[dns.cache] max_bytes`,
  default sized to keep total RSS within the 128 MB budget; document the
  interaction with the existing entry `capacity`).
- Enforce it in the eviction path: evict oldest (existing FIFO) until **both**
  the entry count and the byte estimate are within bounds. Reuse the per-entry
  byte accounting already computed for the debug/memory estimator; keep
  eviction O(1) amortized (no full scan on the hot path).
- Expose the byte ceiling + current bytes in `GET /api/v1/cache` (the UI graphs
  it via p1.5-02's sampler).
- **Sustained-throughput measurement:** extend the criterion throughput bench
  (or a dedicated on-device run) to report steady-state QPS with the cap
  active; record numbers in PERFORMANCE.md. Pin cores per the bench-noise note.
- PERFORMANCE.md: document the byte cap and the measured ceiling under the
  worst-case workload.

## Acceptance criteria

- Under a synthetic large-answer flood, cache byte usage plateaus at the
  configured cap (verified in a test with a low cap); entries evict oldest-first
  and semantics (allow > block ordering, subdomain matching, serve-stale) are
  unchanged.
- Real-traffic behavior unchanged (cap not hit at ~55 MiB).
- Eviction stays O(1) amortized; no >10% regression on the cache benches
  (PERFORMANCE.md), or a justified note.
- Sustained-throughput figure recorded.
- Gates green.

## Out of scope

Any other cache redesign; changing TTL clamps or serve-stale windows.
