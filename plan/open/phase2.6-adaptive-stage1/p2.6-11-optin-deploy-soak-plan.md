## Implementation changes

No code. Sequence:

1. **Merge-gate check** (dev box): S1-G1 #1–#17 green (list the test names
   and their task of origin); p2.6-08 and p2.6-09 results files exist and
   meet their criteria. Any miss → stop; the phase table stays `WAITING`.
2. **Release proposal**: version bump commit (owner-approved), image build
   command, push to the registry the project uses, and the container
   update sequence as p2.5-09 did it — each router command listed with
   effect and timing. Deploy order: binary first; the env opt-in second,
   as a separate container edit the owner applies after the new binary is
   confirmed healthy under `fallback`.
3. **T0 snapshot** after opt-in: `GET /api/v1/config` shows `adaptive`;
   `/telemetry` baseline saved to the review file.
4. **Soak, 7 days** (S1-L L.3, production container): daily read-only
   snapshots. Tier 2 invariants computed as deltas: penalties on a healthy
   link (expect 0 or suite T's base rate); `state` never leaving `healthy`
   on a healthy link; SWR attempts and outcomes (`swr.*`, which `adaptive`
   does not change) comparable to the 0.2.18 window; RSS slope over the
   final third of a 24 h window < 2 MB. **`upstreams[].attempts` is not
   compared across the flip**: under `adaptive` it excludes `resolve_host`
   (≈ 20 % of the 0.2.18 mix, spec S1.8), so a drop of that order is the
   accounting, not the feature — state it beside the figure. Attempts per
   forwarded query (expect 1.000) is read in L.1/L.2 only.
   **Tier 2 L.1/L.2 and tier 3, if alive**: both arms run in the **probe
   container** with its own config — `strategy` flipped there, the
   production container's env untouched for these arms. The p2.6-10 metric
   is compared against its frozen threshold, same session, flat control arm.
5. **S1-G4**: `failure_runs` over the `fallback` window — from the p2.5-06
   deploy to the opt-in flip — per endpoint, **as the sum of per-process
   deltas** read from `/history/perf`: the counters are cumulative per
   process and the window contains at least two restarts (0.2.16 → 0.2.18
   → the 2.6 binary under `fallback`), so `end − start` across a restart
   undercounts (M10). State the bucket counts; decide whether runs of ≥ 2
   exist and at what share; derive `penalty_failures` from that or state the
   window must extend (preferred over guessing). Carry the
   concurrency-splitting caveat verbatim. Samples after the flip are a
   different quantity (throttled attempts) and are not pooled.
6. **S1-G5**: route 1 (no partial failure) — already false per suite T,
   confirm; route 2 (isolated losses only, runs of ≥ 2 absent) — decide
   from step 5.
7. **Outcome record**: `docs/code-review/phase2.6/p2.6-11-optin-deploy-soak-review.md`
   with every number, its window, device, build; then propose the
   `docs/project-state.md` rewrite (owner approval).

## Non-goals

Flipping the default; any router change by the agent; tuning

amendment for the owner, not a config change); Stage 2/3 readings of the
data.

## Open items (procedural — no spec contradiction)

- **Opt-in needs a container env edit**, which is a `/container set`
  command — on the owner's forbidden-for-the-agent list. It is proposed
  exactly and left to the owner; the plan does not assume it has been done
  until `GET /api/v1/config` shows `adaptive`.
- **Tier 3 `fallback` arm** is L.2 in the probe container (its own config,
  benchmarks §S1-L), not a production env flip — no extra `/container set`
  on the production container is proposed for it (M11). If the probe
  container is unavailable, tier 3 is reported as not run and the
  healthy-path claim rests on tiers 1–2, which the spec allows.

## Acceptance criteria

- Merge-gate check written down with the evidence list.
- Deploy and opt-in recorded with build, time, `GET /api/v1/config`.
- Every tier 2 invariant has a measured value and a pass/fail.
- S1-G4 and S1-G5 carry decisions with evidence; if the window is
  extended, the review file says what date re-evaluates it and the phase
  table cell names it.
