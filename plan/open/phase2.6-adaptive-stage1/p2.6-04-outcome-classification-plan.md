## Implementation changes

1. In `health.rs` or a sibling `classify.rs` (pure, no I/O):
   `pub fn classify(transport: TransportKind, result: &io::Result<Message>) -> Outcome`
   where `TransportKind { Plain, Encrypted }` is derived from the `Transport`
   variant at the call site.
   - `Ok(_)` → `Success` regardless of RCODE.
   - `Err(e)` by `e.kind()`:
     `ConnectionRefused | NetworkUnreachable | HostUnreachable` → `PathFailure`;
     `InvalidData` → `PathFailure` **when `Encrypted`** (the only producer is
     a `rustls::Error` in the chain — `transport_error_kind`; a
     post-handshake record-decrypt error is classified the same way, spec
     S1.4), `HardFailure` when `Plain` (TCP-leg decode failure, see C4);
     everything else (`TimedOut`, `Other`, `NotFound`, `InvalidInput`,
     `ConnectionReset`, `BrokenPipe`, `AddrNotAvailable`, the `EMFILE` /
     `ENOBUFS` kinds a local `bind`/`send` can raise, …) → `HardFailure`.
     Local-resource errors are not endpoint properties, but they are not
     separable per endpoint without a taxonomy; spec S1.4 accepts them as
     hard failures — every endpoint fails together and the hard invariant
     keeps sending.
     `ConnectionReset` is deliberately hard on both transports: on an
     encrypted connection it is a transient the attempt already reconnects
     through; on UDP it is what **Windows** reports for ICMP port
     unreachable, which Linux reports as `ConnectionRefused`. The dev box is
     Windows, so the UDP path-failure row is reachable only on Linux (spec
     S1.4 platform note).
2. `pub enum HealthMode { Record, Ignore }` — a plain parameter threaded
   through the attempt loop in p2.6-05. In `Ignore`, p2.6-05 skips every
   `Health` mutation including `attempts`. Nothing in this task changes
   `plain.rs` or `encrypted.rs` behaviour.
3. `TransportKind` is read from `Transport` once per attempt (a match on an
   enum already in hand; no allocation).

## Contradictions — resolved by the owner (2026-08-23)

- **C4 — accepted: classification is transport-specific.** Within
  `Encrypted`, `InvalidData` ⇔ a rustls error in the chain
  (`transport_error_kind`) → `PathFailure`. Within `Plain`, `InvalidData`
  is a TCP-leg wire-decode failure → `HardFailure`. DoH bootstrap
  `resolve` → `NotFound` → `HardFailure`. Both additional cases are now
  pinned by tests in this task; if a future producer emits `InvalidData`
  on the encrypted path for a non-TLS reason, the classification test
  catches it.
- **Not a contradiction, noted:** the encrypted transport's internal
  reconnect-and-retry (`encrypted.rs:117-124`) means one attempt can contain
  two sends. The spec's "idle-close → transparent reconnect → answer =
  success" is satisfied by classifying the final result only.
- **LOW (validation 2026-08-23, accepted):** local socket errors and
  post-handshake rustls errors are classified as the table above says and
  documented in spec S1.4; the Windows `ConnectionReset` platform note is
  carried into the tests. `HealthMode` is defined here but the selector's
  flag is a plain `bool` owned by p2.6-03 (B2); p2.6-05 maps
  `HealthMode::Record` to `claim = true`.
