## Implementation changes

1. **`UpstreamPool`** gains `health: Arc<[Health]>`, `policy: Policy`,
   `epoch: Instant`, `strategy: UpstreamStrategy`. Built in `with_tls_config`:
   `Policy::from_timeout(config.timeout_ms, penalty_failures as u8)` (base =
   `10 × ATTEMPT_LEGS × timeout_ms`, C2), one `Health::new()` per server.
   Per C3 (decided): `attempts` and `failures` move into `Health`;
   `consecutive_failures` and `run_buckets` stay on `UpstreamServer`.
2. **`fallback` branch**: the existing loop body verbatim, with
   `server.attempts` / `server.failures` reading `self.health[index]`. No
   other edit. Behaviour identical; tests untouched.
3. **`adaptive` branch** — private `async fn forward_adaptive(&self, query, mode: HealthMode)`:
   ```text
   start = 0; last_err = None; probed = false
   loop:
     claim = mode == Record && !probed
     cand = select(&health, start, || elapsed_ms(epoch), claim)  — None → break
     if cand.selected == Probe: probed = true
     if mode == Record: health[id].attempts += 1; if Probe: probes += 1
     result = servers[id].query(query, timeout).await
     if mode == Record:
        t = record(&health[id], classify(kind, &result), elapsed_ms(epoch), &policy)
        if let Some(run) = t.closed_run → run_buckets[run_bucket(run)] += 1
        if let Some(ms) = t.penalty_applied → penalties += 1; penalized_ms_total += ms
        if Probe && Ok → probe_successes += 1
     Ok → alarm.clear(); return ForwardOutcome(msg, id)
     Err → failures += 1 (Record only); last_err = Some; start = id + 1
   alarm.claim(); return last_err
   ```
   `claim` carries two rules through one `bool` (spec S1.5, S1.8): `Ignore`
   never claims — a claim with no recorded outcome would leave the word in
   `Probing` with no probe in flight (validation B2) — and a query claims at
   most one probe; after the first claim, later due endpoints on the same
   query are skipped like not-due ones (M3). `Probe` can only be returned
   when `claim` was true, so `probed` and `probes` move only in Record mode.
   `elapsed_ms` is `Instant::now().duration_since(epoch).as_millis() as u64`,
   called at most twice per attempt and never on the all-Healthy success path
   (the closure in `select` is not invoked on an all-Healthy pass —
   p2.6-03; `record(Success)` on a clean Healthy word needs no time —
   p2.6-02 M.5).
4. **`Forwarder::forward`** dispatches on `self.strategy`; the pipeline and
   SWR call it unchanged (`Record`). `lookup` calls
   `self.forward_with(query, HealthMode::Ignore)` under `adaptive`; under
   `fallback` it calls the existing path (no mode exists there).
5. **Path failure on a forced attempt**: handled inside `next_word`
   (Penalized + any failure = counter only) — no special case here. A
   forced attempt landing on a word that is meanwhile `Probing` follows the
   Probing row (round + 1); nothing here distinguishes the cases (H3).
6. **Alarm semantics** unchanged: `clear()` on any success, `claim()` when
   the scan exhausts. Under `adaptive` the scan exhausts after trying the
   Healthy set, at most one probe and the forced endpoint, so the alarm
   still fires during a full outage (S1.15).
7. **`status()`** keeps returning today's `UpstreamStatus` fields (new
   fields are p2.6-06); `consecutive_failures` reports the packed field
   under `adaptive`, the plain counter under `fallback`.
8. **Test seam for scaled policy**: `#[doc(hidden)] pub fn with_policy(config, policy) -> io::Result<Self>`
   (p2.6-09's bench is an external target and cannot reach `#[cfg(test)]`
   or `pub(crate)` seams). Default: `#[doc(hidden)] pub`; a `bench` feature
   only if the owner asks for one at task start.
9. Wrap no new `Arc`, `Vec`, `String` or `Box` on the forward path;
   `ForwardOutcome` stays as is.

## Contradictions — resolved by the owner (2026-08-23)

- **C2** — `attempt_bound_ms = ATTEMPT_LEGS × timeout_ms`; `Policy` base is
  `10 ×` that (step 1). The S1.17 concurrency test's "within one
  `attempt_bound_ms` of the live endpoint" uses the same value.
- **C3** — split as in p2.6-02 (steps 1–2).
- **Clock reads (now stated in spec S1.10/S1.11):** `forward` reads no
  clock today (timeouts are tokio timers). Under `adaptive` the clock is read
  lazily — at the first non-Healthy word a pass meets, and once more when an
  outcome is recorded off the clean-Healthy path (step 3) — so "syscalls
  added: 0" holds for the all-Healthy steady state and ≤ 2 `clock_gettime`
  (vDSO) per attempt are added off it. Report the measured cost in the
  review file; p2.6-08 M.3 carries it.
- **B1 / B2 / M3 (validation 2026-08-23, accepted):** the loop in step 3
  passes `claim = mode == Record && !probed` to the one-pass selector; G1 #8
  (live endpoint behind the due one), #16 and #17 pin the three rules.
- **M5 — `attempts` coverage changes under `adaptive`. Decided by the
  owner (2026-08-23): `resolve_host` attempts stay uncounted in Stage 1.**
  `Ignore` moves no counter, so `resolve_host` attempts (≈ 20 % of the
  deployed mix) vanish from `upstreams[].attempts` / `failures` under
  `adaptive` while `fallback` counts them. Not a code change — B.7 forbids
  counting them — but the review file states it, p2.6-07 puts it in API.md,
  and p2.6-11 reads `attempts` accordingly. Do not revisit inside the task.
- **H1:** the `DnsUpstreamsConfig` literal field was added by p2.6-01; this
  task adds no line to the existing `fallback` tests.
