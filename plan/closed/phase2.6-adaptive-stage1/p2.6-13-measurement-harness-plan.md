# P2.6-13 — On-device measurement harness — Implementation Plan

No runtime code. No router command executed by the agent — every one is
proposed and the owner runs it (working agreement).

## What "done" means, and what it does not

Done is **the harness exists and one trial repetition works**. It is not a
benchmark-tuning project. The protocol is already frozen in p2.6-10's review and
validated on the dev box; this task moves that shape onto the device and stops.

Explicitly **not** done here, and not a reason to keep the task open:

- The trial repetition's numbers looking good, quiet, or close to a budget.
- The achieved rate reaching 10 000 QPS. Whatever the harness holds is measured
  and recorded; a lower figure is a result, not a defect to tune away.
- Any iteration on the protocol, the metric order, the N estimator or the
  S1-G2 acceptance rule. All four are frozen and out of scope.
- Re-running the trial to get a different answer. One repetition, reported as it
  came out.

If the trial reveals a genuine harness defect — a metric that never populates, a
mount that does not write through, a generator that cannot hold a declared rate
— that is reported and the task stops for a decision. It is not silently worked
around.

## Steps

### 1 — Read-only pre-flight (owner runs, agent reads the output)

No write command is drafted until these are back. Mount names, `root-dir`, the
veth, routes and firewall placement are deployment-specific and are **never
guessed**.

```text
/system/resource/print
/container/print detail
/container/mounts/print detail
/interface/veth/print detail
/ip/route/print
/ip/firewall/filter/print where chain=forward
/file/print where name~"kingston"
```

### 2 — Freeze the harness decisions

Recorded before anything is built, and not revisited once the trial starts:

- The load generator: which one, which host it runs on, and its exact
  invocation including the fixed offered rate.
- The mock upstreams: which software, where they run, the forward zone's short
  TTL and the control zone's long TTL.
- Whatever routing or firewall the two above require, decided from step 1's
  output — a firewall rule is never proposed as a bare `add`, because `add`
  appends behind any final drop.

### 3 — Build and ship the probe image

Cross-compile `aarch64-unknown-linux-musl`, pack as a single-layer OCI tar,
convert to a docker-archive with skopeo — RouterOS cannot import OCI layout and
has no `docker` CLI. `scp` to the Kingston store needs the owner's permission
for each use. `buildx` needs QEMU re-registered after any Docker Desktop restart
and the builder container restarted afterwards.

### 4 — Propose the container add (owner runs)

Drafted from step 1's actual values, each command with its effect and when it
takes effect. Fixed constraints:

- Its own veth, its own `root-dir` **under `kingston/`** — without that prefix
  the image lands on the internal NAND.
- Its own mounts and its own config; the production container's mounts, env
  lists and comment are not reused or modified.
- `logging=yes` — not the default, and the only channel that reports the probe's
  generated API key, which is printed exactly once at first boot.
- `start-on-boot=no`.
- No `memory-high`. It once OOM-killed the live resolver.
- Probe config: `strategy = "fallback"`, the two mock upstreams as
  `address = "<ip>:<port>"` entries, and `history.sample_interval_seconds` fine
  enough to yield several perf rows per repetition — the production container's
  360 s yields one or two per ten minutes.

### 5 — Verify the harness

- Probe container answers on its own DNS port and its own API;
  `GET /api/v1/config` reports the intended probe configuration.
- Both mocks answer; the probe's `upstreams[]` shows attempts against them.
- `/api/v1/telemetry` and `/api/v1/history/perf` both return; perf rows appear
  at the configured cadence.

### 6 — One trial repetition

Exactly one, through the frozen protocol — settle, T0, load, 30 s drain, T1,
perf pull. Every metric checked for population: `forward` count and mean,
`cache_hit` count and mean, total upstream attempts, attempts per forward,
server QPS, and enough perf rows to read the percentiles.

Achieved rate and loss are taken from the generator's own report and recorded.
The 10 000 QPS figure is a target, not an assumption.

### 7 — Teardown

Probe container removed. Production container shown untouched — same uptime, same
config, same counters advancing normally.

## Implementation changes

None to runtime code. The deliverable is a procedure plus one trial result.

Whether the collector, analyser and generator scripts are committed to the
repository — and where — is an owner decision, not part of this plan.

## Tests

None. The trial repetition is the verification.

## Benchmarks / gates

None of its own. It unblocks S1-N (p2.6-10) and the S1-L arms (p2.6-11).

## Dependencies

The owner's time and the owner's approval for each router write and each `scp`.
No code dependency.

## Non-goals

Running the K ≥ 6 null A/B; running `adaptive`; any S1-L failure arm; any change
to runtime code, to the production container, to the S1-G2 acceptance rule, to
the S1-N metric order, or to the frozen protocol.

## Open items for the owner

- Where the harness scripts live, if they are committed at all.
- Generator host: a second container on the device, or a LAN host driving the
  probe across the container bridge.
- Mock upstream host: same decision, same routing and firewall constraint.

## Acceptance criteria

As listed in the task file: probe container up and answering on its own API with
the intended config; two mocks answering with attempts recorded against them;
generator holding a declared fixed rate with achieved rate and loss recorded;
one trial repetition completing with every metric populated and enough perf rows
to read the percentiles; the procedure written down as a repeatable command
sequence; probe removed and production shown untouched.
