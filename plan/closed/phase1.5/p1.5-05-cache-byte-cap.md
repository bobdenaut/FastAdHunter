# P1.5-05 — Memory Hardening: Byte-Aware Cache Cap + Rule Deduplication

**Phase:** 1.5 · **Depends on:** phase1 (`fah-dns` cache, `fah-rules` matcher)
· **Model:** Opus

Two independent memory-hardening deliverables:

- **A. Byte-aware cache cap** (+ sustained-throughput measurement) — below.
- **B. Rule deduplication in the compiled matcher** — the section
  "Rule deduplication (compiled matcher)".

## Goal (A — cache cap)

Bound the DNS cache by **bytes**, not just entry count, so the worst-case
memory ceiling respects the 128 MB budget under adversarial input — and take
the sustained-throughput measurement deferred from p1-11.

## Context

The ~91h soak (docs/code-review/phase1/p1-11-soak.md) proved the cache is bounded but
by **entry count**: under `test_aleator.py`'s worst-case mix (7 query types ×
1M unique domains → millions of large TXT/SOA/NXDOMAIN answers) the *byte*
ceiling reached ~230 MiB on-device — 80% over budget — while real traffic sits
at ~55 MiB. Still bounded, never near OOM, but it's a mild DNS-water-torture
surface. The O(1) FIFO eviction (`crates/fah-dns/src/cache.rs`) and the byte
estimator built for `GET /api/v1/debug/memory` already exist — this task turns
the estimator into an *enforced* cap. Do **not** change caching semantics
beyond eviction (root CLAUDE.md hard rule #3; the earlier O(1) work preserved
semantics — keep that invariant).

## Scope

- Add a configurable byte budget for the cache (e.g. `[dns.cache] max_bytes`,
  default sized to keep total RSS within the 128 MB budget; document the
  interaction with the existing entry `capacity`).
- Enforce it in the eviction path: evict oldest (existing FIFO) until **both**
  the entry count and the byte estimate are within bounds. Reuse the per-entry
  byte accounting already computed for the debug/memory estimator; keep
  eviction O(1) amortized (no full scan on the hot path).
- Expose the byte ceiling + current bytes in `GET /api/v1/cache` (the UI graphs
  it via p1.5-02's sampler).
- **Sustained-throughput measurement:** extend the criterion throughput bench
  (or a dedicated on-device run) to report steady-state QPS with the cap
  active; record numbers in PERFORMANCE.md. Pin cores per the bench-noise note.
- PERFORMANCE.md: document the byte cap and the measured ceiling under the
  worst-case workload.

## Acceptance criteria

- Under a synthetic large-answer flood, cache byte usage plateaus at the
  configured cap (verified in a test with a low cap); entries evict oldest-first
  and semantics (allow > block ordering, subdomain matching, serve-stale) are
  unchanged.
- Real-traffic behavior unchanged (cap not hit at ~55 MiB).
- Eviction stays O(1) amortized; no >10% regression on the cache benches
  (PERFORMANCE.md), or a justified note.
- Sustained-throughput figure recorded.
- Gates green.

## Rule deduplication (compiled matcher)

### Why (context)

The engine does **no rule deduplication**. `MatcherBuilder::add_rule`
(`crates/fah-rules/src/matcher.rs`) unconditionally appends every rule's domain
to the arena, pushes an 8-byte `Record`, and `build()` linear-probes each into
the hash table — identical domains "simply occupy extra slots" (the module doc
says so). This holds even for exact duplicates **within one list**. Lists merge
into one combined matcher at compile time
(`crates/fah-rules/src/lifecycle/mod.rs`, `compile()` on the blocking pool);
each list's raw text is cached independently on `/data` and lists are
independently add/removed/toggled.

Correctness is fine today (lookup applies allow > block > pass over all
colliding slots), so this is a **memory/size** problem: two overlapping ~1M
lists store their overlap twice — arena bytes + 8 B/record + ~1.43× hash slots —
eating into PERFORMANCE.md's ≤40 MB/1M-domains budget on a 1 GB box. Surfaced
by a user loading AdGuard HostlistsRegistry `filter_48.txt` and HaGeZi
`pro.txt` (near-identical content, both loaded in full).

**Goal:** the compiled matcher holds **distinct rules only**.

### Design

- **Where:** dedup at the single merge point — `MatcherBuilder`, in `add_rule`
  — so the per-list `/data` caches stay whole (removing a list still works) and
  both cross-list and intra-list duplicates collapse for free. Early-return on a
  duplicate so the arena bytes / record / slot are never allocated (reclaims
  memory up front).
- **Dedup key = full rule identity**, not domain:
  `(domain, action, include_subdomains, dns_types, dns_rewrite)` — `list_id` is
  attribution, **not** identity. In the compiled layout that identity already
  lives across `arena` (domain bytes) + `Record.flags` (allow/subdomains/
  dnstype/rewrite presence) + the `dnstype`/`rewrite` side maps (keyed by record
  index) — see `matcher.rs`.
- **Mechanism (mandated — most memory-efficient bounded approach, not the
  first that compiles):** dedup against the **arena as the source of truth**,
  never against a redundant owned-key store. Concretely: a transient
  open-addressing **`Vec<u32>` of record indices** keyed by a full-identity
  hash. On `add_rule`: hash the identity, probe; for each candidate index it
  points at, compare the incoming `&DomainRule` **by reading arena + record
  flags + (rarely) the side maps**; match → skip and never append the
  duplicate's bytes; else append + insert the index. The u64 hash only
  accelerates the probe — accept/reject is a **real byte/field compare**, so a
  hash collision can never silently drop a distinct rule. `~5.7 MB` transient at
  1M rules, no `Arc` clones, deterministic by construction (membership-only
  table, never iterated for output). See "Memory note" for why the owned-key
  `HashSet` is rejected.
  
  Required properties of the implementation:
  - arena remains the single source of truth
  - duplicate bytes must never be appended
  - transient memory should be O(distinct rules)
  - no owned duplicate representation
  - no hash-only acceptance
  - deterministic output
- **The lookup table is sized once.** It is allocated a single time at the start
  of compilation with a capacity derived from the expected distinct-rule count
  (the total parsed-rule count is a safe upper bound; the load-factor headroom
  the real slot table already uses applies here too) and freed immediately after
  `build()`. It must **not** grow-and-reallocate as rules are inserted — a
  `Vec::with_capacity(_)` up front, never a `Vec::new()` that doubles a dozen
  times mid-compile. One allocation, one free; no realloc churn on the compile
  path.
- **Verdicts unchanged:** only *identical* rules collapse. Block-in-A +
  allow-in-B for the same domain are different keys → both kept → `lookup` still
  returns Allow (allow > block). A `$dnstype`-scoped rule and a plain rule for
  the same domain are different keys → both kept.
- **First-contributor wins attribution:** the kept rule is attributed to the
  first list that supplied it (compile order = enabled ids, then `USER_RULES`);
  the duplicate's list attribution is dropped. **Rule semantics are unaffected —
  attribution is informational only** (query-log / `rules/test` reporting),
  never an input to the verdict. A "matched in N lists" feature is out of scope.

### Observability (decided — expose in metrics + API)

- Per-list `RefreshStats` (active/inactive) stay parse-based / pre-merge —
  unchanged.
- The compiled matcher `len()` now equals distinct rules → the reported total
  reflects dedup (the intended behavior change).
- `MatcherBuilder` tracks a `duplicates_removed` count carried onto the built
  `Matcher` (accessor). The telemetry poll (`main.rs`) reads it like
  `len()`/`heap_bytes()` into `fah_metrics::RulesetSnapshot`
  (`compiled_rules` + `duplicates_removed`), exposed as a Prometheus gauge and
  on the lists/ruleset API response (`crates/fah-api`, alongside
  `rules_total`/`rules_active_dns`/`rules_inactive` in `wire.rs`) so a future
  Pi-hole-style UI can show it. Also logged at compile
  (`INFO removed N duplicate rules across M lists`).

### Cost

- **Query (lookup) performance MUST remain unchanged** — dedup is build-time
  only; `lookup` is untouched (marginally faster with fewer slots). Hard rule
  #3 intact. Hard requirement, not a nice-to-have.
- Compile time **may increase modestly** and that is acceptable: one probe +
  identity compare per rule. Compile already runs on `spawn_blocking` off the
  hot path.

### Memory note (the transient dedup structure)

The requirement is the outcome — **lowest bounded compile-time peak** — not a
named container. Performance and memory are primary objectives here, so the plan
mandates the efficient mechanism rather than fixing the first one that compiles.
The transient dedup structure is freed after `build()`; steady-state RSS and the
query hot path stay flat regardless. Ranked:

- **Mandated — hash → record-index into the arena (`Vec<u32>`):** ~1.43×
  record-count of `u32` → **~5.7 MB for 1M distinct rules**, no `Arc` clones.
  Arena is the source of truth; the hash is only a probe accelerator and every
  accept/reject is a real field compare. This is the design above.
- **Rejected — owned-key `HashSet<(domain, …)>`:** ~56–64 B/distinct-rule →
  **~60–70 MB for 1M**, ~12× the transient for **zero correctness gain**, and it
  pins an `Arc` refcount per distinct rule. Simpler to write, but "simplest to
  write" is not the bar in a memory-primary project. Not used.
- **Rejected — dead-bit + compaction inside `build()`:** correct and low
  steady-state, but duplicate bytes are already in the arena by compaction time,
  so peak briefly holds ~2× arena. The mandated approach never appends a
  duplicate's bytes at all, so its peak is strictly lower. Not used.
- **Non-negotiable regardless of mechanism:** no hash-only set (a 64-bit
  collision could silently drop a distinct rule → under-blocking); steady-state
  memory and the query hot path stay flat.

**At execution: still measure the compile-time RSS spike on the RB5009** to
confirm the ~5.7 MB estimate and the flat steady-state — but the mandated
mechanism is the starting point, not a fallback to switch to.

### Determinism (required)

Compiling the **same enabled rule lists must always produce the same matcher**,
regardless of any hash-table probe order:

- The dedup index table is used **only for membership** (probe → compare →
  insert); it is **never iterated to build output**. Records/arena/slots are
  produced by processing rules in a fixed order (enabled list order, then
  `USER_RULES`; file order within each list), so first-seen-wins is
  deterministic. (Open addressing over a `Vec<u32>` has no iteration-order
  hazard anyway — it stores indices, and output comes from the record vector.)
- No output ordering may depend on `HashMap`/`HashSet` iteration (existing
  `dnstype`/`rewrite` side maps are keyed lookups, not iterated for output —
  keep it so).
- **The table's capacity and probe order must not influence the output.**
  Which rule survives a collision is decided by *insertion order*
  (first-seen-wins), never by where a probe happens to land, so the chosen
  `Vec::with_capacity(_)` size — and any future change to it — must leave the
  compiled arena/records/slots byte-identical. Capacity is a performance knob
  (avoiding realloc, per the sizing note), never a correctness input.
- **Test:** compile the same lists twice → assert byte-identical matcher (same
  `len()`, arena, records in the same order — compare a structural fingerprint).
  Extend it: compile once more with a deliberately different transient-table
  capacity (e.g. min vs. oversized) and assert the same fingerprint — proving
  capacity is inert to the output.

### Acceptance criteria (B — dedup)

- Two lists sharing a domain → `len()` counts it once; verdict unchanged.
- Same domain, block in A + allow in B → both survive; `lookup` returns Allow.
- Same domain, different `$dnstype` → both survive (distinct keys).
- Exact duplicate within one list → collapsed; `duplicates_removed` correct.
- Double-compile determinism test passes.
- Lookup bench unchanged (hot path); matcher build bench: modest compile-time
  increase acceptable, memory drops on overlapping input. Pin cores.
- `duplicates_removed` + `compiled_rules` surfaced in metrics + lists API;
  RULE_ENGINE.md documents the dedup behavior + first-list attribution.
- Gates green.

## Out of scope

Any other cache redesign; changing TTL clamps or serve-stale windows. For
dedup: changing lookup/verdict semantics; per-list post-dedup contribution
counts; "matched in N lists" attribution; any change to how raw lists are
cached on `/data`.
