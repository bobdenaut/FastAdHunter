> **TO BUILD in phase1.5 (liviu): `SO_REUSEPORT` — one socket per worker, one

## Goal

Remove the single-threaded UDP *ingest* funnel so datagram receipt scales
across all cores — **but only after measuring that it is actually the ceiling.**
Measure → decide → implement → re-measure.

## Context (what's true today)

Handling is already multi-worker: `crates/fah-dns/src/udp.rs` spawns a task per
datagram, so rule-match/cache/forward/reply spread across the 4 tokio workers
(`main.rs:164`, `new_multi_thread`, one worker per core). But **intake is
single-threaded**: one `recv_from` loop on one socket pulls packets serially and
does a `.to_vec()` + spawn before the next read. On-device the RB5009 held
**15–25% total CPU** under the `test_aleator.py` hammer — 25% ≈ *one core*,
consistent with either a single-recv-loop ceiling **or** forwards being
I/O-bound (upstream waits = near-free CPU). The code comment already anticipates
the fix: *"Every worker can be running one of these — no central dispatcher —
Phase 1 binds exactly one socket and spawns one receive loop."* The lever is
`SO_REUSEPORT`: N sockets, N recv loops, the **kernel** load-balancing datagrams
across cores.

**Honesty up front:** this raises the *stress ceiling*; real household traffic
never approaches it (the box loafs at ~20% under a synthetic assault). Worth
doing for the "performance is the primary feature" goal and to prove headroom
for Phase 2/3's heavier engines — not to fix a user-visible problem.

## Scope

1. **Measure first (gate the rest on this):** re-run `test_aleator.py` against
   the device (or the throughput bench with core pinning per the bench-noise
   note) and capture **per-core** CPU + QPS. If one core is ~100% while others
   idle → ingest-bound, proceed. If all cores share evenly with headroom →
   record that ingest is *not* the limiter and stop (don't add complexity for
   nothing). Write findings either way.
2. **If ingest-bound — implement `SO_REUSEPORT` multi-socket ingest** in
   `crates/fah-dns/src/{server.rs,udp.rs}`:
   - Bind `reuseport_count` sockets (default = worker/core count) with
     `SO_REUSEPORT` via `socket2`, each its own `recv_from` loop task. Must
     compose with the dual-stack `::` bind (753fffb) — each reuseport socket is
     itself dual-stack; keep the v4-mapped canonicalization.
   - Linux-only (`SO_REUSEPORT` is the musl-container target); on non-Linux dev
     (Windows) fall back to the single-socket path — `SO_REUSEPORT` semantics
     differ there, so don't pretend. Document and `#[cfg]`-gate.
   - Consider trimming the per-datagram `.to_vec()` (reuse a pooled/bounded
     buffer) only if the measurement says the copy matters — otherwise leave it
     (hard rule #4: any pool must be bounded).
3. **TCP** stays as-is unless the measurement flags it (TCP is the fallback
   path, far lower volume).
4. **Config:** `[dns.listen] reuseport_count` (boot-class), documented in
   CONFIGURATION.md with the "0/1 = single socket" meaning.
5. **Docs:** ARCHITECTURE.md §Runtime Model (make the intended multi-socket
   model concrete), PERFORMANCE.md (before/after QPS + per-core numbers).

## Acceptance criteria

- Measurement recorded (per-core CPU + QPS) that either justifies or cancels
  the implementation.
- If implemented: sustained QPS scales beyond the single-recv-loop ceiling with
  cores sharing load evenly; dual-stack + v4-mapped canonicalization still
  correct; single-socket fallback on non-Linux; no correctness change to any
  verdict/answer.
- No regression to blocked/cache p99 (<1 ms, PERFORMANCE.md).
- Gates green.

## Out of scope

Changing the pipeline, cache, or verdict logic; TCP redesign; io_uring (a
separate, much larger investigation — note it, don't do it here).
