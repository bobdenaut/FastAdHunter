# P2.5-10 — WS Endpoint Attribution

**Phase:** 2.5 · **Depends on:** p2.5-05, p2.5-09 · **Model:** Opus

## Goal

The per-query `endpoint` that p2.5-05 put on `QueryEvent` reaches the one
per-query surface a client can see: the `WS /api/v1/events` `query` message.

## Context

p2.5-09 F1: `endpoint` is set by `UpstreamPool::forward`, carried through
`Resolved` → `QueryEvent::with_outcome` → the event channel → `fah-api`'s
`QueryRecord` intact, and dropped in `From<QueryRecord> for QueryItemResponse`
(`crates/fah-api/src/wire.rs`), which never reads it. No other consumer reads
it. A wiring gap, not a design question — the field, its semantics
(CONTEXT.md §Answering Endpoint) and its serde rule already exist.

## Scope — strict

- `QueryItemResponse` gains `endpoint: Option<u8>`,
  `#[serde(skip_serializing_if = "Option::is_none")]`, filled from the DNS
  event's `endpoint` in the existing `From<QueryRecord>` impl. Absent on cache
  hits, blocks, HTTP events.
- One wire/API test: a forwarded query carrying `endpoint = 1` encodes to a WS
  `query` message whose `data.endpoint == 1`; a cache-hit event encodes with no
  `endpoint` key.
- API.md §`WS /api/v1/events`: document the key and the absent-means-no-upstream
  rule; drop the paragraph saying attribution is aggregate-only
  (owner-approved edit at execution time).

Nothing else: no `upstream` string, no `answer` key, no tui-monitor change
(no `deny_unknown_fields`), no refactor of `QueryItemResponse`.

## Acceptance criteria

- Test above green; gates green.
- Live check (read-only, dev box → RB5009 after the next deploy): one observed
  WS event on a forwarded query with `endpoint` set; one cache-hit event
  without it — this is p2.5-09 V5b, which stays FAIL until this task deploys.
- No hot-path cost: the field is already on the event; the copy is one `u8`.

## Out of scope

Per-query `answer` outcome on the feed; `upstream` address string; anything in
`fah-dns` or `fah-model`.
