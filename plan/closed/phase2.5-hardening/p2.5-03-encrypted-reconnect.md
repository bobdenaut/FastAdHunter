# P2.5-03 — Encrypted Transport Reconnect on Timeout

**Phase:** 2.5 · **Depends on:** — · **Model:** Opus

## Goal

A timed-out DoT/DoH exchange invalidates the pooled connection so the next
exchange establishes a fresh one — making the accepted spec's S1.15 row ("a
persistent v6 DoT/DoH connection reconnects, which is not a failure") true
in code.

## Context

Reconciled §3.2 / GAR-A risk 4a: `ExchangeConn::query`
(`crates/fah-dns/src/upstream/encrypted.rs:84-96`) keeps the pooled
connection on timeout ("the connection is likely fine and the upstream
slow") and reconnects only on non-timeout errors. An IPv6 prefix rotation
blackholes the stale source address, and a blackhole's failure shape *is*
timeout — so the dead connection is never replaced, every query pays the
full timeout forever, and Stage 1's recovery probes (S1.7) would reuse the
dead exchange and pin a healthy endpoint at maximum penalty.

**Decision** (session-settled: user-directed — single-timeout invalidation
chosen over an N-consecutive-timeouts threshold: the blackhole heals in one
timeout window, no counter state is needed, and the churn cost of a spurious
reconnect after a slow-but-alive answer is negligible at the measured
0.072 % failure rate and observable via the existing `tls_handshakes`
counter; the timed-out answer was going to be discarded anyway).

## Scope

- On `TimedOut` from an exchange (pooled or fresh), clear the connection
  slot before surfacing the error. Identity-check the slot under its lock —
  only clear it if it still holds the exchange that timed out, so a newer
  connection installed by a concurrent task is never dropped.
- Surface semantics unchanged: the timeout still returns `Err` to the pool
  within the one-extra-window budget (no retry-now); the reconnect happens
  on the next use.
- The reconnect itself is not an endpoint failure: nothing beyond the
  timeout that triggered it may move failure counters (preserves S1.15's
  "not a failure" and ADR-0005 interactions).
- The non-timeout reconnect path (idle-close) stays as is.

## Acceptance criteria

- Test: a blackholed pooled connection (send that never completes → timeout)
  causes the next query on that server to establish a fresh connection
  (handshake count increments) instead of reusing the slot.
- Test: concurrent queries racing a timeout do not drop a newer connection
  (identity check).
- Test: the timeout surfaces `Err` unchanged; fallback ordering and timing
  budget unaffected.
- Existing idle-close reconnect test still passes.
- Gates green.

## Out of scope

Error-kind mapping (p2.5-04); Stage 1 penalty/probe logic; connection
pooling redesign.
