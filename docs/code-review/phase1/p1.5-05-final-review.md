## 1. Correctness

### C1 — `dns.cache.max_bytes` is classified runtime but nothing applies it live

**Severity:** Medium
**Location:** `crates/fah-api/src/config_store.rs::BOOT_KEYS` (l.19) and
`apply_patch` (l.99–101); `crates/fah-dns/src/pipeline.rs::Pipeline::new`
(l.62); `crates/fastadhunter/src/main.rs:245`; `CONFIGURATION.md:50`

**Evidence.** `BOOT_KEYS` holds seven paths, none under `dns.cache`. Everything
not listed is runtime-mutable by construction, so a
`POST /api/v1/config {"dns":{"cache":{"max_bytes": …}}}` returns
`applied: true, restart_required: false`.

Nothing consumes that. `DnsCache::new` is called from exactly one place —
`Pipeline::new` — with `&config.dns.cache` captured once at boot
(`main.rs:245`). There is no `ArcSwap`, no config-store reference and no
`apply_*` port anywhere in `fah-dns` or `fastadhunter` that could re-read it.

This is not a blanket "no runtime key is live": `history.retention_days` *is*
wired, through `CacheSource`-style port `apply_history_config`
(`fah-api/src/ports.rs:39`, called at `routes.rs:939`) into an
`Arc<AtomicU32>` the pruner reloads (`fah-stats/src/history/perf.rs:96`). The
runtime/boot contract is real and enforced elsewhere, which is what makes the
new key's classification a violation rather than an aspiration.

Observable consequence: after such a POST, `GET /api/v1/config` reports the new
ceiling while `GET /api/v1/cache`'s `max_bytes` still reports the old one — two
endpoints disagreeing, with the API having said the change was applied.

`max_entries`, `min_ttl_seconds`, `serve_stale` and `dns.blocking.ttl_seconds`
carry the same defect and predate this task; `max_bytes` is a new key added
under the same wrong label. The cheap correct fix is classification
(`dns.cache` into `BOOT_KEYS`, `# boot` in CONFIGURATION.md), not new swap
machinery.

#### Resolution — FIXED (boot-only, all mislabeled keys)

A full audit of every `# runtime` label found 3 of ~20 honest, plus one inverse
mismatch (`history.sample_interval_seconds`, documented boot, classified
runtime). `BOOT_KEYS` now lists whole sections — `dns.listen`, `dns.blocking`,
`dns.cache`, `dns.upstreams`, `query_log`, `stats`, `log.level`,
`history.sample_interval_seconds` — so a field added to one of them is boot
until someone wires it live. The runtime set is now exactly the four keys with
a real live consumer: `history.enabled`, `history.retention_days`,
`api.metrics_public`, `rules.refresh_hours_default`.

`boot_key_classification_matches_configuration_md` was itself part of the
problem — it asserted `dns.cache.max_entries` was runtime *because the doc said
so*, and passed while the API lied. Replaced by
`boot_key_classification_matches_what_actually_applies_the_key`, whose runtime
list is exhaustive and names each key's live consumer, so adding to it requires
wiring one first. `a_runtime_key_applies_live_without_requiring_a_restart` and
`a_mixed_patch_reports_both_flags` were rebuilt on genuinely-live keys (they
were demonstrating the contract with `dns.cache.max_entries`), and
`a_cache_config_change_persists_and_asks_for_a_restart` pins the new behavior at
the HTTP level.

Docs: CONFIGURATION.md's class table now states the rule — runtime means
something re-reads it after the patch — and points at `POST /cache/clean` as
the restart-free way to release cache memory. API.md and `requests/settings.http`
updated to match.

**Known gap, deliberately not closed here:** `POST /api/v1/config` with a
`rules.lists` array persists to the file and reports `applied: true`, but does
not reload `ListManager`. The dedicated `/lists` endpoints *do* keep both in
step (`persist_lists` + `state.rules.remove_list`), which is why the key stays
runtime — but the `POST /config` path for it is the same class of defect as C1
and wants either a reload hook or its own classification.

## 2. Reliability

Nothing found. Specifically checked and clean:

- The `while guard.over_bounds() && guard.map.len() > 1` loop terminates in
  every reachable state — `evict_oldest` always removes one entry while the map
  is non-empty, including the degenerate all-ghosts queue (the fallback at
  `cache.rs:278` pops an arbitrary key rather than growing).
- Byte accounting cannot drift: entries leave through `Shard::remove` or
  `clean`'s `retain`, both of which subtract, and the refresh path subtracts the
  replaced entry via `map.insert`'s return value. `saturating_sub` on all three
  paths means a broken invariant fails soft instead of wrapping `bytes` to
  `~u64::MAX` and pinning `over_bounds()` true forever.
- Dedup index and side maps stay in lock-step: `add_rule` sets `FLAG_DNSTYPE` /
  `FLAG_REWRITE` under the same condition that inserts the side-map entry at
  `rec_idx`, so `identity_matches`' `self.dnstype[&idx]` indexing cannot panic.
- No off-by-one in the transient index sizing. `with_capacity(e)` allocates
  `2e` slots; `reserve_dedup` grows when `records + 1 > e`, and `records ≤ e`
  because `rule_upper_bound` is a true ceiling — so the "one allocation, one
  free" property the plan mandated actually holds, including the boundary case
  where every token becomes a rule.
- `dedup_slot_for` returns a slot that is still valid when `add_rule` writes to
  it: nothing between the probe and the write resizes `dedup`.

## 3 & 4. Performance / Memory

### M1 — the eviction queue is bounded by `max_entries`, not by `max_bytes`

**Severity:** Low as deployed (Medium only if `max_entries` is raised)
**Location:** `crates/fah-dns/src/cache.rs::Shard::compact` (l.308–314),
`DnsCache::insert` (l.463, l.484), `Shard::over_bounds` (l.301)
**Disposition:** deferred past p1.5-07, gated on a bench — see below

**Evidence.** `compact()` sweeps ghost nodes only when
`queue.len() > self.capacity * 2`, and `capacity` is `max_entries / 16`
(l.337) — the *configured entry* bound. It is never derived from the resident
entry count or from the byte bound. `over_bounds()` compares only
`self.bytes` (the `entry_heap_bytes` sum) against `byte_capacity`;
`queue_bytes` (l.226) is reported inside `estimated_bytes` and never enforced.

Every `insert` pushes exactly one node (l.463), including a *refresh* of an
existing key — which leaves `map.len()` unchanged and, for an equal-sized
answer, leaves `bytes` unchanged, so `over_bounds()` stays false, no node is
popped, and the queue grows by one ghost. This is not speculative: the module's
own test `refresh_churn_keeps_the_eviction_queue_bounded` (l.1065) hammers one
key 100 times with one live entry and asserts the queue is allowed to reach
`2 × capacity + 1`. Real DNS traffic re-resolves popular domains on TTL expiry,
so this is the steady-state shape, not a corner case.

Before this task the two were proportionate — the queue was ≤ 2× the only
bound. The byte cap decouples them, and nothing re-couples the queue:

| `max_entries` | resident entries under the 64 MiB cap | queue ceiling | queue memory |
|---|---|---|---|
| 10 000 (default) | ~10 000 (entry cap binds first) | 20 000 nodes | ~1.3 MB |
| 200 000 | ~150 000 | 400 000 nodes | ~26 MB |
| 1 000 000 | ~150 000 | 2 000 000 nodes | ~128 MB |

Node cost: `size_of::<(CacheKey, u64)>()` ≈ 32 B (`Box<str>` 16 + `RecordType`
+ `DNSClass` + `u64`) plus a *separate* heap copy of the domain,
`alloc_rounded(len)` ≈ 32 B. Resident-entry estimate uses ~448 B/entry — the
value `entry_heap_bytes` produces for a one-record answer given
`size_of::<hickory::Record>()` ≈ 280 B (`Name` ≈ 80 B, `RData` ≥ 184 B because
`RData::SOA` carries two `Name`s).

At `max_entries = 1_000_000` the ghost queue alone can exceed the byte cap it
sits beside and blow the whole 128 MB budget, while `GET /api/v1/cache`'s
`bytes` reads comfortably under `max_bytes`. CONFIGURATION.md meanwhile states
*"Raising `max_entries` 'to 100k+ if RAM allows' is safe precisely because
`max_bytes` still holds the ceiling"* — which is exactly the claim that fails.
The doc does say the queue slab "scales with `max_entries`", so the fact is
disclosed; the safety conclusion drawn two paragraphs earlier is not consistent
with it.

The compaction threshold is the whole fix surface — it is the only thing tying
queue length to `max_entries` rather than to what is actually resident.
`self.capacity * 2` → `self.map.len() * 2` is provably the same bound except
when the byte cap binds: the eviction loop exits either with
`map.len() <= capacity` or with `map.len() == 1`, so `map.len() <= capacity`
always holds at the `compact()` call site. Strictly tighter, never looser; the
existing `refresh_churn_keeps_the_eviction_queue_bounded` assertion still
passes.

**Why it is deferred.** There is no config file in the repo, so the RB5009 runs
the compiled default `max_entries = 10_000`: 625/shard, a 1250-node compaction
threshold, **~1.3 MB** of queue. The over-provisioning factor is
`max_entries / resident`, so at the deployed sizing the defect is worth nothing
— it only becomes real at the 100k–1M sizings CONFIGURATION.md invites. Against
that, `compact` runs `retain` with a `HashMap` lookup per node *inside the shard
lock on the store path*; a tighter threshold fires it ~2× more often over
proportionally smaller queues (~1.1 → ~2 amortized node-visits per insert).
Changing a measured-good hot-path component for an unmeasured one, to reclaim
~1 MB, is not a trade worth making without a pinned cache bench showing no
regression. Revisit after p1.5-07, bench first.

**The soak measures it already.** p1.5-02's sampler writes `bytes` and
`estimated_bytes` every 60 s; their difference *is* the slab + queue residue the
byte cap does not govern, sampled against RSS in the same row. The p1.5-07 run
therefore produces the evidence for both M1 and M2 with no added
instrumentation — if the gap stays flat and small over the soak, neither needs
code.

### M2 — the enforced figure excludes the per-entry table slab

**Severity:** Low
**Location:** `cache.rs::entry_heap_bytes` (l.202–210), `table_bytes`
(l.218–221), `over_bounds` (l.302)

**Evidence.** `entry_heap_bytes` deliberately excludes the inline
`(CacheKey, Entry)` pair — its doc comment says so — and `table_bytes` prices
that pair at `buckets × (size_of::<(CacheKey, Entry)>() + 1)` with
`buckets = capacity × 8/7`. Only `bytes` is compared against `byte_capacity`,
so the slab is uncapped. Per entry that is ≈ (24 + 48 + 1) × 8/7 ≈ 84 B of
untracked memory against ~448 B tracked — the cache's real footprint runs
~15–20 % above whatever `max_bytes` is set to (≈ 76 MiB at the 64 MiB default).

Disclosed in CONFIGURATION.md, but the default was chosen as "half of
PERFORMANCE.md's 128 MB steady-state budget"
(`fah-config/src/schema/dns/cache.rs:46`) against the smaller of the two
numbers. The `size_of` values above are read off the struct definitions, not
measured — p1.5-07's on-device run is the place to confirm the multiplier.

### M3 — CONFIGURATION.md understates the near-floor overshoot by ~10×

**Severity:** Low
**Location:** `CONFIGURATION.md` ("`bytes` can sit a couple of MB over the cap")

**Evidence.** The doc's own formula is right:
`16 × max(per-shard share, one largest answer)`. The magnitude is not. A
maximum-size TCP answer (~5 400 records in 64 KiB with compression) costs
`alloc_rounded(5400 × 280) + 5400 × 48` ≈ **1.8 MB** of `entry_heap_bytes` for
a single entry. At the validated 1 MiB floor the per-shard share is 64 KiB, so
the `map.len() > 1` guard leaves one such answer resident per shard: ~28 MB,
not "a couple of MB". Same class as M2, and it only bites a config the doc
already advises against — but the stated bound is the one an operator would
plan RAM against.

## 5. Security

The `MAX_PREALLOC_RULES` clamp is sound and the counting-allocator test
(`crates/fah-rules/tests/dedup_alloc_bound.rs`) is a genuine red/green for it.
One qualification:

### S1 — the clamp bounds the smaller of two allocations on the same path

**Severity:** Low (pre-existing, not a p1.5-05 regression)
**Location:** `crates/fah-rules/src/lifecycle/mod.rs::compile()` — the `texts`
vector

**Evidence.** `compile()` accumulates *every* enabled list's full raw text into
`Vec<(Arc<str>, String)>` before `spawn_blocking`, each capped at
`MAX_LIST_BYTES` = 64 MiB. The clamp's stated threat model is "a 64 MiB list …
a few such lists abort the process at `handle_alloc_error` on the 1 GB
RB5009" — but N such lists put N × 64 MiB in `texts` first, and the parsed
rules land on top of that. The peak the clamp removes (256 MiB → 30.5 MiB) is
real, and it is not the first allocation to fail under that scenario. Identical
at `bff9d5a`, so this is context for the clamp's value, not a defect introduced
here.
