## 2. Metrics cache-outcome fix (`0401af0`) — the reason for this deploy

Under 0.2.3, `Metrics::record` counted a blocked query as a cache **miss**. A
blocked query never reaches the cache (ADR-0001), so it carries
`cache_hit == false` by construction; the counter therefore overstated
`cache_misses_total` by exactly the block count and understated the hit rate the
harder the blocker worked.

Counters were zero at 11:01:58, so there is no pre-existing skew to explain
away. Reading at a later point under real household traffic:

```text
queries_total{pass}=485  {allow}=3  {block}=411
cache_hits_total=299     cache_misses_total=189
```

Three independent confirmations, all exact:

1. **The identity itself** — `hits + misses = 488 = pass + allow`. Blocks are
   excluded, as intended.
2. **The stage histogram** — `count{stage="cache_hit"} = 299 == hits`,
   `count{stage="forward"} = 189 == misses`, `count{stage="block"} = 411`. The
   histogram always tested `Block` first and so was never wrong; under 0.2.3 it
   disagreed with `cache_misses_total` by precisely the block count.
3. **The cache port's own counters** — `GET /api/v1/cache` reports
   `hits=299 misses=189`, total 488, **delta 0** against `pass + allow`.
   `DnsCache::note_lookup` and `Metrics::record` are separate code paths
   counting the same event, and they now agree to the query.

Under 0.2.3 the same traffic would have reported `misses = 600` and broken all
three relations. Scope of the old bug was `/metrics` only — the admin API and
persisted history always read correct counters.

## Findings

### F1 — `fastadhunter_ruleset_compile_duration_seconds` is structurally always 0

**Severity:** low (observability, not correctness)
**Location:** [crates/fastadhunter/src/main.rs:416](../../../crates/fastadhunter/src/main.rs#L416)

`compile_duration: std::time::Duration::ZERO` is hardcoded at the only
production call site, so the exported series can never read anything but `0`.
The encode path is correct and tested (`encode.rs:242` uses `as_secs_f64()`,
covered by a 1.5 s assertion), and the code comment states the reason honestly:
the lifecycle does not report compile timing, and since this poll overwrites the
whole snapshot every 10 s, wiring it here would be erased — it needs its own
setter driven by compile events.

**Evidence:** live scrape reads `fastadhunter_ruleset_compile_duration_seconds 0`
while the startup log shows a ~2.3 s compile (11:01:58.7 → 11:02:01.08).
Pre-existing since `4d72fd2` (phase 1), **not** a 0.2.4 regression.

The defect is not the placeholder, it is **exporting** it. A Prometheus consumer
cannot distinguish "not implemented" from "compiles instantly", and nothing in
API.md says so. Either suppress the series until it has a real setter, or
document it as reserved.

### F2 — a pending restart is not observable after the fact

**Severity:** low (contract usability)
**Location:** `GET /api/v1/config` vs `POST /api/v1/config` response

`restart_required: true` is returned once, in the POST response, and stored
nowhere. `GET /config` then reports the **persisted** boot value as though it
were effective: after patching `log.level` to `debug`, `GET` read `"debug"`
while the running tracing filter was still `info`. This is the documented
contract ("the file always reflects the running intent"), but it means an
operator who patches a boot key and loses the response has no way to learn that
the file and the process disagree.

Worth a `restart_required` (or `pending_boot_keys`) field on `GET /config`
before the dashboard phase, since the dashboard will render effective config and
would present persisted-but-inactive values as live.

## Notes carried forward (not defects)

- **`timeout_ms = 800` is an explicit TOML value**, so 0.2.3 already ran with
  it. The compiled-in default change in this build only affects a fresh
  `/config` volume; the on-device reading does not exercise it.
- **`metrics_public = false`** on this deployment, so any Prometheus scraper
  needs `Authorization: Bearer <key>` configured. `/metrics` was reachable in
  every test above only because the key was supplied.
- **No liveness watchdog is deployed.** `/system/scheduler/print` is empty, so
  deploy-doc §7 was never applied. Phase 1's "no watchdog restarts" criterion
  was satisfied by the watchdog's absence — which is the stronger form of the
  evidence, since nothing could mask a crash by restarting the process, and
  0.2.3 held 56,183 s (15 h 36 m) of unbroken uptime. It does mean an unnoticed
  panic costs LAN-wide DNS until a human notices.
- **The byte cap's eviction path is still unexercised on-device.** At the time of
  reading: `entries 152/50000`, `bytes 156,000/67,108,864`, `evictions 0`. The
  entry cap has bound first on every previous fill too. Proving p1.5-05's
  headline criterion on hardware needs the large-answer profile or a temporarily
  lowered `max_bytes`; unit tests cover the logic today.
- `events_dropped_total = 0` throughout — the QueryEvent channel never
  backpressured.

## Deploy-doc corrections made alongside this verification

[docs/deploy-rb5009.md](../../deploy-rb5009.md), 4 fixes, all driven by readings
from this box:

1. **§4** — `comment="fastadhunter 0.2.3"` → `comment="fastadhunter"`. RouterOS
   `=` is exact equality, so a version inside the comment makes every
   `[find comment="fastadhunter"]` in §4, §7 and §8 match nothing and fail
   *silently* — the start, the watchdog's stop/start pair and the rollback all
   become no-ops. The live container's comment is the plain form (as is
   `p1-11-review.md:148`), so §4 was the outlier. Version lives in `name=` and
   `repo=`, which RouterOS derives on its own.
2. **§5** — the redeploy sequence's two bracketing steps are now marked
   conditional, with the `print` commands to check first. Both of its
   assumptions were false here: no scheduler exists, and the old resolver
   (`adguardhome`, `pihole`) is `status=stopped`, which makes the `dns-adguard`
   flip aim the redirect *and* `/ip/dns` at a dead address — worse than skipping
   it.
3. **§5 IPv6** — removed the claim that FastAdHunter binds `0.0.0.0` and "does
   not accept IPv6"; it binds `::` since `753fffb`. The section's real point is
   preserved and restated correctly: the *listener* is dual-stack, the
   *steering* (DHCP + `dstnat`) is IPv4-only.
4. **§1** — added the layout trap hit while building this image: buildx emits an
   OCI archive that *also* carries `manifest.json` for `docker load`
   compatibility, so the doc's own "not optional" layout check can read as
   legacy when it is not. Judge by `manifest.json`'s `Layers` paths —
   `blobs/sha256/…` means convert with skopeo.
