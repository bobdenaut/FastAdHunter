# p1.5-05 — Byte-aware cache cap + rule deduplication: implementation review

**Task:** [plan/closed/phase1.5/p1.5-05-cache-byte-cap.md](../../../plan/closed/phase1.5/p1.5-05-cache-byte-cap.md)
· **Status:** DONE, gates GREEN · **Commit:** deferred (phase1.5 commits as one
batch).

Two independent memory-hardening deliverables, both closing findings recorded
during phase 1: the DNS cache was bounded by entry count but not by bytes, and
the compiled matcher stored overlapping lists' rules twice.

---

## A — Byte-aware cache cap

### What was built (A)

**`fah-config`** — `[dns.cache] max_bytes`, default **64 MiB**: half of
PERFORMANCE.md's 128 MB steady-state budget, which leaves the ≤40 MB compiled
ruleset and the process base underneath the ceiling even with the cache
completely full. Validated with a 1 MiB floor (below that a shard could not
hold a single maximum-size DNS answer, so every insert would evict what it just
stored). Env override `FAH__DNS__CACHE__MAX_BYTES` via a new `coerce_u64`.

**`fah-dns/cache.rs`** — each shard carries `byte_capacity` (its slice of
`max_bytes`) and `bytes`, a running sum of `entry_heap_bytes` maintained on
every insert, eviction and clean. Eviction now runs *after* the insert, from
the same FIFO head, until **both** bounds hold:

```rust
while guard.over_bounds() && guard.map.len() > 1 {
    guard.evict_oldest();
    self.evictions.fetch_add(1, Ordering::Relaxed);
}
```

Three details worth naming:

- **`map.len() > 1` guards the insert against itself.** An answer larger than a
  whole shard's byte budget is kept alone rather than evicting itself, so the
  degenerate case is "one entry per shard", never a cache that thrashes on
  every store. Tested.
- **Insert-then-evict replaced check-then-insert**, which also removed a
  `contains_key` probe from the store path. Equivalent ordering: the new entry
  sits at the queue's back, so FIFO reaches it last.
- **A refresh subtracts the replaced answer's bytes** (`map.insert` returns the
  old value), so re-caching a domain whose answer shrank releases the
  difference instead of leaking accounting.

The estimator was *reused*, not duplicated: `stats()` no longer re-walks the
map summing `entry_heap_bytes`; it reads the tracked total. One number is both
enforced and reported, so the two cannot drift — asserted by a test that
compares the running total against a full walk after churn.

**Surface** — `CacheStats` gained `bytes` + `max_bytes` through
`fah-dns` → adapter → `fah-api` port → wire, exposed on `GET /api/v1/cache` as
`bytes`, `max_bytes` and `byte_load_percent` alongside the existing
`load_percent`. `fah_model::CacheStatsSample` gained the same pair (both
`#[serde(default)]`) so p1.5-02's sampler graphs the byte ceiling over time and
rows written before this task still deserialize.

### Scope decision (A)

`estimated_bytes` (slab-inclusive, `/debug/memory`) is deliberately **not** what
the cap governs. The hash-table and eviction-queue slabs scale with
`max_entries`, not with answer size, and they cannot be shrunk by evicting;
capping the entries' own heap is what actually contains the adversarial case.
Both figures are documented where they are served.

### Measurements (A)

Cache-hit in-engine latency, pinned to one core, A/B against a pre-change
worktree: **2.48 µs** vs **2.56 µs** baseline — intervals overlap, no
regression. The cap only touches the insert path.

Sustained throughput (four cores, per PERFORMANCE.md §Measuring reliably), with
the cap active: **~567 000 elem/s** (median of 3 pinned runs, range
560.7–574.8 K) — the figure deferred from p1-11, now recorded in
PERFORMANCE.md.

## B — Rule deduplication

### What was built (B)

`MatcherBuilder::add_rule` drops a rule whose **full identity** — domain
(case-insensitive), action, subdomain flag, `$dnstype` raw, `$dnsrewrite` raw —
is already compiled, and returns *before* appending anything, so a duplicate's
arena bytes, record and slot are never allocated.

The index is a transient open-addressing `Vec<u32>` of record indices keyed by
an identity hash, dropped with the builder at `build()`. The arena stays the
single source of truth: the hash only picks the probe start, and every
accept/reject is a real byte-and-field comparison against arena + flags + side
maps, so **a hash collision can never silently drop a distinct rule**.

`MatcherBuilder::with_capacity(n)` sizes the index once for the whole compile.
`ListManager::compile` derives `n` from a new `parser::rule_upper_bound(text)` —
a ceiling computed in one pass over the raw text without parsing it. It counts
whitespace-separated tokens on content lines because the **hosts parser emits
one rule per host token**, so a line count would *not* be an upper bound; that
property is asserted against the real parsers in a test.

`duplicates_removed` is carried onto `Matcher`, read by the telemetry poll into
`RulesetSnapshot`, exposed as `fastadhunter_ruleset_duplicates_removed`, added
to the `GET /api/v1/lists` envelope next to `compiled_rules`, and logged at
`INFO` on compile. Per-list `rules_*` counts stay parse-based — each list really
does contain those rules; the envelope describes the merge.

### Determinism

The index is membership-only and never iterated to produce output; records,
arena and slots come from processing rules in a fixed order (enabled lists, then
user rules), so first-seen-wins decides survivors, not probe order. The test
compiles the same lists at capacities `0`, `1`, `n`, `100_000` and unhinted, and
asserts a byte-identical fingerprint (arena, records in order, slot count) every
time — proving capacity is inert to the output.

### The performance argument (measured, not asserted)

This is the part that took the most work, and the first two attempts were wrong.

**Cost.** On 1M *unique* rules — the worst case for dedup, all cost and no
benefit — the build phase went 41.6 ms → 135.7 ms at first. A/B'd against a
pre-change worktree on the same box with the same core pinning, not against
criterion's stored baseline, which interleaved runs had polluted.

Two tuning attempts, both measured:

| dedup index | build (1M unique) | verdict |
|---|---|---|
| `Vec<u32>`, 0.7 load | 135.7 ms | first cut |
| `Vec<u32>`, **0.5 load** | **93.3 ms** | **kept** |
| `Vec<(u32, u32)>` tagged, 0.7 load | 124.0 ms | **rejected** |

The tagged slot was meant to reject collisions without touching the arena; it
lost, because the load factor — not the compare — was the dominant term, and
doubling the slot halved the slots per cache line. Rejecting it is recorded in
`matcher.rs` so nobody re-tries it blind. What remains (~52 ms, ~52 ns/rule) is
essentially one random memory access per rule against the index, which is the
floor for membership-testing 1M rules.

**Saving.** Two 1M-rule lists compiled together, by overlap — ~30 bytes per
duplicate removed:

| overlap | duplicates | compiled | saved | build |
|---|---|---|---|---|
| 0% | 0 | 57.7 MiB | — | 493 ms |
| 25% | 250 000 | 50.4 MiB | 7.6 MiB | 469 ms |
| 50% | 500 000 | 43.0 MiB | 15.2 MiB | 454 ms |
| 90% | 900 000 | 31.3 MiB | 27.3 MiB | 430 ms |
| 100% | 1 000 000 | 28.3 MiB | 30.3 MiB | 437 ms |

The 0% row is the argument: two non-overlapping 1M lists compile to 57.7 MiB,
**past the 40 MB budget**. And build time *falls* as overlap rises — a
duplicate's bytes are never appended, so dedup increasingly pays for itself.

**The lookup win — what the memory figure hides.** Collapsing duplicates shrinks
the slot table, so probe chains shorten. A new `overlap_lookup` bench, written
against the pre-dedup builder API so the identical file runs in both checkouts,
on two 500k lists sharing 250k domains:

| lookup | before | after | |
|---|---|---|---|
| hit, domain carried by **both** lists | 154.4 ns | ~83 ns | **−46%** |
| hit, domain in one list | 57.2 ns | 44.5 ns | −22% |
| miss | 63.1 ns | 57.1 ns | −10% |
| compiled | 28.2 MiB | 21.2 MiB | −7.0 MiB |

"After" is the median of 3 pinned runs (shared-hit ranged 79.8–85.5 ns across
runs; a single earlier run read 75.2 ns and was optimistic). A domain both lists
carried used to occupy two slots hashing to the same place, and every query
walked both. So dedup is a **hot-path improvement**, not only a memory one. Hard
rule #3 is intact — `lookup` itself is byte-for-byte unchanged; it simply has
less to walk.

`matcher_lookup` on the 1M-unique corpus (where dedup collapses nothing) is
unchanged-to-slightly-better: 99.7 ns / 345.4 ns / 63.6 ns for
exact / subdomain / miss.

## Deviations from the plan, and why

1. **Dedup index is ~8 MB at 1M rules, not the planned ~5.7 MB.** The plan's
   figure assumed a 0.7 load factor. Measurement showed 0.7 costs 42 ms more
   compile time than 0.5 on a 1M-rule build; 2.3 MB of transient memory, freed
   at `build()`, buys that back. Steady-state RSS is unaffected either way.
2. **`MatcherBuilder::new()` keeps a growable index.** The plan mandates one
   allocation with no realloc churn; that holds for the compile path, which uses
   `with_capacity`. `new()` is used by tests, benches and small ad-hoc builds
   where a fixed ceiling is unknowable, and it rehashes geometrically. The
   determinism test covers the grown path explicitly.

## Known risk (flagged, not hidden)

Projected RB5009 startup rises from the measured 2 440 ms toward **~3.0 s**
against the "< 3 s hard" budget, on the *worst-case* assumption of a
zero-overlap 1.2M-rule corpus. The real corpus is the overlapping one this
feature exists for, where build time falls rather than rises — but the
projection is a dev-box extrapolation either way. **This must be measured
on-device in p1.5-07**; PERFORMANCE.md already names chunked parallel parsing as
the next lever if it breaches.

# Adversarial gatekeeper review (independent second pass)

**Verdict: production-safe on correctness. One robustness finding (adversarial
list input) to address or explicitly accept before shipping.**

This pass traced the invariants rather than trusting the implementation notes
above, aggressively trying to prove the code incorrect. It could **not**
construct any scenario that makes the byte accounting drift, the dedup collapse
a distinct rule, a hash collision drop a rule, eviction thrash unbounded, or the
compiled output become non-deterministic. Those cores are solid (evidence
below). The only surviving concern is a memory-amplification path reachable
through hostile *list content*, not traffic.

## Major

### M1 — `with_capacity` sizes the dedup index from a pre-parse token count, so adversarial list content can force a multi-hundred-MB up-front allocation → possible process abort

**Why it's a bug.** `compile()`
([lifecycle/mod.rs](../../../crates/fah-rules/src/lifecycle/mod.rs#L668-L672))
sizes the transient dedup index *before parsing*:

```rust
let upper_bound: usize = texts.iter().map(|(_, t)| rule_upper_bound(t)).sum();
let mut builder = MatcherBuilder::with_capacity(upper_bound);
```

`with_capacity` then allocates `dedup_slots(upper_bound) = upper_bound * 2` ×
4 bytes = **`upper_bound * 8` bytes, unconditionally, in one `vec![EMPTY; …]`**
([matcher.rs:277-282](../../../crates/fah-rules/src/matcher.rs#L277-L282)).
`rule_upper_bound` is *token count on non-comment lines*
([parser/mod.rs:30-41](../../../crates/fah-rules/src/parser/mod.rs#L30-L41)) — a
correct ceiling, but a very loose one for pathological content.

**How it happens.** `MAX_LIST_BYTES = 64 MiB` per list. A 64 MiB body of
single-char space-separated tokens (`a a a a …`) is ~33.5M tokens →
`with_capacity(33.5M)` → **~268 MB single allocation** — even though, detected
as a plain-domain or adblock list, every multi-token line is a *parse error*
producing **zero** records. `compile()` sums `upper_bound` across all lists, so
a few such lists (or one 64 MiB list ×4) exceed the RB5009's 1 GB. `vec!` on
allocation failure calls `handle_alloc_error`, which **aborts the process** — it
is *not* caught by the `.expect("ruleset compile task panicked")` wrapper. On a
router where FastAdHunter *is* the LAN's DNS, that is a resolver outage.

**Why it's new to p1.5-05.** Before this task, compile memory was sized from
*actual parsed rules* (arena/records/slots), so garbage content → parse errors →
~0 bytes. The dedup index is the first structure sized from a pre-parse token
count, which is where the amplification enters. Hard rule #4 ("bounded
everything") is met only weakly: the bound is `MAX_LIST_BYTES × N_lists`, which
on a 1 GB box exceeds RAM.

**Production impact.** Availability DoS via a compromised/hostile list source
(list URLs are third-party). No data corruption.

**Likelihood.** Low with well-behaved lists; the amplification only bites on
crafted content — but list bodies are the least-trusted input in the system, and
this is squarely the "adversarial/corrupted input" class.

**Smallest correct fix.** Clamp the up-front allocation; `reserve_dedup` already
grows the index correctly if a (realistically impossible) corpus exceeds the
clamp, and determinism is proven capacity-inert, so nothing observable changes:

```rust
pub fn with_capacity(expected_rules: usize) -> Self {
    // A pre-parse token count can be adversarially inflated (64 MiB of
    // 1-char tokens → tens of millions of "rules" that parse to nothing).
    // Cap the transient so it can't force a multi-hundred-MB alloc before
    // parsing discovers there's nothing there; reserve_dedup grows it for
    // the (unreachable on a 1 GB box) case of >4M genuine rules.
    const MAX_PREALLOC_RULES: usize = 4_000_000;
    Self {
        dedup: vec![EMPTY; dedup_slots(expected_rules.min(MAX_PREALLOC_RULES))],
        ..Self::default()
    }
}
```

(4M rules already implies a ~200 MB compiled matcher, past budget, so the clamp
never bites a legitimate corpus.) A stricter alternative is lowering
`MAX_LIST_BYTES`, a separate policy call.

## Minor

### m1 — The byte cap is a soft ceiling: it can be exceeded by up to one max-size answer per shard

`over_bounds()` evicts only while `map.len() > 1`
([cache.rs:476](../../../crates/fah-dns/src/cache.rs#L476)), so a single answer
whose `entry_heap_bytes` exceeds a shard's `byte_capacity` is kept alone.
Resident bytes are bounded by `16 × max(byte_capacity, one_max_answer)`, not by
`max_bytes`. At the **default** 64 MiB (`byte_capacity` = 4 MiB/shard) no real
answer approaches that, so `bytes ≤ max_bytes` strictly. At the **1 MiB floor**
(`byte_capacity` = 64 KiB) a 64 KB TCP answer (~128 KB heap) exceeds it, so total
can reach ~2 MB against a 1 MiB cap. Bounded and tiny in absolute terms (well
inside the 128 MB RSS budget), and the "kept alone" behavior is deliberate and
tested — but "byte usage plateaus at the configured cap" is only exactly true
when no single answer exceeds a shard's share. Worth one sentence in
CONFIGURATION.md by the floor. No code fix needed.

### m2 — Refresh path uses non-saturating `-=` where remove/clean use `saturating_sub`

[cache.rs:468](../../../crates/fah-dns/src/cache.rs#L468):
`guard.bytes -= entry_heap_bytes(key, &previous);`. Safe **today** — the
accounting invariant (`guard.bytes` = Σ resident bytes) guarantees `previous`'s
bytes are included, enforced by the `tracked == walked` test. But `remove()`
([cache.rs:290](../../../crates/fah-dns/src/cache.rs#L290)) and `clean()`
([cache.rs:589](../../../crates/fah-dns/src/cache.rs#L589)) both use
`saturating_sub` defensively and this path doesn't. If a future change broke the
invariant, a release-build underflow here wraps `bytes` to ~`u64::MAX`, making
`over_bounds()` permanently true and silently evicting every shard down to one
entry for the process lifetime — a catastrophic-vs-graceful asymmetry. Make it
`saturating_sub` for consistency and fail-soft. No impact now; defense-in-depth.

### m3 — Load factor differs between the hinted and grown dedup paths

`with_capacity` builds at 0.5 load (`dedup_slots = entries*2`); `reserve_dedup`
grows to `dedup_slots(needed*2)`, oscillating 0.25→0.5
([matcher.rs:428](../../../crates/fah-rules/src/matcher.rs#L428)). Not a bug — both
keep load ≤ 0.5 so probing terminates, and the grown path is only `new()`
(tests/API ad-hoc). Flagging only that the two paths don't share a load target.
No action required.

## Nitpick

### n1 — `identity_matches` reads side maps by panicking index, guarded only by the flag bit

[matcher.rs:407,410](../../../crates/fah-rules/src/matcher.rs#L407-L410) use
`self.dnstype[&idx]` / `self.rewrite[&idx]`. Safe because every
`FLAG_DNSTYPE`/`FLAG_REWRITE` record has a map entry (insert precedes push) and
the `has_dnstype()`/`has_rewrite()` guards gate the access — verified on every
path including the rehash. The safety rests entirely on the flag↔map coupling;
worth a `debug_assert` if you want it enforced rather than argued.

## Verified correct (so the silence is credible)

- **Byte accounting is exact — no drift, no underflow.** Symmetric add/subtract
  over immutable fields; the refresh subtract can't underflow because
  `map.insert` returning `Some` implies key equality → same domain length → the
  replaced entry's bytes are in the running total. The `tracked == walked` test
  nails it.
- **Eviction is bounded and never evicts its own insert.** The just-stored key
  sits at the queue back, reached only when `map.len() == 1` (loop stops first).
  Queue stays ≤ `2×capacity+1` via `compact`; `clean` never adds queue nodes.
- **Dedup cannot drop a distinct rule.** Identity covers every `DomainRule`
  field; the hash only accelerates the probe, accept/reject is a real
  arena+flags+side-map compare. Raw-value comparison can only cause dedup false
  *negatives* (both kept = safe), never false positives.
- **Lookup is provably unchanged by dedup.** Collapsed duplicates had identical
  domain+flags+options, and pre-dedup lookup already returned the lowest-index
  record for a domain (= the survivor), so verdict *and* attribution are
  byte-identical with or without dedup.
- **Determinism holds across capacities and restarts.** Output comes from the
  ordered records/arena, never from HashMap/dedup-table iteration; `hash_domain`
  is fixed FNV (not `RandomState`); first-seen-wins is insertion-order.
- **`rule_upper_bound` is a genuine upper bound** for all three parsers (hosts ≤
  tokens−1 rules/line; plain-domain and adblock exactly one push/line;
  comment/`!`/`[` lines emit no active records) — so M1 is an alloc-*size* issue,
  not a correctness one.
- **No integer overflow reachable:** `saturating_mul` in slot sizing, `fastrange`
  in u128, u64 counters need ~10⁷ years to wrap at 15k QPS.
- **Config plumbing sound:** 1 MiB floor validated, `coerce_u64` wired,
  `percent_of` guards div-by-zero and uses f64, `#[serde(default)]` lets
  pre-p1.5-05 history rows read back as 0.

**Gate recommendation:** correctness-critical logic is production-safe. Gate on
**M1** (apply the clamp, or explicitly accept the adversarial-list allocation
risk given the trust model for list sources); fold in **m2** while in the file.
Everything else is documentation or defense-in-depth.
