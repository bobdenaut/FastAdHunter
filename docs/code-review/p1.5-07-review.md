## Cross-cutting e2e (new) — `crates/fastadhunter/tests/history_e2e.rs`

The per-crate tests own the arithmetic; nothing before this proved the whole
**write → `/data` → read → HTTP** chain with the *real* `fah-stats` behind the
*real* `fah-api` server. This assembles `Stats` behind `ApiServer` in-process

test's lifetime).

**`history_is_written_to_disk_and_served_over_http`**

- Records three queries in the 10:00 hour of 2023-09-25 (a block, a cache-hit
  pass, an AAAA pass) plus a second block at 23:00, then flushes across 11:00 and
  across midnight into 2023-09-26.
- Asserts `rollup-2023-09-25.jsonl` **appears on disk** (write half of the
  contract).
- `GET /api/v1/history/summary` returns the 10:00 point with `queries=3`,
  `blocked=1`, `cache_hits=1`, `per_type {A:2, AAAA:1}`, `ts=2023-09-25T10:00:00Z`.
- `GET /api/v1/history/perf` carries the seeded **`rss_bytes` (57 213 952)** and
  **cache stats** (`entries=1234`, `max_bytes=67 108 864`) — proving RSS and cache
  series are persisted and served (DoD).
- `GET /api/v1/history/top?kind=blocked` returns the seeded top-N
  (`ads.example.com`, count 2 — both blocks merged into the completed day's file).

**`post_config_retention_change_prunes_on_the_next_flush`**

- A throwaway `Stats` lays down a 40-day-old and a 10-day-old rollup day-file on
  the shared `/data` **through the real writer** (a query recorded in each day,
  the hour flushed) — the only way to place files older than a test's lifetime,
  and one that keeps the test from restating fah-stats' filename scheme or row
  format, so there is nothing here to drift out of step with the writer.
- The served instance boots over those files with `retention_days=90`; both days
  read back through `GET /api/v1/history/summary` first (proving the files exist
  black-box, no filename reconstruction).
- Flips retention to 30 through the real `POST /api/v1/config` (`applied: true`),
  then the next flush prunes.
- Asserts the 40-day day now reads **empty** and the 10-day day still **has
  data** — at the original 90-day window neither would have been pruned, so the
  deletion is attributable to the live change reaching the writer through the API
  (hard rule 3: atomic swap, no restart).

**What it is settling from.** The overnight run was started on a process that had
just absorbed a hammer *plus* list add/remove/refresh churn. Every one of those

sample is one such recompile caught mid-flight. In parallel the cache is still
evicting hammer-profile answers in favour of real traffic, which is why
`cache.bytes` falls ~6 MiB while RSS does not.

**Therefore this run bounds RSS but cannot clean-room the "does the new sampler
leak" question** (p1.5-07's stated risk: "the sampler adds no unbounded memory",
hard rule 4). A process carrying a dozen recompiles' worth of retained arenas is
not a steady-state baseline. Two ways to close it:

- **Accept the decay curve.** Morning reading (~14 h in) should show RSS

  sufficient evidence of a plateau, given the known contamination — record it and
  tick "RSS flat over hours".
- **Or take a clean baseline.** Restart the container and run `--profile real`

  start is real, and this is the only run that can attribute growth to the new

and no longer decelerating**, treat it as real accumulation: compare
`cache_estimated_bytes` and `ruleset_bytes` across the two readings first — if

### Bug found while checking the numbers — `cache_misses_total` counted blocks

**FIXED** in `crates/fah-metrics/src/registry.rs`. `Metrics::record` runs for
every `QueryEvent`, and its cache branch was unconditional — so a blocked query,
which carries `cache_hit == false` by construction because it never reaches the
cache (ADR-0001), was counted as a cache **miss**.

Three independent confirmations:

- **Static:** every query-path cache access (`key`, `lookup` ×3, `store`) lives
  inside `Pipeline::resolve`, whose only call site is the `None` arm of
  `match local_response`; `local_response` is `Some` iff the verdict was `Block`.
  So a blocked query provably never calls `note_lookup`, and the blocked arm
  hardcodes `cache_hit: false` as a literal.
- **Cumulative, over 26.4 M queries:** `hits + misses` = 26 420 468 =
  `pass + allow + block`, when it should equal `pass + allow`. Remove the block
  count and it is exact: `18 800 471 + (7 619 997 − 37 821)` = 26 382 647 =
  `pass + allow`.
- **Delta, two scrapes 330 s apart:** Δ(hits+misses) − Δ(pass+allow) = **+106 =
  exactly Δblock**, and the cumulative gap equalled the block total at both ends.

Scope: **`/metrics` only.** `GET /api/v1/cache` reads the cache's own
`note_lookup` counters and `build_perf_sample` takes hits/misses from the
`fah_dns::CacheStats` port, so neither the admin API nor the persisted history
was affected — p1.5's data contract is clean.

Impact scales with block rate, which is why this soak nearly hid it: blocks were
0.38 % of traffic under the hot-set profile, so the reported hit rate was 77.7 %
against a true 78.0 %. At a realistic 30 % household block rate the same
arithmetic reports ~55 % against a true ~78 % — a 23-point understatement, worst
exactly when the blocker is working well, on the number a Grafana dashboard would
plot. Regression test: `a_blocked_query_is_not_counted_as_a_cache_miss`, which
asserts the invariant `hits + misses == pass + allow`.

### The query log's disk segments have no read path

**Documented, not fixed** — a reader is dashboard-phase work.

`Stats::query_log` is one line: `self.ring.lock().unwrap().query(…)`. It reads
the in-RAM ring (`[query_log] ring_entries`, default 10 000) and never opens the
`/data/query_log/segments/` files that `retention_days` / `retention_max_mb`
govern. Confirmed black-box: with 501 MB of segments on disk, every `from`/`to`
window older than ~2 minutes returned an empty `items` array — and
`10 000 ÷ 85 qps` = 118 s, which matches.

Why it matters:

- API.md documented `from`/`to` and cursor pagination on `/api/v1/queries` with
  no mention of a ring limit, and an out-of-range window returns **empty rather
  than an error** — an operator reads that as "no queries happened".
- Under this load the segments cost ~1.8 GB/day of writes (≈250 B/record ×
  7.3 M queries/day) recycling a 500 MiB cap every ~6.7 h, for data nothing can
  return. `retention_max_mb` binds long before `retention_days`, so the retained
  span is hours, not the configured week. At household rates it is ~25 MB/day and
  the ring covers ~2.8 h.
