# p2.5-03 — Encrypted Transport Reconnect on Timeout

## Implementation Summary

A timed-out DoT/DoH exchange now invalidates the pooled connection, so the
next exchange establishes a fresh one. The timeout itself surfaces unchanged
(same `io::ErrorKind::TimedOut`, same message, no in-query retry); the
reconnect is paid by the *next* query. Spec S1.15 ("a persistent v6 DoT/DoH
connection reconnects, which is not a failure") is now true in code.

Invalidation is identity-safe via a monotonic generation counter, not by
comparing connection handles: `DnsExchange` is a cheap clone with no identity
that survives cloning, so pointer/`Arc::ptr_eq`-style comparison was not
available. `Mutex<Option<DnsExchange>>` became `Mutex<Slot>` where
`Slot { generation: u64, exchange: Option<DnsExchange> }`; `generation`
increments on every **store** and never on clear.

| Element | Shape |
| --- | --- |
| `acquire(timeout, stale)` | one entry point for both the first attempt (`stale = None`) and the post-error reconnect (`stale = Some(g)`): adopts the slot's exchange unless its generation *is* `stale`, otherwise connects and stores. Returns `Held { exchange, generation, fresh }` |
| `invalidate_if_current(g)` | locks the slot; clears `exchange` only if `slot.generation == g` |
| Invalidates | any `TimedOut` from `send_once` (pooled or fresh); any error from a fresh connection; any error from the post-reconnect retry (that exchange is fresh) |
| Does not invalidate | pooled non-timeout error — keeps today's reconnect-once-and-retry path; connect-phase errors store nothing, so there is nothing to clear |

## Design decisions

- **Generation counter over handle identity.** Cloned `DnsExchange` handles
  are indistinguishable, and the slot's `Arc` inners are not exposed. A `u64`
  bumped under the slot's own lock gives a total order with no ABA: it never
  decreases, only a store advances it, and a clear leaves it alone — so a
  stale generation can match only when the slot still holds that exact
  exchange, or when it is already `None` (clearing `None` is a no-op).
- **Retry-after-reconnect errors invalidate too.** The retry runs on a
  just-stored connection; it falls under the plan's "fresh connection's error
  clears its own exchange" rule. Without it a dead just-made connection would
  be handed to the next query.
- **One `acquire` instead of `connected` + `reconnect`** (F1 fix). The two
  differed only in whether a stored exchange may be adopted, which the stale
  generation expresses directly: `stale != Some(slot.generation)` → adopt.
  A reconnect therefore adopts a connection a concurrent query installed
  meanwhile instead of dropping it, and the plan's "never drop a newer
  exchange" invariant now covers reconnect as well as invalidation.
- **Fresh non-timeout error is not distinguishable by handshake count.** The
  plan's test 3 ("fresh error clears → `handshakes()` +2") cannot separate old
  from new behaviour: the old code reached 2 handshakes anyway via its
  pooled-error reconnect path. That test was replaced with the *fresh timeout*
  case, which is a genuine discriminator — the old code never reconnected on
  timeout at all.
- **Two comments deleted** (hard rule 7 permits deletion only, not rewriting):
  - `query()`'s "the connection is likely fine and the upstream slow" rationale
    — this task reverses exactly that decision;
  - `connect()`'s `mux_timeout` rationale, whose "(fall back, keep the
    connection), never as 'connection dead' (reconnect)" clause is now false.
    The surviving invariant, recorded here instead: **`mux_timeout` must stay
    above `attempt_timeout`** (it is `attempt_timeout * 2`) so `send_once`'s
    own timeout always fires first and the `TimedOut` classification in
    `query()` is the one that runs.

## Known limitations / deferred

- Timing assertions use a 400 ms attempt timeout and a "< 2 windows" bound.
  That bound is the semantic invariant (no in-query retry), not a latency
  budget; it is loose enough to survive a loaded dev box.
- The blackhole tests cost ~0.4 s each in wall time.
- DoH is not covered by an offline test (no local H2 DoH rig exists); the
  invalidation code path is transport-agnostic — it lives in `ExchangeConn`,
  above the `ConnectTarget` split.
- Error-kind mapping fidelity remains p2.5-04's job; this change depends on
  `send_once`'s own `TimedOut` construction, which p2.5-04 must keep exact.

### Findings

#### F1 — Minor: `reconnect()` discards a connection another query installed concurrently — **FIXED**

- `reconnect()` connected unconditionally. Two queries holding the same
  idle-closed pooled exchange (gen G) both fail non-timeout; A reconnects
  (G+1), B then reconnects again (G+2), dropping A's live connection.
  Pre-existing behaviour, but the plan's invariant "a concurrently installed
  newer exchange is never dropped by an older query" held for invalidation and
  not for reconnect.
- Impact if unchanged: N extra handshakes per idle-close under N concurrent
  queries (`tls_handshakes` over-counts churn — relevant since that counter is
  this task's churn signal for Stage 1). Inference, not measured.
- Fix: `connected` and `reconnect` merged into `acquire(timeout, stale)`; the
  adopt branch runs whenever the stored generation differs from `stale`. Net
  effect is fewer lines than before the fix. Covered by
  `reconnecting_adopts_a_connection_another_query_already_installed`.
- A retry on an *adopted* exchange still invalidates on error: the generation
  check means only that exchange can be cleared, and it just failed a send.

#### F2 — Minor (observation, defer): slot lock is held across `connect()`

- `connected()` holds the `Mutex` through the TLS handshake (pre-existing).
  Concurrent queries queue behind it; if the handshake itself hangs (upstream
  unreachable at TCP level), query k waits up to `k × attempt_timeout` before
  its own attempt, which the pool's per-server window does not bound.
- This change does not alter that, but makes the empty-slot state more
  frequent (every timeout empties it). In the S1.15 scenario the new-prefix
  handshake succeeds fast, so the practical effect is nil; the pathological
  case is a fully dead upstream, which behaved this way before.
- Inference. Out of scope here (plan closes connect-ahead/eager paths);
  record for the Stage 1 design, where per-endpoint penalty should shortcut a
  dead endpoint before the lock is reached.

#### F3 — Nitpick: 3-tuple return from `connected()` — **FIXED**

- Replaced by `Held { exchange, generation, fresh }`, which also gave the two
  `acquire` call sites in `query()` a single readable shape.

#### F4 — Nitpick: `Instant`-based timing assertions in tests

- `< 2 × window` with a 400 ms window is loose; the assertion is semantic
  (no in-query retry) and the margin is 400 ms. Acceptable; noted so a future
  flake on a loaded box is diagnosed as the margin, not the fix.

## Code review — final classification of F2 and F4

Re-examined against the task boundary (plan §Out of scope) and the actual
invariant each test pins. No code changed in this pass.

### F2 — reclassified: accepted architectural constraint, not a finding

- **What it is.** `acquire()` holds the slot `Mutex` across `connect()`.
  The field doc on `slot` records this as deliberate: concurrent first queries
  share one handshake instead of stampeding. Unchanged by p2.5-03 — the diff
  neither introduced nor widened the lock scope; it only made the empty-slot
  state reachable after a timeout, which is the task's whole purpose.
- **Why p2.5-03 does not own it.** The only alternatives are connect outside
  the lock (N concurrent handshakes — the stampede the lock prevents), a
  connect-ahead/eager path, or skipping a known-dead endpoint before the lock.
  The plan closes the first two explicitly ("no connect-ahead/eager reconnect
  … no pool of multiple connections per server") and the third ("no Stage 1
  penalty/probe logic"). The k × `attempt_timeout` queueing only arises for an
  upstream dead at TCP level, which is pre-existing behaviour on the first
  connect and is not the S1.15 scenario (new-prefix handshake succeeds).
- **Owner.** Adaptive DNS Stage 1 — S1.6 Penalty / S1.7 Probing
  ([docs/design/adaptive-upstream-selection.md](../../design/adaptive-upstream-selection.md)
  §S1.6): a Penalized endpoint is skipped during selection, so queries never
  reach this lock on a dead endpoint. That is the designed fix; it belongs to
  the Stage 1 implementation phase, not to a p2.5 hardening task. Nothing is
  owed by p2.5-04 … p2.5-09.
- **Classification:** closed — accepted constraint, no action in this phase.

### F4 — reclassified: accepted test-design margin, not a finding

- **Invariant under test.** After a timeout there is no in-query retry; the
  reconnect is paid by the next query. The failure signature of a regression
  (retry-now reintroduced) is `≥ 2 × attempt_timeout` (first send times out at
  T, reconnect, second send times out at T). The pass signature is
  `T + handshake` (milliseconds on the rig).
- **Is `< 2 × T` the right bound?** Yes — it sits exactly between the two
  signatures, and the gap it must absorb (one local TLS handshake) is orders
  of magnitude smaller than the 400 ms margin. The plan's tighter
  `T + 50 ms` would not detect any additional defect (every regression shape
  lands at ≥ 2T) and would turn a slow handshake on a loaded box into a false
  red. Same reasoning holds for the `[blackholed, live]` fallback test.
- **Classification:** closed — accepted margin, no action.
