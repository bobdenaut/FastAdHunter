1. Baseline: `GET /api/v1/telemetry` (`ruleset.rules`), `GET /api/v1/lists`
   (per-list `rules_total`, `last_status`); owner: `/file/print where
   name~"fastadhunter/data/lists"` (sizes + dates).
2. **Yes #1** → `POST /api/v1/lists` `{"id":"p2509-drill","url":"https://example.com/","enabled":true,"refresh_hours":24}`
   then `POST /api/v1/lists/refresh`.
3. Verify: `GET /lists` shows `p2509-drill` `last_status: "rejected"`, every
   other list unchanged; `ruleset.rules` unchanged; `/file/print` sizes
   unchanged; no `p2509-drill` file under `/data/lists` (no baseline → nothing
   written).
4. **Yes #2** → `DELETE /api/v1/lists/p2509-drill`; re-read `GET /lists`,
   `/telemetry`, `/file/print` — back to step-1 values.

Caveat: a brand-new list has no last-good copy, so "last-good survives" is
exercised as "nothing is written and the serving ruleset is untouched". The
stronger variant (poison an existing list's source) is a config mutation on a
serving list and is not proposed.

## Soak procedure (V6, prepared)

Window = V2 container start → ≥ 12 h later, no router reboot / ISP outage
inside it (rerun otherwise). Source `GET /api/v1/history/perf?from=<T0>&to=<T1>&fields=rss_bytes,peak_rss,memory`.
Residual = `memory.residual_bytes` per sample. Split into thirds; least-squares
slope per third; pass when slope signs disagree between thirds (no monotone
drift). `counters.events_dropped` and `counters.swr.dropped` deltas from the T0
vs T1 `/telemetry` snapshots must be 0; `peak_rss` steps only at the scheduled
list refresh.

## Findings

### F1 · Major · V5b unsatisfiable — per-query `endpoint` is dropped at the API wire (plan/code mismatch)

Chain, verified by reading:

| Hop | Location | `endpoint` |
| --- | --- | --- |
| `UpstreamPool::forward` | `fah-dns/src/upstream/mod.rs:224` | set: walk index |
| `Resolved::forwarded` → `QueryEvent::with_outcome` | `fah-dns/src/pipeline.rs:439,466,497` | `Some(idx)` on forwarded, `None` on hit/block |
| `fah_model::QueryEvent` | `fah-model/src/query_event.rs:64` | field present, `skip_serializing_if` |
| event channel → `EventHub::publish_query` | `fah-api/src/events.rs:71` | whole `fah_model::Event` boxed into `QueryRecord` — still present |
| `From<QueryRecord> for QueryItemResponse` | `fah-api/src/wire.rs:165-215` | **never read**; `upstream: None` hardcoded |
| `encode(Event::Query)` | `fah-api/src/events.rs:103` | serializes `QueryItemResponse` → no key |

No other consumer reads it: `fah-stats` never touches `endpoint`;
`fah-metrics` reads `answer` only (`registry.rs:152`). So p2.5-05's
"endpoint attribution on the event" is true of the internal `QueryEvent` and
false of every external surface. API.md §WS (as reconciled in p2.5-08)
documents exactly that. p2.5-05's review listed "WS event stream: add optional
`answer` and `endpoint` keys" as a *doc* proposal — the code never followed.

Impact: the plan's V5b cannot be observed; the phase definition of done
("per-endpoint attribution appear … on events") is not met on any surface a
client can see. Aggregate attribution does exist: `/telemetry`
`upstreams[i].attempts` per endpoint and `counters.dns.answers`.

Options (owner decision, neither applied):

- **A — amend V5b** to an observable surface: "after a forced-fallback query,
  `upstreams[1].attempts` increments while `upstreams[0]` does not" is the
  nearest per-endpoint evidence; it is aggregate, not per-query.
- **B — small change, separate task or approved fix here**: add
  `endpoint: Option<u8>` (+ `answer`) to `QueryItemResponse` with
  `skip_serializing_if`, filled from `record.as_dns()`, and API.md §WS updated
  to the absent-means-cache-hit rule. ~10 lines, no hot-path cost (the field is
  already on the event), tui-monitor unaffected (no `deny_unknown_fields`).

Owner decision 2026-08-22: **B**, opened as
`plan/wip/phase2.5-hardening/p2.5-10-ws-endpoint-attribution.md` (strict
scope: `QueryItemResponse.endpoint` + one wire test + API.md §WS). V5b stays
FAIL in this task; it closes when p2.5-10 is deployed and observed live.
