# p2.5-05 — Outcome Telemetry: Client-Visible Failure and Endpoint Attribution

## Implementation Summary

A served SERVFAIL is now countable and separable by origin, and a forwarded
query's event names the upstream that answered it. Both ride the existing
`/telemetry` surface, the WS event stream and the perf-sample series — no query
log, no Prometheus (p2-09 stands).

### What was implemented

**Answer outcome on the event.** New `fah_model::AnswerOutcome`
(`Answered` | `ServfailSynthesized` | `ServfailRelayed` | `RefusedRelayed`,
`snake_case`, `Default = Answered`) plus two new `QueryEvent` fields:
`answer: AnswerOutcome` and `endpoint: Option<u8>`. Both are
`#[serde(default, skip_serializing_if = …)]`, so an ordinary answered query
serializes byte-identically to what it did before this change, and an event
written before this change still deserializes.

**Endpoint attribution.** `Forwarder::forward` now returns
`io::Result<ForwardOutcome>` — `{ message: Message, endpoint: u8 }` — declared
next to the trait in `crates/fah-dns/src/upstream/mod.rs`, deliberately not in
`fah-model`: it never crosses the event channel. `UpstreamPool` fills
`endpoint` with the walk index in configured order (`enumerate()`), so a
fallback past a dead primary is visible as `endpoint == 1`.

**Tagging.** In `Pipeline::resolve`:

| Path | `answer` | `endpoint` |
| --- | --- | --- |
| Forward `Ok`, ordinary RCODE | `Answered` | `Some(index)` |
| Forward `Ok`, `SERVFAIL`, no stale entry | `ServfailRelayed` | `Some(index)` |
| Forward `Ok`, `REFUSED` | `RefusedRelayed` | `Some(index)` |
| Forward `Err`, no stale entry | `ServfailSynthesized` | `None` |
| Block / cache hit / SWR stale / stale-after-failure | `Answered` | `None` |

A stale serve that masked a failure stays `Answered`: the masking is already
counted through `cache_stale` + `StaleServe::AfterForwardFailure`, and
double-counting it here would break the "SERVFAIL served to a client" reading
the counter exists to give.

**Counters and export.** Three `AtomicU64` on `fah_metrics::Metrics`
(`answers_servfail_synthesized`, `answers_servfail_relayed`,
`answers_refused_relayed`), incremented in `record()` off `event.answer` and
touching none of the verdict/cache/stage logic. Exported as
`fah_model::AnswerCounters` embedded as `answers` in `DnsCounters`
(`/telemetry` → `counters.dns.answers.*`) and mirrored as three fields on
`MetricsSnapshot`.

**Persistence.** `PerfSample` gains `answers_delta: AnswerCounters`
(`#[serde(default)]`), computed by `build_perf_sample` as the per-interval
delta the way `queries_delta` is, and surfaced on `GET /history/perf` as an
`answers_delta` key with a matching `?fields=answers_delta` selector. Without
this the numerator resets at every restart and the before/after judgement the
task exists to enable would have no history behind it. Rows written before this
change read back as all-zero.

### Design decisions

**1. `with_outcome` builder instead of two more `QueryEvent::new` parameters
(deviation from the plan's U1).** The plan called for extending `new`. Doing so
takes it to eight parameters, which trips `clippy::too_many_arguments` under
`-D warnings` on a public constructor, and churns 19 call sites — almost all
test and bench fixtures that would pass `AnswerOutcome::Answered, None`. The
file already establishes the chained-setter idiom for exactly this kind of
optional attribution field (`under_policy`, added for `policy` in p2-06), so
`with_outcome(answer, endpoint)` follows the surrounding code. The cost is that
the compiler no longer forces every construction site to state an outcome; that
is covered instead by the pipeline tests, which assert the outcome end-to-end
on every path rather than at the constructor.

**2. `u8::try_from(index).unwrap_or(u8::MAX)` rather than `index as u8`.** A
silent truncation would attribute upstream 256 to upstream 0. Saturating is
wrong too, but wrong in a way that reads as "off the end of the list" instead of
as a real endpoint. Since the m4 fix it is also unreachable by configuration:
`fah_config::MAX_UPSTREAM_SERVERS` (255) is rejected at validation, so every
accepted index is ≤ 254 and `u8::MAX` stays a pure sentinel.

**3. `ForwardOutcome` in fah-dns, not fah-model.** It never crosses the event
channel; putting it in L1 would make `fah-model` carry a type only one L3
consumer sees.

**4. `answers` nested under `DnsCounters` rather than three flat fields.** One
`#[serde(default)]` instead of three, and the grouping says these three are one
axis. Same reasoning applied to `PerfSample.answers_delta`, which reuses
`AnswerCounters` rather than declaring a structurally identical delta type.

**5. `Pipeline::resolve` returns a private `Resolved` struct** (n2 fix), with
four named constructors — `blocked`, `from_cache`, `forwarded`,
`synthesized_servfail` — one per way a query can be answered. That is what
removed the 6-tuple, the `answer` shadowing (n1) and the
`#[allow(clippy::too_many_arguments)]` on `emit_event`, which now takes
`&Resolved` instead of six positional fields. It also makes the
cache_hit/upstream_used/stale/outcome/endpoint combination unspellable
per-branch: each path picks a constructor, not six values.

### Invariants checked

- `hits + misses == pass + allow` — asserted explicitly in
  `answer_outcomes_are_counted_on_their_own_axis` across a five-event matrix
  including a block, a cache hit and all three failure outcomes. The new
  counters are a parallel axis; nothing was re-routed.
- A synthesized SERVFAIL still counts pass + miss + one `forward`-stage sample
  and nothing else — pinned by
  `a_synthesized_servfail_still_counts_as_a_pass_a_miss_and_a_forward`.
- The `StaleServe` identity from the 0.2.12 soak is untouched: no branch that
  sets `stale` was changed, and the SWR test asserts
  `stale == Some(FromSwr)` alongside the new fields.
- No serialized field renamed or removed. Old event JSON deserializes to
  `Answered`/`None` — pinned by
  `pre_change_event_json_deserializes_to_answered_without_an_endpoint`.
- `fah-model` purity held: data types, derives and two trivial accessors.

### Hot path

Per event: one enum copy plus one `Option<u8>` copy into a struct already being
built, and one predictable branch in `Metrics::record` that is a no-op for the
`Answered` case. `ForwardOutcome` moves the `Message` rather than cloning it.
Zero allocations added. `QueryEvent` gains two single-byte fields; whether they
land in existing padding was not measured.
Benches were not re-run — no bench-visible code path changed shape, but the
bench forwarders' source did change (`Ok(response)` →
`Ok(ForwardOutcome::new(response, 0))`), which p2.5-09's A/B must account for.

a deployed older binary ignores the unknown `answers` / `answer` / `endpoint` /

binary against an older server reads them back as defaults. Verified by
compiling the workspace including `tui-monitor` and by the pre-change-JSON
