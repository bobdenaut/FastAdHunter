# p2.5-07 — SWR Claim Lease vs Worst-Case Upstream Walk

## Implementation Summary

The refresh claim lease is now a `DnsCache` field set by the constructor, and
the **binary** derives it from `[dns.upstreams]`. `crates/fah-dns/src/cache.rs`
keeps its refusal to know upstream configuration; the derivation is one pure
function in `crates/fastadhunter/src/main.rs`.

- `DnsCache::new(config, refresh_claim_lease)`; `Pipeline::new(rules,
  forwarder, blocking_ttl, cache_config, refresh_claim_lease, events)` — sixth
  parameter, before `events`.
- `pub const DEFAULT_REFRESH_CLAIM_LEASE = 5 s` exported from `fah-dns` for
  tests and the two benches; the private `REFRESH_CLAIM_LEASE` const and its
  now-wrong rationale block are deleted (mechanism recorded here instead).
- No configuration validation added. No `servers × timeout_ms` combination can
  fail boot.
- SWR semantics unchanged: `REFRESH_FAILURE_COOLDOWN` (30 s), `STALE_SERVE_TTL`,
  `MAX_STALE`, worker count, queue bounds and drop-not-backpressure (ADR-0005)
  are untouched. Only the claim's expiry duration is parameterized.

### Decisions

- Lease is a `DnsCache` constructor parameter; the binary derives it. The
  cache still knows nothing about upstream configuration.
- Per-server attempt is wall-clock bounded by an outer `timeout(3T)` in
  `UpstreamServer::query` — one site for UDP and encrypted. The bound lives
  next to the walk it bounds (`ATTEMPT_LEGS`, `worst_case_walk` in `fah-dns`).
- `lease = max(5 s, 2 × worst_case_walk)`; no ceiling, no config key, no
  config validation.
- Outer timeout does not invalidate the pooled exchange; the inner `send_once`
  timeout still does (p2.5-03 invariant kept).
- Queue residency (claim → dequeue) is not part of the walk: out of scope,
  recorded in ADR-0005 as a known bound.

### For the Stage 1 spec's S1.9 section

| Quantity | Value |
| --- | --- |
| Per-server attempt bound | `ATTEMPT_LEGS × T` = `3T`, outer `timeout` in `Server::query` (wall-clock) |
| Worst-case ordered walk | `worst_case_walk = 3 × N × T` (`fah_dns::worst_case_walk`) |
| Lease formula | `max(5 s, 2 × worst_case_walk)` |
| Guarantee | lease ≥ 2 × wall-clock worst-case walk, floor 5 s, no ceiling |
| Shipped defaults (N=2, T=800 ms) | 5 s → **9.6 s** |
| 8-endpoint cap (N=8, T=800 ms) | 38.4 s |

N = `config.dns.upstreams.servers.len()`, T = `timeout_ms`. Amended
2026-08-22 (finding #4): plan U2 implemented — outer bound in
`Server::query` (`upstream/mod.rs`), `ATTEMPT_LEGS` and `worst_case_walk`
exported from `fah-dns`, derivation in `main.rs` imports them.

### Why `3 × N × T` is a wall-clock bound

`UpstreamPool::forward` (`upstream/mod.rs:197-228`) is a sequential `for` over
`self.servers`, no concurrency, no early exit on error — so the walk is
`N × (one server attempt)`, and one attempt is `≤ 3T` because `Server::query`
is wrapped in `timeout(ATTEMPT_LEGS × T, …)` regardless of transport.

The inner legs justify the number 3, and they are why the outer bound never
fires first on an uncontended attempt:

| Transport | Inner chain | Sum |
| --- | --- | --- |
| Encrypted (`encrypted.rs:93-120`) | pooled `send_once` (≤ T) + `acquire` reconnect (≤ T) + retry `send_once` (≤ T) | 3T |
| Plain UDP (`plain.rs:21-49`) | `udp_round_trip` (≤ T) + truncation `tcp_round_trip` (≤ T) | 2T |

Each inner leg is a `tokio::time::timeout(attempt_timeout, …)`: `send_once`,
`connect` (`encrypted.rs:181`, also enclosing the DoH `lookup_host`
bootstrap), `udp_round_trip`, `tcp_round_trip`. The retry leg is unreachable
when the first `acquire` connected (`held.fresh`) or the error was `TimedOut`.

**What the outer bound fixes (finding #4).** Two legs are untimed: the `slot`
mutex wait in `acquire` (`encrypted.rs:123`) and in `invalidate_if_current`
(`encrypted.rs:143`). The lock is held across `connect`; with the exchange
`None` and a dead server every waiter runs its own connect in turn, so the
*k*-th concurrent forward waits `k × T` before its own legs start, *k*
unbounded. Before U2, `3NT` therefore bounded timed legs only and the 2×
margin was carrying the mutex wait (covers k ≤ 6). After U2, the 2× margin
covers executor scheduling latency only.

`UdpSocket::bind`/`connect`/`send` are outside the inner timeouts but are
non-blocking syscalls, and inside the outer bound anyway.

### Why derive rather than validate

A config-load rejection of large `servers × timeout_ms` turns a working
configuration into a boot failure for something a derived lease absorbs
silently — the same migration-trap class as `deny_unknown_fields`.

### Why a longer default lease is safe

A lease is a *deadline*, not a flag. Lengthening it only delays reclaiming an
abandoned claim (worker panicked or aborted at shutdown). It can never produce
a wrong answer or an entry that never refreshes: the failed-refresh path sets
the 30 s cooldown, and a successful refresh replaces the whole entry, clearing
suppression. The 5 s floor keeps small configurations on today's behaviour.

### Answer to the review question

**No.** P2.5-07 proves `lease >= 2 x (timed legs of one forward walk)`, not
`lease > worst-case walk`. Two legs of the real walk are outside every timeout
and outside the derivation: the `slot` mutex wait in `ExchangeConn::acquire`
(`encrypted.rs:123`, *k* concurrent forwards serialise at ~*k*·T per dead
server) and SWR queue residency between claim and dequeue (`cache.rs:536`
stamps the lease; `swr.rs:174` dequeues up to 64 jobs per worker later, no
re-stamp). The 2x margin covers k <= 6 and an empty queue; beyond that it is a
heuristic, as the summary's own caveat admits. The 8-endpoint arithmetic
(3·8·0.8 s = 19.2 s < 38.4 s) holds for the timed legs only.

  2T. On an exact 3T tie `Timeout::poll` polls the wrapped future before its
  `Sleep`, so the inner result wins.
- **Cancel-safety.** No await between `connect(..).await?` returning and
  `slot.store`, so a handshake that completes is never lost; guard drop
  releases the lock; during `send_once` only the request's oneshot drops, the
  pooled exchange stays (documented decision).
- **Arithmetic.** N ≤ 255 (`fah_config::MAX_UPSTREAM_SERVERS`); at
  (u32::MAX ms, 255, ×3, ×2) = 6.6e9 s, far below `Duration`'s u64 secs — no
  `Duration * u32` panic. `timeout_ms = 0` is not rejected by config
  validation (pre-existing); the lease floors to 5 s and inner timeouts were

- **Walk = N × attempt.** `forward` has exactly one await per server;
