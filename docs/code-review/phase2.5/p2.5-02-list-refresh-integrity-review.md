## Summary

A fetched body is parsed on the blocking pool and gated before `commit_raw`
can touch the `/data` copy. A refused body behaves exactly like an I/O
failure: last-good copy untouched, no compile, reason recorded and readable
via `GET /api/v1/lists`. `rejected` is one word on every surface —
`last_status`, `POST /api/v1/lists/refresh` results, the `list_refreshed`
event. A permanently rejected list (source legitimately restructured) is
recovered by `DELETE` + re-add, and `DELETE` now guarantees that contract:
it removes the cached copy first and fails (`500`, list kept) if it cannot.

Three review passes. Pass 1 (F1–F4, N1) fixed worker placement, the
poisoned-baseline lockout, the mid-fetch disarm race, and weak collapse
tests. Pass 2 closed every deferred item (N2–N6), unified the REST/SSE
vocabulary, made the recovery contract real and tested, removed the stale
Rust doc comments, and brought API.md, RULE_ENGINE.md, project-state.md and
the task/plan files to the shipped behaviour. Pass 3 (adversarial, final)
closed S6 by construction, bounded the validation-parse transient under
`compile_lock`, and added the document sniff that protects URL-only and
first-fetch copies from the common error-page case.

## Gate rules

| Rule | Fires when | Armed |
| --- | --- | --- |
| document | first non-blank text (BOM skipped) is `<!doctype` / `<html`, ASCII case-insensitive | always |
| misparse | `RefreshStats::looks_misparsed()` — ≥ 100 parse errors **and** errors > rules | always |
| zero-DNS | fetched `active == 0` | baseline `active > 0` |
| collapse | fetched `active + url < baseline / 10` | baseline `active > 0` and `active + url ≥ 1000` |

Baseline = `ListStatus.compiled`, snapshotted before the fetch await; when
that snapshot is `None` the value after the fetch is used instead (closes the
re-enable window found in pass 2). The boot compile restores it from the
cached copy, so a rejection holds across restarts. `compiled == None` on both
reads (no cached copy) leaves rule 1 as the only guard.

## Decisions

- **`rejected` on every surface.** `ListRefreshOutcome.result` is a
  `RefreshResult`; `routes.rs::status_label` is the one place that turns a
  `RefreshResult` into a status word, used by `GET /lists`, both refresh
  routes and the event. Additive in the same sense as the `GET /lists`
  widening (no consumer switches on `failed`: `dashboard/` is empty,
  `tui-monitor/` does not read these fields). `failed` in
  `RefreshAllResponse` counts rejected lists, so `refreshed + failed ==
  results.len()`.
- **`DELETE` + re-add is the recovery contract**, documented in API.md and
  RULE_ENGINE.md and pinned by test. `remove_list` removes the cached copy
  before dropping the entry and returns `LifecycleError::CacheRemove` on
  failure; the API answers `500` and restores the TOML. Disable/re-enable
  does not clear a baseline; the copy belongs to the `id`, not the `url`.
- **Stale Rust doc comments deleted, not rewritten** — hard rule 7 and the
  hook forbid writing any comment, so deletion is the only legal fix
  (`LifecycleError`, `refresh_list`, `ListRefreshOutcome`, `remove_list` in
  `mod.rs`; `last_status`, `status`, `error` in `wire.rs`).
- **Validation parse runs under `compile_lock`** (pass 3). The text +
  `ParsedRuleList` transient can no longer sit beside a batch compile's
  transient (158 MiB peak measured on the RB5009 for the compile alone,
  256 MB container ceiling — an inferred OOM path, not a measured one).
  Cost: a manual refresh waits for an in-progress compile before parsing
  instead of before committing; it already waited for the compile at the
  commit step. Lock order `refresh_lock` → `compile_lock` is unchanged.
- **A deleted id cannot be written back by a refresh in flight** (pass 3,
  S6). `remove_list` takes `compile_lock` before removing the copy and the
  entry; `fetch_and_commit` checks under the same lock that the entry it
  fetched for is still the registered one (`ptr::eq` on the `Arc`) and
  returns `LifecycleError::ListRemoved` otherwise — parse skipped, nothing
  written. `record_status` updates only an existing status, so a stale
  attempt cannot resurrect a deleted id. If the id was re-added inside the
  window, the new entry shows `failed: list … was removed while its refresh
  was in flight` until its next attempt (due at the next scheduler tick).
- **Document sniff** (pass 3). Reads at most nine characters after leading
  whitespace/BOM; no rule format can begin with `<!doctype` or `<html`, so
  the rule has no false positive by construction. It names the common
  captive-portal / CDN error page on any baseline — including URL-only
  copies and first fetches, which the count rules leave open by design.
  Bodies it does not catch (JSON errors, HTML without a leading tag,
  truncation) stay with the count rules.
- **Parse panic left as in `compile()`** — `.expect` on the
  `spawn_blocking` join mirrors the existing compile path; a parser panic was
  already fatal to the scheduler before this task. Not widened here.
- **`parse_errors` describes the serving copy**, like the `rules_*` counts,
  never the refused body (whose counts live only in `last_error`).

## Known limitations

| Case | Behaviour |
| --- | --- |
| DNS list (`baseline.active > 0`) replaced by an HTML/empty/binary body | rejected, any size |
| URL-only list (`baseline.active == 0`) replaced by an HTML document or a misparsing body | rejected |
| URL-only list replaced by non-HTML, sub-floor garbage (empty body, JSON error, URL-pattern noise) | **committed** — the count rules are disarmed by design: arming a URL-pattern floor lets a poisoned first fetch (`a_poisoned_url_only_baseline_does_not_lock_out_the_real_list`) lock the real list out, and the URL tier is the opt-in HTTP path, not DNS protection |
| First fetch, no cached copy, non-HTML body with sub-floor parse errors | committed — nothing to protect |
| List that legitimately publishes zero DNS rules, or restructures below a tenth | rejected until `DELETE` + re-add |
| Same `id` pointed at a new `url` | gated by the old source's copy — use a new id or `DELETE` + re-add (API.md) |

Deferred, unchanged from the plan's out-of-scope list: no `pending_cache`
aggregate bound, no `Content-Length` pre-check, no checksums, no
retry-sooner-on-reject.

A/A control (baseline tree re-run against its own `base`, same session):
`hit_exact` +10.3 %, `hit_subdomain` +11.3 %, `miss` +5.1 % — all with
`p < 0.05`. The dev box's run-to-run spread is therefore ≥ 10 %, larger
than every A/B delta, and the A/B deltas point both ways. **No hot-path
change is detectable**; criterion's `p` values are not evidence here
(docs/measurement-traps.md). The structural proof is the diff: since
`8868fec` only `lifecycle/mod.rs`, `fah-api/routes.rs` and `wire.rs`
changed; `ListManager::matcher()`, `swap_in`, the `ArcSwap` field and
everything under `matcher/` and `fah-dns` are byte-identical, and
`pipeline.rs:270` still reads `self.rules.matcher()`. The rebuilt
`fah-rules` crate shifts code layout, which is the most plausible source of
the ±2–7 % scatter.

Refresh path — intentionally changed, not expected to be neutral. Per
successful refresh the tree adds: one `parse_rule_list` of the fetched text
(below), a ≤ 9-character sniff, and `compile_lock` held across that parse.
Nothing else on the path changed (`fetch`, `commit_raw`, `compile` untouched).

Double-parse cost — a second full parse of the fetched text per successful
refresh, on the blocking pool, under the list's `refresh_lock` only.
