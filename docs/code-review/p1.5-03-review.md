# p1.5-03 — History Config + REST-Live Retention: implementation review

**Task:** [plan/wip/phase1.5/p1.5-03-history-retention-config.md](../../plan/wip/phase1.5/p1.5-03-history-retention-config.md)
· **Status:** DONE, gates GREEN · **Commit:** deferred (phase1.5 commits as one
batch).

A `[history]` config section and a `retention_days` the user can change to
30/60/90 (or anything in `[1, 3650]`) **via `POST /api/v1/config` without a
restart**, applied live to both history writers through an atomic — not baked at
construction like the p1-07 query-log caveat.

## What was built

**`fah-config`** — new `HistoryConfig { enabled: bool,
sample_interval_seconds: u32, retention_days: u32 }` (defaults `true` / `60` /
`30`), wired into `Config`, the reference TOML, the `FAH__HISTORY__…` env
override match arms, and `validate()`. Validation rejects `0` and absurd values
(`retention_days ∈ [1, 3650]`, `sample_interval_seconds ∈ [1, 86400]`) via a new
`validate_range` helper, consistent with the existing non-zero-port style.

**`fah-stats`** — the two history writers (`RollupWriter`, `PerfWriter`) now hold
`retention_days` as a single **`Arc<AtomicU32>` shared between them** and with
`Stats`; `prune` reads it with `Ordering::Relaxed` each pass. `Stats` gained:

- `set_history_retention_days(u32)` — one atomic store; the next prune on *both*
  writers keeps the new window, nothing reconstructed (hard rule #3).
- `set_history_enabled(bool)` / `history_enabled()` — an `AtomicBool` gating
  `flush_history` and `persist_perf_sample` (each becomes a no-op when off),
  mirroring `query_log.enabled`.
- `Stats::new` now takes `&HistoryConfig` and seeds both from it.

**Wiring** — `post_config` (routes.rs), after a successful `apply_patch`, reads
the merged effective `history.{enabled, retention_days}` and calls the new
`StatsSource::apply_history_config(enabled, retention_days)` port method
(implemented on the binary's `StatsAdapter`, forwarding to the two setters).
Idempotent (two atomic stores), so it runs after every apply rather than diffing
the patch. `main.rs` passes `&config.history` into `Stats::new` and threads
`history.sample_interval_seconds` into `spawn_perf_sampler`.

## The design call worth flagging

**`retention_days` and `enabled` are runtime (live); `sample_interval_seconds`
is boot.** The perf sampler's `tokio::time::interval` ticker is built once at
startup — making the *cadence* live would mean rebuilding or `select!`-reloading
the ticker, machinery the acceptance criteria don't call for. So the cadence is
honestly documented as restart-required in CONFIGURATION.md, while retention and
the master switch — the things a dashboard actually toggles — apply live. The
sampler still **re-reads `history_enabled()` every tick** (and resets its delta
baseline when off), so disabling takes effect immediately even though the
interval itself is fixed.

One shared atomic for two writers (not one per writer) means the single
`POST`-driven setter moves both prune cut-offs together — there is no state where
rollups and perf disagree on the window.

## How the acceptance criterion is verified

"Setting `history.retention_days` via `POST` changes what the next prune keeps —
no restart" is proven by two composing tests:

- **`fah-api/tests/api.rs::history_retention_change_is_pushed_live_to_the_writers`**
  — a real `POST /api/v1/config` with `{"history":{"retention_days":90}}` returns
  `applied:true, restart_required:false`, and a recording `FakeStats` confirms
  the handler reached the stats port with `(true, 90)`.
- **`fah-stats::history::rollup::live_retention_change_moves_the_next_prune_cutoff`**
  — with a 40-day-old file present, a prune at retention 90 keeps it; storing 30
  into the shared atomic (what the port setter does) and pruning *again* deletes
  it — no reconstruction between the two prunes.

Plus `history_enabled_toggles_the_flush_live` (disabled → flush writes nothing;
`set_history_enabled(true)` → the next flush persists) and config-crate tests for
defaults, `0`/absurd rejection, and the `FAH__HISTORY__RETENTION_DAYS` env
override.

## Performance

Nothing on the per-query path. The live apply is two `AtomicU32`/`AtomicBool`
stores on the admin-plane `POST` handler; each prune reads one relaxed atomic
load it was already going to run. Memory is unchanged — the writers still hold a
path, a (now shared) retention handle, and prune cursors. No hot-path
allocation, lock, or new bench target, so none was taken (consistent with the
~6× unpinned-criterion noise on this box).
