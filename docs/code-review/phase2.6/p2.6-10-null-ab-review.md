## Frozen measurement protocol

Pre-declared before any measurement. Nothing below is tuned after results are
seen; a defect found mid-session stops the session and is reported.

### One repetition

1. 60 s settle, no load.
2. `GET /api/v1/config`, then `GET /api/v1/telemetry` — **T0**.
3. Fixed-duration load at a fixed offered rate (L.1: 600 s).
4. **30 s quiet drain, no load.** `upstreams[].attempts` and `counters.swr.*`
   reach the metrics registry through the binary's 10 s telemetry poll
   ([main.rs:697](../../../crates/fastadhunter/src/main.rs#L697)), not live, so a
   snapshot taken at load stop undercounts them by up to one poll interval of
   traffic (F4).
5. `GET /api/v1/telemetry` — **T1**.
6. `GET /api/v1/history/perf?from=T0-120s&to=T1+120s`.
7. 60 s cool-down.

The load window `[load_t0, load_t1]` is recorded separately from `[T0, T1]`.
Counters come from the T0/T1 snapshots; perf rows are filtered to the load
window, so the drain's near-idle rows never enter a per-repetition percentile.

Nothing is restarted or reset for the whole session. Every counter is a delta.

### Warm-up repetition

One repetition labelled `W` runs first and is **discarded**. It is declared
discarded here, before the session, not selected out afterwards. It absorbs the
cold cache, the boot compile and the first-interval sampler artefacts, all of
which the dry run observed (F7 evidence below).

### What is alternated

Only the label string in the output directory name. Same container, same image,
same config file, same process with no restart, same generator command, same
corpus, same offered rate, same duration. The arms differ in nothing a program
can observe, so every measured difference is session noise by construction.
`A/B/A/B…` splits monotone drift — thermal, production-container traffic, cache
growth, ISP variation — across both labels instead of loading one.

### Workload and fixed configuration

The S1-L L.1 shape, two streams, identical in both labels:

| Stream | Names | Rate | Purpose |
| --- | --- | --- | --- |
| forward | unique per repetition, `r<NN>-<seq>.bench.invalid` | 10 000 QPS | every query is a cache miss, so it drives `forward` |
| control | 100 pre-warmed `ctl.bench.invalid` names, long TTL | 1 000 QPS | drives `cache_hit`, the control arm |

Probe container: `strategy = "fallback"`, `timeout_ms = 800`,
`penalty_failures = 2` (unread under `fallback`),
`history.sample_interval_seconds = 30`, cache defaults, two healthy mock
upstreams. The production container is not stopped, reconfigured or restarted.

**This workload produces zero SWR activity, and therefore does not measure the
SWR component at all.** Forward names are unique and never re-queried, so no
entry is ever served stale; control names stay fresh. §S1-N lists "SWR attempts
and outcomes per repetition — the ~69 % the client metric misses" as a metric,
and under L.1 that metric is structurally zero. Whether the SWR path needs its
own arm therefore cannot be answered from an L.1 session; it is carried into
p2.6-11 as an open question, not reported as "no SWR variance observed".

### Metrics per repetition

`forward` p50/p99, `cache_hit` p99 (control), `forward` and `cache_hit` exact
means (`sum_seconds / count`), total upstream attempts, attempts per forward
`(Σ attempts − (swr.completed + swr.failed)) / cache_misses`, SWR attempts
(`completed + failed`) plus `enqueued`/`dropped`, server QPS, and
`cache.{entries,fresh,stale}` at T0.

The means are recorded because they are exact and the percentiles are not
(F1). They are **descriptive only** and do not enter the tier-3 decision.

### N per metric

Identical estimator for every metric. For K repetitions labelled `A,B,A,B,…`:

- `μ` = pooled mean of all K values, both labels.
- `D = { |a − b| / μ : a ∈ A-group, b ∈ B-group }`, `(K/2)²` cross pairs.
- **N = P95 of `D`**, type-7 linear interpolation.

Sign is meaningless in a null A/B, so the absolute value makes "half-width of
the interval containing 95 % of the pairwise deltas" well defined: the interval
is `[−N, +N]`. `max|d|` is reported beside N. At K = 8 the P95 estimate sits
near the second-largest pair; that is a stated limitation of the estimator and
is why the resolution-vs-K curve is reported.

### Control-arm drift and the invalidation rule

The same estimator on `cache_hit_p99` and on `cache_hit_mean`. The session is
**void** when `N_control > N_measured` on the *matching* statistic — p99 against
p99, mean against mean, never mixed.

### Phase-effect guard

Least-squares slope of each metric against repetition index, as a percentage of
`μ`. Flagged when `|trend| > N`: a monotone trend wider than the band it is
supposed to sit inside means the alternation did not absorb the drift.

### Resolution vs K

N recomputed from the first *k* repetitions only, `k = 4, 6, 8, … K`. Per
§S1-N, if K = 12 still leaves N wide the answer is to drop tier 3, not to run
more repetitions.

### Tier-3 decision — fixed order, no judgment

1. Total upstream attempts, if its N ≤ 10 % — carries tier 3.
2. Else `forward` p99, if its N ≤ 10 % — carries tier 3.
3. Else tier 3 is dropped, with both N stated.

Threshold on the chosen metric = `max(2 × N, 5 %)`. The order and the
acceptance rule are unchanged by this task.

### Probe container versus RouterOS

| Source | What it provides |
| --- | --- |
| Probe container API (read-only GETs) | every counter, percentile and cache figure |
| Load generator's own report | offered and achieved rate, loss — the authority on QPS |
| RouterOS (read-only, owner-run) | session bookkeeping only: `/system/resource/print`, `/container/print detail`, `/log print` for probe start and identity |

No RouterOS figure scales any result. `cpu-frequency` and `scaling_cur_freq`
are never used to calibrate ([measurement-traps.md](../../measurement-traps.md)
§Calibration).

## Findings

### F1 · Major · `forward` p99 is quantized below any resolution the gate needs

`quantile()` returns a bucket **bound**, never an interpolated value
([snapshot.rs:124-138](../../../crates/fah-metrics/src/snapshot.rs#L124-L138)),
over the eleven bounds at
[histogram.rs:17-19](../../../crates/fah-metrics/src/histogram.rs#L17-L19):
`0.1 · 0.25 · 0.5 · 0.75 · 1 · 2.5 · 5 · 10 · 25 · 50 · 100 ms`, saturating at
100 ms. In the region a real `forward` p99 occupies the grid step is 2.0–2.5×.

*Measured:* 17 perf rows produced four distinct `forward_p99` values; every
repetition's median was 10.0, giving N = 0.00 %, while the exact means over the
same windows spread ~6 %. The next value `forward_p99` can express above 10.0 is
25.0 — a +150 % step.

*Impact:* N = 0 on this metric is a quantization artefact, not a quiet harness.
The freezing rule would derive `max(2 × 0, 5 %) = 5 %` on a metric whose
smallest representable change is +150 %, producing a gate that cannot fail for
any reason short of a doubling. Worse, the `N ≤ 10 %` adequacy test cannot
distinguish "quiet" from "quantized" — a fully quantized metric scores best.

*Disposition:* **not fixed, and the S1-G2 acceptance rule is deliberately left
unchanged.** `forward` p99 stays in the metric order and stays reported; it is
recorded as **descriptive only** and is not a credible tier-3 carrier. Total
upstream attempts remains the first eligible metric by the existing fixed order,
which is unaffected. Substituting mean latency was considered and **rejected** —
it would rewrite the benchmark methodology to preserve a timing gate.

*Evidence class:* measured on the dev box; the bucket grid is a property of the
binary and carries to the RB5009.

### F2 · Major · The `cache_hit` control arm cannot move at p99 resolution

`cache_hit` runs at ~5 µs mean, which lands in the first bucket (`0.1 ms`) and
stays there. It read `0.1` in 17 of 17 perf rows.

*Impact:* the invalidation rule — "if `cache_hit` moved more than `forward`, the
box drifted and the session is void" — can only fire if `cache_hit` crosses a
bucket boundary, which at this stage requires a ≥ 2.5× real move. The session's
stated drift protection does not exist at p99 resolution. A session could drift
badly and still read `N_control = 0.00 %`.

*Impact if left unchanged:* the void rule reads as protection that was never
exercised. [measurement-traps.md](../../measurement-traps.md) §Carry a control
arm is explicit that a caveat on a weak comparison is not a substitute for a
control arm; a frozen control arm is a weaker instrument than the caveat.

*Disposition:* deferred, reported. The exact `cache_hit` mean is collected
alongside and does move (N = 8.50 % on the dry run, dominated by the warm-up
repetition), so the drift question is answerable from the raw data even though
the rule as written cannot fire.

### F3 · Major · The on-device harness S1-N requires does not exist

Missing: the probe container image, an on-device DNS load generator, on-device
mock upstreams, and an enabled `veth`. `veth3` is disabled with no container
attached ([routeros-traps.md](../../routeros-traps.md) §Topology).

*Impact:* S1-N cannot run. The same harness gates S1-L L.1, L.2, L.4a and L.4b,
so this blocks p2.6-11 as well as p2.6-10.

*Disposition:* **blocker, out of scope for this task**, which is defined as no
code and no repository change. It belongs to a separate prerequisite task shared
by p2.6-10 and p2.6-11, covering the probe-container build and ship, the load
generator, the mock upstreams and the veth setup, with every router command
proposed and owner-run. That task has not been created — it needs the owner's
approval first.

### F4 · Major · `upstreams[].attempts` and `counters.swr.*` lag live traffic

Both reach the metrics registry through the binary's 10 s telemetry poll
([main.rs:697](../../../crates/fastadhunter/src/main.rs#L697)); only
`latency.*` and `counters.dns.*` are live.

*Measured:* a snapshot taken during load read 400 attempts against 1 100
completed forwards, and settled at 1 102 once traffic stopped.

*Impact:* a T1 snapshot taken at load stop undercounts attempts and SWR by up to
one poll interval of traffic — at 10 000 QPS, up to ~100 k attempts on a ~6 M
total. That error is sampling artefact, not harness noise, and it would land on
the metric the fixed order selects first.

*Disposition:* **fixed in the protocol**, not in code — a 30 s quiet drain
between load stop and T1, with the load window recorded separately so perf rows
are not diluted by the drain. Verified in the dry run: attempts/forward read
exactly 1.0000 in all four repetitions.

### F5 · Minor · Benchmarks §S1-L sources percentiles from the wrong endpoint

[benchmarks §S1-L](../../design/adaptive-upstream-selection-benchmarks.md) line
504 reads "`forward`-stage p50/p99 from `/api/v1/telemetry`". `/telemetry`
carries only `{count, sum_seconds}` per stage; percentiles exist only on
`/api/v1/history/perf`, and [API.md](../../../API.md) line 63 confirms there is
no Prometheus surface, so raw buckets are exposed nowhere.

*Impact:* an implementer following the doc literally finds no percentile and
either invents one or reports the mean as a percentile.

*Disposition:* deferred. Documentation edits need the owner's approval at
execution time; none is made here.

### F6 · Minor · §S1-N's workload references a load that never ran

§S1-N pins the L.1 workload to "whatever served p2.5-09's on-device forward
load — the same tool and the same host". p2.5-09 ran no on-device forward load;
its on-device work was the V4 list drill and the V6 memory soak
([p2.5-09-phase-verification-review.md](../phase2.5/p2.5-09-phase-verification-review.md)).
[p1-11-review.md](../phase1/p1-11-review.md) line 600 records that throughput was
never measured for want of a generator.

*Impact:* the plan file's open item — "if p2.5-09 used a different tool or QPS,
the run plan says which one it reuses and why" — has no answer. The tool must be
chosen and frozen by the prerequisite task in F3, not inherited.

*Disposition:* deferred to the F3 task.

### F7 · Minor · The L.1 workload measures no SWR activity

Forward names are unique per repetition and never re-queried, so no entry is
served stale; control names stay fresh. SWR deltas were 0 in all three
steady-state repetitions. The 1 000 SWR attempts in repetition 1 came from
short-TTL entries left by an earlier smoke test, which is also why that
repetition's cache held 1 100 entries at T0 against 10 000 for the rest, and why
its mean latency reads 2.617 ms against ~1.6 ms.

*Impact:* §S1-N lists SWR attempts among its metrics and §S1-G2 names "whether
the SWR path needs its own arm" as a dimension to validate. Under L.1 both are
structurally zero, so an L.1 session cannot answer either. Reporting "no SWR
variance observed" from such a session would be a false negative.

*Disposition:* stated in the protocol above. The SWR arm question carries into
p2.6-11 unanswered. Repetition 1's behaviour is also the direct evidence for the
pre-declared warm-up repetition.

### F8 · Minor · Total upstream attempts is capacity-only under an open-loop generator

With a fixed offered rate, total attempts is an input, not an output: its N
measures the generator's rate stability. It moves only when the resolver drops
queries.

*Measured:* N = 0.02 % on the dry run, against a generator holding 2 200 QPS
with zero loss.

*Impact:* this is coherent with tier 3's stated role as a *gross-regression*
check, and the fixed order is not changed. But the metric is blind to a
regression that makes the resolver slower while it still keeps up, and any
result carrying tier 3 on it must say so rather than implying latency coverage.

*Disposition:* reported, carried into the result of the on-device session.

### F9 · Minor · Production sampling cadence is too coarse for a 10-minute repetition

The production container samples every 360 s (159 samples over 15.81 h,
p2.5-09), against a compiled default of 60 s. At 360 s a 600 s repetition yields
one or two perf rows.

*Impact:* per-repetition percentiles would rest on one or two intervals.

*Disposition:* the probe container carries its own
`history.sample_interval_seconds = 30`, set in the protocol above. No production
change is proposed. The dry run confirms 30 s yields 4–5 rows per 120 s window.

### F10 · Nitpick · Plan file and spec disagree on the tier-3 candidate set

The plan file lists `attempts_per_forward` among the tier-3 candidates; the
spec's fixed order names only total upstream attempts and `forward` p99.

*Disposition:* the spec governs. `attempts_per_forward` is reported and is not
eligible. Noted so a later reader does not treat the plan file as the rule.

## Status

**BLOCKED.**

The protocol is frozen and validated: the dry run passed all six required
plumbing checks and produced three corrections that are now part of the
procedure. `forward` p99 is established as non-resolvable at the current
histogram resolution and is descriptive only; total upstream attempts remains
the first eligible tier-3 metric under the unchanged S1-G2 fixed order.

The on-device K ≥ 6 session has **not** run and is blocked on F3 — the probe
container, load generator, on-device mock upstreams and veth setup, which are a
separate prerequisite task shared with p2.6-11 and await the owner's approval.
No N is frozen and S1-G2 tier 3 carries no threshold until that session runs.

No repository code, configuration, test or documentation was modified by this
task. Nothing was executed on the RB5009.
