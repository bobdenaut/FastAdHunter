### L.1s — the SWR arm

L.1 produces **zero** SWR activity by construction: its forward names are
unique and never re-queried, so no entry is ever hit while stale. Its `swr.*`
zeroes are therefore a property of the workload, and no statement about SWR
safety may be inferred from them. B.8 (`p2.6-09`) exercised the path in-process
at 100 stale keys against a black-holed endpoint; it says nothing about
on-device behaviour at load. L.1s exists to close that gap, and only that gap.

| Item | Declared value |
| --- | --- |
| Container | The probe container `fah-probe`, started through the `p2.6-13` procedure. Production untouched |
| Arms | `adaptive` and `fallback`, alternating, same session, no restart between repetitions |
| K | **6 repetitions** (3 per arm) plus one discarded warm-up |
| Duration | **300 s** of load per repetition, not 600 s. Every L.1s criterion is an exact count or an exact identity, not a percentile, so the extra 300 s buys no resolution |
| Protocol | The frozen `p2.6-10` repetition, unchanged, including the 30 s quiet drain |
| Offered load | **500 QPS over a recurring 6 000-name set + 1 000 QPS control names.** No unique-name flood — see the amendment below |
| Why those numbers | The mock forward zone's TTL is 5 s and the probe runs `min_ttl_seconds = 0`, so answers expire on schedule. At 500 QPS over 6 000 names each name is re-queried every 12 s, past expiry, so every hit after the first serves stale and enqueues a refresh. Steady-state refresh rate ≈ 500/s. The working set of 6 000 sits below `max_entries = 10 000`, so nothing is evicted before it can go stale |

**Amendment, made before the first L.1s run (2026-08-25).** The declaration
first said 9 500 QPS of unique forward names *plus* the recurring set, totalling
11 000 QPS. That is structurally incapable of measuring SWR: the probe's cache
holds **10 000 entries**, so 9 500 unique names per second evict the whole cache
roughly once a second, and a name re-queried every 12 s is always gone before it
can go stale. The arm would have reported `swr.* == 0` — the same zeros L.1
produces — and the precondition `swr.completed > 0` would have failed for a
reason having nothing to do with SWR.

Found by reading the probe's live `dns.cache` settings while setting the arm up,
before any measurement. The unique-name stream is dropped; the control stream
stays. The owner agreed to the amendment before the first run. Recorded here for
the same reason as the M.8 correction: a declaration that can be quietly edited
is not a declaration.
| Calibration | **One 120 s calibration repetition `C`, discarded, declared discarded here and reported anyway.** `swr_workers = 3` has a finite refresh throughput and the enqueue rate above is an estimate, not a measurement. `C` measures the achieved refresh rate and whether `swr.dropped` moves |
| Rule after `C` | Mechanical, declared now so it is not a judgment call later: if `C` shows `swr.dropped == 0`, the measured repetitions run at the declared rate. If `C` shows `swr.dropped > 0`, the SWR generator's rate is set to **60 % of the enqueue rate at which `C` first dropped**, that saturation figure is reported as a finding about `swr_workers = 3`, and the measured repetitions run at the reduced rate. The client and control rates never change |
| Reported per repetition | `swr.enqueued`, `swr.completed`, `swr.failed`, `swr.dropped`, `upstreams[].attempts` per endpoint, `cache` hits / misses / stale hits, the client-visible `forward` count, `penalties`, `probes` |
| SWR vs client separation | Through the identity `Σ attempts − (swr.completed + swr.failed) == cache_misses`. Client-visible forwards are the `forward` stage count; SWR upstream work is the `swr.completed + swr.failed` term. L.1 never exercised that subtraction because both terms were 0 |

**Does SWR need its own acceptance criterion?** Yes — decided here, before the
measurement. The tier 2 rows `swr.failed == 0` and `swr.dropped == 0` already
exist in the spec but are vacuous under L.1, where nothing enqueues. Passing
them on zeroes is not evidence. L.1s therefore carries its own table, and the
arm reports **no result at all** unless `swr.completed > 0`.

| L.1s row | Type | Criterion |
| --- | --- | --- |
| `swr.completed > 0` | Precondition | Below it the arm did not exercise SWR and reports nothing |
| `swr.failed` | Pass/fail | `== 0` in both arms — the mocks never fail |
| `swr.dropped` | Pass/fail | `== 0` in both arms at the rate fixed by `C` |
| Attempts identity | Pass/fail | `(Σ attempts − (swr.completed + swr.failed)) / cache_misses == 1.000` in both arms |
| `penalties`, `probes` | Pass/fail | Deltas `== 0` on the `adaptive` arm. Refresh traffic against healthy mocks must neither penalize an endpoint nor claim a probe |
| Queue residue | Bounded report | `swr.enqueued ≥ completed + failed + dropped`; the residue is stated, not gated |
| SWR share of attempts | Descriptive | Stated beside the 69.1 % deployed attribution. L.1s is not built to reproduce that share |

**L.1s counts are not pooled into tier 3.** It is a different workload from
L.1, and the 5.00 % threshold and the metric order stay exactly as `p2.6-10`
froze them. L.1s carries no timing gate.

### A trap that must be settled before the opt-in

The production container and the probe container **share the envlist
`fah-env`**. Adding `FAH__DNS__UPSTREAMS__STRATEGY=adaptive` to `fah-env` would
flip *both*, silently turning every future `fallback` arm (L.2, the tier-3
control) into a second `adaptive` arm. The opt-in therefore goes in a **second,
production-only envlist**, and the probe's `envlists` is left untouched.

### Step 3 — build and ship (dev box)

QEMU must be re-registered after any Docker Desktop restart, and the builder
container restarted afterwards — `buildx inspect --bootstrap` alone does not
refresh the platform list.

**Deviation, 2026-08-25:** `buildx_buildkit_fah-builder0` no longer exists on
the dev box — `docker restart` returns `No such container`. The named builder
`routeros-traps.md` describes was lost to a Docker Desktop reset at some point,
and with it its build cache. `docker buildx ls` shows `desktop-linux` already
carrying `linux/arm64`, so the build runs there. The consequence is a cold
QEMU-emulated build, not a different artefact.

```sh
docker run --privileged --rm tonistiigi/binfmt --install arm64

docker buildx build \
  --platform linux/arm64 \
  -t fastadhunter:0.2.20 \
  -o type=docker,dest=fastadhunter-arm64-0.2.20.tar \
  .
```

**Then check the layout — not optional.** With the containerd image store on
(the Docker Desktop default) `-o type=docker` still emits OCI, which RouterOS
cannot follow: it hangs at `status=extracting` forever with `OS` and `Arch`
blank, and reports no error. A `manifest.json` in the listing does not mean
legacy; judge by where the layers live:

```sh
tar -xOf fastadhunter-arm64-0.2.20.tar manifest.json
```

`"Layers":["blobs/sha256/…"]` → OCI, convert. `"Layers":["<hash>.tar"]` →
already legacy, skip the conversion.

```sh
docker run --rm -v "$PWD:/work" quay.io/skopeo/stable copy --insecure-policy \
  oci-archive:/work/fastadhunter-arm64-0.2.20.tar \
  docker-archive:/work/fastadhunter-rosready-0.2.20.tar:fastadhunter:0.2.20

ls -lh fastadhunter-rosready-0.2.20.tar
```

Expect ~12 MB — legacy layers are uncompressed. Budget is ≤ 30 MB.

### Step 4 — deploy the binary, still under `fallback`

S1.14 order: binary first, config second. **Add-first, chosen by the owner.**
The old container is kept, stopped, until the new binary has proved itself —
which is what makes the rollback in Step 6 a few seconds rather than a
re-extraction.

The new container gets its own `root-dir` and a comment that is **not**
`fastadhunter`: `[find comment="fastadhunter"]` is exact equality and would
otherwise match both. RouterOS auto-suffixes the derived name, so the shared
image tar causes no collision.

Every field below is copied from Step 1's `print detail`, with three deliberate
differences: `root-dir`, `start-on-boot` and `comment`.

```routeros
/container/add file=kingston/fastadhunter-rosready-0.2.20.tar interface=veth1 \
  root-dir=/kingston/fastadhunter/root-0220 mountlists=fah-config,fah-data \
  envlists=fah-env workdir=/home/nonroot start-on-boot=no logging=yes \
  comment="fah-next"
```

`shm-size`, `stop-signal`, `stop-time`, `cpu-list`, `memory-high` and
`auto-restart-interval` are left unset because production runs them at their
defaults. `memory-high` stays **unlimited** — a value there once OOM-killed the
live resolver.

Wait for extraction to finish before stopping anything — `status=extracting`
that never becomes `stopped` is the OCI-layout failure from Step 3, and the
old container must keep serving if it appears:

```routeros
/container/print where comment="fah-next"
```

Only once it reads `status=stopped`:

```routeros
/container/stop [find comment="fastadhunter"]
/container/start [find comment="fah-next"]
```

Both containers use the same `fah-config`/`fah-data` mount lists and only one
runs at a time. The comment swap and the removal of the old container happen
**after the soak decides**, not now — until then `comment="fastadhunter"` still
names the 0.2.19 container, and every `[find comment="fastadhunter"]` in an
older runbook points at the stopped one.

Runs immediately after Step 4b passes, before the opt-in. `fah-next` was added

`fah-next` carries `image-id=5845c30a7135…`, which is the config blob sha256

### Naming from this point on

The old container **keeps** `comment="fastadhunter"` for the whole soak — a
rename buys nothing and costs a step that can fail. The consequence is a
selector trap, and it is the reason the rule below is absolute rather than a
preference:

> From Step 4 onward, every soak, verification and rollback command targets the
> live container as **`[find comment="fah-next"]`**. `[find
> comment="fastadhunter"]` now resolves to the **stopped 0.2.19 rollback
> target**, and any older runbook line carrying it is pointing at the wrong
> container.

The comment swap happens only in the post-soak cleanup, once the old container
is removed and the selector is unambiguous again.

### Step 5 — the opt-in, as a separate change

### Step 6 — rollback to 0.2.19

**The config edit comes first and is mandatory.** The 0.2.20 binary serializes
every field, so first boot and any `POST /api/v1/config` write
`penalty_failures = 2` into `/config/fastadhunter.toml`. 0.2.19 rejects that key
under `serde(deny_unknown_fields)` and **will not boot** — the same failure that
killed the first probe container in `p2.6-13`.

Add-first makes this cheap: the 0.2.19 container is still present, still
`comment="fastadhunter"`, already extracted, merely stopped. No re-add, no tar,
no extraction wait.

1. Fetch `/kingston/fastadhunter/config/fastadhunter.toml` by `scp` (RouterOS
   `/file get` cannot edit it) and check whether `penalty_failures` is in it.
   If the key is there, delete the line and write the file back. Both transfers
   are owner-run.

   **Checked 2026-08-25, after the 0.2.20 boot: the key is NOT present.** The
   file still reads `strategy = "fallback"` / `timeout_ms = 800` with nothing
   appended. 0.2.20 writes the key only on first-boot generation — which did
   not happen, the file already existed — or on a `POST /api/v1/config`, which
   nothing has issued. **Rollback is currently a two-command operation with no
   config edit.**

   This is a property of the current state, not of the build, and it can change
   without anyone intending it: **any** `POST /api/v1/config` during the soak —
   from the dashboard, from a script, from `tui-monitor` if it ever writes —
   rewrites the whole file and arms the trap silently. The check is therefore
   repeated immediately before any rollback, never inherited from this reading.
2. Then:

```routeros
/container/stop [find comment="fah-next"]
/container/set [find comment="fastadhunter"] start-on-boot=yes
/container/set [find comment="fah-next"] start-on-boot=no
/container/start [find comment="fastadhunter"]
```

The two `set` lines undo Step 4c and are **part of the rollback, not a
follow-up**. Leaving them out produces a resolver that works until the next
reboot and then does not come back — the failure Step 4c exists to prevent,
reintroduced by rolling back without reversing it.

The old container never carried `fah-optin`, so nothing has to be unset. If the
config file was left carrying `penalty_failures`, 0.2.19 does not boot — it
exits at config parse with `unknown field 'penalty_failures'`, exactly as the
first probe container did in `p2.6-13`. That is the whole reason step 1 comes
first.

Only after the soak has decided, and never during it, the cleanup:

```routeros
/container/remove [find comment="fastadhunter"]
/container/set [find comment="fah-next"] comment="fastadhunter"
```

`start-on-boot` is not touched here — Step 4c already moved it to `fah-next`.
The removal comes first so that the rename cannot briefly leave two containers
answering to `comment="fastadhunter"`.

### What "rollback verified" can and cannot mean here

Verifying the rollback by executing it costs a second DNS outage on the
household resolver for no measurement gain. What is verified instead, before
the soak starts, is every precondition it depends on:

| Precondition | How it is checked |
| --- | --- |
| The 0.2.19 container still exists, stopped, with its `root-dir` intact | `/container/print detail where comment="fastadhunter"` after Step 4 |
| The 0.2.19 tar is still on the store — the fallback to the fallback, if that container is ever removed | **Confirmed**, `kingston/fastadhunter-arm64-0.2.19.tar`, 13.1 MiB |
| Whether the live config actually contains `penalty_failures` | **Checked after the 0.2.20 boot — absent.** Re-checked before any actual rollback, because a single `POST /api/v1/config` re-arms it |
| 0.2.19 rejects that file, and accepts it once the line is gone | Reproduced **on the dev box** against the 0.2.19 binary, not on the router |

Stated as a limit, not as a pass: the rollback path is verified by
precondition, and has not been executed end to end on the device. Executing it
would cost a second outage on the household resolver and produce no
measurement.

**Concurrency caveat, carried verbatim from the spec:** concurrent queries can
split one upstream outage across several short runs, so observed run lengths are
a **lower bound** on real clustering. Two length-1 runs are consistent with two
isolated losses and equally consistent with one clustered event split by
concurrency.

### Decision

**`penalty_failures` cannot be frozen from this data. The window must extend.**

Two closed runs cannot distinguish "this deployment produces only isolated
single losses" from "the sample is far too small". The spec is explicit that too
few closed runs means extend the window rather than guess the constant, so
`penalty_failures` stays at its compiled default of **2**, provisional and
unvalidated.

Sizing the extension from the measured rate: 0.0050 % over ~1 000 primary
attempts/hour is roughly one failure per 20 h. Distinguishing "no runs of ≥ 2
exist" from "too few events" needs on the order of 15–20 closed runs — **12 to
17 days** of `fallback` traffic at the current volume, not days already served.

**This collides with the opt-in flip.** Samples taken after the flip are a
different quantity — under `adaptive` attempts are throttled and exclude
`resolve_host` (spec S1.8) — and are explicitly not pooled with the `fallback`
window. The flip therefore **closes the S1-G4 window permanently at 2 closed
runs**.

**Owner decision, 2026-08-25: flip now, with S1-G4 explicitly not validated.**
The alternative — holding `fallback` for another 12–17 days — was put and
declined. The consequences are accepted rather than absorbed:

- `penalty_failures = 2` is a **provisional, empirically uncalibrated**
  compiled default. No measurement in this phase supports or refutes it.
- S1-G5 route 2 **stays open** and is not decidable from this deployment's data.
- The `fallback` run-length window closes at 2 closed runs, both length 1, and
  is not reopenable without reverting the strategy.

Segment 03 is captured immediately before the opt-in restart, so the `fallback`
window closes on a recorded boundary rather than losing its tail the way
segment 02 did.

### Why the two failure rates are not comparable

Suite T's 0.072 % and this window's 0.0050 % are both `failures / attempts` on
`1.1.1.1`, but the attempts are not the same population. Upstream traffic
composition, measured on the production container:

| Class | Suite T, 0.2.16, 45.7 h | 0.2.20, 8.7 h snapshot |
| --- | --- | --- |
| SWR refreshes | 69.1 % | **47.0 %** |
| `resolve_host` | 20.1 % | **36.5 %** |
| Client forwards | 10.3 % | **16.4 %** |

Total volume is nearly identical — 913 attempts/h then, 929/h now — so the
change is in the mix, not the load.

**This is a conclusion, not a defect in either measurement.** Neither figure is
wrong; they are rates over differently composed denominators, and pooling or
comparing them directly is a category error. The spec's "base rate documented —
0.072 % primary" should be read as scoped to suite T's composition.

What it does **not** establish: that the composition shift *causes* the 15×
difference. Telemetry carries no per-class failure attribution — by design
(S1.12), which is why B.8 exists to measure SWR-vs-client probe attribution
in-process — so the failures cannot be assigned to the class that shrank. The
mechanism is plausible and unproven.

Two limits on the table itself: it is an 8.7 h snapshot against a 45.7 h window,
and `resolve_host` is dominated by blocklist refreshes, which are bursty on
12–48 h schedules, so its share moves with sampling time.

Ruled out as explanations: `timeout_ms` is unchanged since phase 0
(`git log -S`), and p2.5-05 added event fields without touching
`upstreams[].failures` semantics.
