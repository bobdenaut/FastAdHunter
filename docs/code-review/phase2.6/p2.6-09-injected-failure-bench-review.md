### Decisions

- **Paying is split three ways, not two.** `non_probe_paying_first` (paid and
  attempted endpoint 0), `probe_paying` (carried a probe), `stalled` (paid but
  never touched endpoint 0 — host noise, not upstream tax). Only the first two
  feed the net-cost formula.
- **`adaptive_paying` excludes probe carriers** (S1-G3). The double-subtraction
  it prevents is 1 attempt bound per failed probe.
- **Measured net cost uses one shared baseline** — the adaptive arm's
  `healthy_p50_ms` — because the `fallback` arm has no non-paying queries and
  therefore no baseline of its own.
- **`dead_hold` = one leg.** The mock holds a black-holed request outstanding
  exactly as long as the client waits, so the high-water mark measures
  concurrency rather than cumulative arrivals.
- **Long arms are `#[ignore]`d** (B.1, B.5, B.7, B.8); B.2/B.3/B.4/B.6 run in
  `cargo test`.

### Critical

### Major

**F1 — FIXED (2026-08-24) — The suite silently depends on `--test-threads=1`;
nothing enforces or documents it.**
Every latency figure, the `paid()` classification at the 50 ms threshold, and
every assertion derived from them assume one arm runs at a time. `cargo test`
defaults to one thread per core, so the repo's own gate
(`cargo test --workspace`) runs B.2/B.3/B.4/B.6 concurrently with each other and
with the rest of the workspace's test binaries.
*Impact:* spurious failures that look like Stage 1 regressions, and — worse —
silently wrong latency numbers if an `#[ignore]`d arm is ever run without the
flag. *Fix before DONE.* Options: assert the thread count at suite start, or
move the timing-dependent arms behind a single `#[tokio::test]` entry point that
owns the ordering.

**F2 — FIXED (2026-08-24) — B.2's `attempts[0] == penalty_failures` assertion
encodes the DoT connect behaviour and will fail when that behaviour changes.**
Measured: the DoT path returns `TimedOut` after 60 ms against a closed TCP
port, so classification sees a soft failure and the endpoint is penalized after
`penalty_failures` attempts instead of 1. The assertion pinned that exactly
(`== penalty_failures`).
*Correction (2026-08-24):* the earlier rationale here — that
`timeout(attempt_timeout, connecting)` at `encrypted.rs:186-188` swallows the
refusal — is wrong. `timeout` propagates the inner `Err` unchanged; it only
manufactures `TimedOut` when the inner future has not resolved. What the runs
show is that hickory's DoT exchange does not surface `ECONNREFUSED` inside the
50 ms attempt bound, and `mux_timeout = attempt_timeout * 2`
(`encrypted.rs:159`) guarantees hickory's own connect timeout can never fire
first. Why the refusal is not reported earlier is not established by these
runs. The earlier "raw TCP refuses in 0.03 ms" figure is void — see F14.
*Impact:* the moment the connect path is corrected to surface `ECONNREFUSED`,
B.2 fails for `penalty_failures` 2 and 3 — a green-to-red flip caused by a fix.
*Fix before DONE:* assert `attempts[0] <= penalty_failures` and record which
classification fired, so both behaviours pass and the difference is reported.

**F3 — FIXED (2026-08-24) — B.5's `fallback` arm overruns its own script.**
The loop runs a fixed `count = script.total() / cadence` iterations with
`MissedTickBehavior::Delay`. Under `fallback` every black-hole-phase query pays
~80 ms against a 50 ms tick, so the loop falls behind ~30 ms per paying query.
At ratio 12.5 that is ~750 paying queries ⇒ ~22 s of drift against a 92 s
script.
*Impact:* the `fallback` arm's samples spill past the scripted end and are all
attributed to the last phase, so its per-phase latency split is not comparable
to the adaptive arm's. Phase attribution of individual samples stays correct
(it uses wall-clock), and no adaptive assertion is affected — adaptive queries
are ~15 ms and the tick governs. *Fix before DONE:* drive the loop until
`script.total()` has elapsed rather than for a fixed sample count.

**F4 — FIXED (2026-08-24) — B.4's "both endpoints probed" assertion is
timing-dependent and runs in the default gate.**
`probes[0] > 0 && probes[1] > 0` needs two 1.5 s penalty deadlines to expire
inside a 40-query run that takes ~4.4 s. B.4 is not `#[ignore]`d.
*Impact:* flakes under parallel test load, in the gate that is supposed to be
the stable signal. *Fix before DONE:* lengthen the run or gate the assertion on
elapsed wall-clock rather than on query count.

### Minor

**F5 — FIXED (2026-08-24) — `MockConfig::black_hole()`'s default `dead_hold` is
150 ms, not one leg.**
Every call site currently overrides it via `dead_mock()`, but the constructor is
public and the default silently inflates the outstanding-request high-water mark
for any future caller that forgets: at 20 QPS with a 50 ms client timeout, three
sequential requests overlap in a 150 ms hold window and the mark reads 3 when the
true concurrency is 1. *Fix before DONE* — make the default one leg, since the
knob's meaning is "how long the client waits".

**F6 — `non_probe_paying_first` and `stalled` silently mean "endpoint 0".**
The classification `sample.attempts[0] > 0` is only meaningful in arms where
endpoint 0 is the injected-failure endpoint (B.1, B.2, B.4, B.5, B.8). In B.3
and B.7 every query attempts endpoint 0, so a host stall is classified as
upstream tax. Neither arm reads those fields, so nothing is wrong today.
*Impact:* a future arm that reads them would get a wrong answer with no warning.
*Deferred* — rename to carry the endpoint, or take the failure-endpoint index as
a parameter.

**F7 — FIXED (2026-08-24) — Per-arm `non_probe_tax_ms` / `probe_tax_ms` still
use each arm's own baseline and are printed unqualified.**
For an arm with `healthy_n = 0` (any `fallback` outage arm) the printed "tax" is
absolute latency, not excess over baseline. The net-cost row no longer uses
these — it takes an explicit shared baseline — but the per-arm fields remain in
the output and read as if comparable. This is the same defect that corrupted the
measured net-cost row before it was fixed. *Fix before DONE:* print `n/a` when
`healthy_n == 0`.

**F8 — `net_avoided` has no assertion of any kind.**
It is computed and printed; nothing checks its inputs against their definitions.
`run_b1` does assert `probe_paying == probes[0]` and `probes[0] + 1 ==
penalties[0]`, which constrains two of the three inputs, but the formula itself
is unverified by the suite and must be re-derived by hand in the acceptance
audit. *Deferred by design* — an assertion here would only restate the code.
Recorded so the audit does not treat a green suite as evidence for the
economic figure.

### Nitpick

**F9 — `MockConfig` is cloned twice per mock** (once into the serving task,
once retained for `behaviour_now`). Harmless; the struct is small and mocks are
per-test.

**F10 — `Distribution::LogNormal` and `loss` are unused by every arm.** Both are
required by the benchmarks doc's five-knob harness contract, so they stay, but
they are untested code paths.

## Spec observations for the owner

**F11 — S1-G3's recovery criterion conflates two distinct guarantees.**
"Healthy within `PENALTY_MAX` + one query interval of the endpoint's return"
assumes the endpoint *stays* returned for a full window. B.5's script keeps it
up for 0.6 P, so at ratio 37.5 the probe fires inside a later dark window and
recovery is deferred by another window (measured, session 2: probe claimed at
38.4 s inside a 56.3 s budget; recovery at 109.7 s; `flap_probes=1`,
`penalty_rounds` shows the round-8 penalty landing in `flap_down_3`).
The suite now reports the two separately and marks that case
`recovery_criterion=deferred` with its reason. Not a Stage 1 failure.

**F12 — S1-G3's recovery bound is stated against nominal `PENALTY_MAX`, which
S1.6's own jitter can exceed.**
`penalty()` scales each deadline to 75–125 % of nominal. A deadline set just
before the endpoint returns can therefore legitimately fall at
`1.25 × PENALTY_MAX` after it. Measured, session 3, ratio 12.5: first probe at
21.304 s against a nominal 18.8 s budget — ratio 1.136, inside the jitter band.
The suite now asserts the jitter-aware bound and prints both verdicts
(`within_nominal`, `within_jittered`).
*Proposed to the owner as a spec-wording amendment; not applied.*

| Row | fallback_paying | adaptive_paying | failed_probes | derived |
| --- | --- | --- | --- | --- |
| Client forwards, bound | 10 000 | 2 | 11 | (10 000 − 2) × 150 − 11 × 150 = **1 498 050 ms** |

### Findings (new)

**F13 — FIXED (2026-08-24) — Major — B.2's UDP arm carried the defect already
fixed in the DoT arm.**
`run_b2_udp` asserted `report.paying() <= 1` — all payers, including a host
stall at the healthy endpoint. That is bug 6 in the table above, fixed for the
DoT arm and left in the Linux-only path, where it would have surfaced as a
false failure on the first stall. Inferred (the arm has never run — no Linux
session). Fixed: assert `non_probe_paying_first() <= 1` and report `stalled`;
`assert_answered` added, which the arm also lacked.

**F14 — FIXED (2026-08-24) — Major — `b2_refusal_probe`'s raw-TCP figure
measured nothing.**
The `Instant` started *after* the connect resolved, so `raw_tcp_elapsed_ms`
timed the `println!` argument evaluation. The "0.03 ms" in §What was run is
void, and it was the evidence F2 rested on. Fixed by starting the clock before
the connect. The `ConnectionRefused` *kind* remains valid; only the duration
was wrong.

**F15 — FIXED (2026-08-24) — The cache-hit-adjusted line is missing from the
results.** Written in §Acceptance audit → Net timeout cost avoided.
Plan step 4 requires the net-cost figure to be restated against the deployed
composition (spec §Upstream traffic composition: 10 % client forwards, 69 %
SWR) so the reader knows what fraction of client queries it touches. Neither
the suite nor §Net timeout cost avoided states it. Impact: the 1 498 050 ms
headline reads as if it applied to all client traffic. *Fix in the acceptance
audit* — it is arithmetic over numbers the suite already prints, not code.

**F16 — OPEN — Minor — B.5 contributes nothing to the net-cost rows.**

only B.1 feeds `net_avoided`. Impact: the client row rests on a single
scenario — a permanent black hole — and says nothing about the flapping case,

**F17 — FIXED (2026-08-24) — Minor — Time-to-penalize was reported in queries
only.**

### Instrumentation finding that shaped this session

**F22 — Windows timer quantum, and what it did to B.1.**
The mock's nominal 5 ms healthy latency measured **15.69 ms** (sessions 2–4).
Tokio does not raise the Windows timer resolution, so any `sleep` under one
quantum (~15.6 ms) rounds up; a 50 ms `timeout_ms` costs ~62.5 ms. Every arm's
healthy path was paying it, and the original session was therefore dominated by
the scheduling floor rather than the code under test. **The corrected healthy
p50 is 0.12 ms** (measured, session A) — that is the figure to treat as real.

The correction had a consequence the first pass did not anticipate.
Benchmarks doc §S1-B derives B.1's window count from the run's *duration*:
"at 12.5 the run spans ~6 windows, at 2.5 ~13", and §what-justifies states
"a ~50 s scaled run". That ~50 s is 10 000 queries × 5 ms — **the mock latency
was B.1's pacing mechanism, not decoration.** Zeroing it collapsed B.1 to
~1.4 s, shorter than the first penalty deadline (1 500 ms nominal), so:

| B.1 arm (session A) | probes | penalties | tax-free share |
| --- | --- | --- | --- |
| adaptive pf=1 r=12.5 | 1 | 2 | 0.99990 |
| adaptive pf=2 r=12.5 | 0 | 1 | 1.00000 |
| adaptive pf=3 r=12.5 | 0 | 1 | 1.00000 |
| adaptive pf=2 r=2.5 | 0 | 1 | 1.00000 |
| adaptive pf=2 r=37.5 | 0 | 1 | 1.00000 |

Identical at every ratio, because no arm reached round 2 — the first window is
1 500 ms at *every* ratio, so a 1.4 s run cannot distinguish them. This is a
genuine instrumentation defect, not a Stage 1 result: it voids `failed_probes`
(hence `probe_cost`) and the per-ratio tax-free share, both named deliverables.
Session A's other seven arms are unaffected — B.5, B.7 and B.8 are time-scripted
or sleep-driven, B.2/B.3/B.4/B.6 are count-based.

*Remediation applied:* B.1 re-run with an explicit 5 ms query cadence — the
doc's own pacing, restored as an explicit knob instead of an accident of the
mock. Validated first at 1 % scale (100 queries, 80 ms cadence, 8.53 s):
`penalties=3 probes=2 failed_probes=2 tax_free_share=0.97959 round=3` — two
deadlines crossed, `probes + 1 == penalties`, and the only two payers after the
penalty are the two probe carriers. No other arm re-run.

*Measurement-environment detail, not a defect:* the prescribed workload is a
5 ms cadence (`cadence_ms=5` nominal). `tokio::time::interval(5ms)` is subject
to the same quantum, so the measured span is longer — `elapsed_ms=117533` for
10 000 queries, ~11.75 ms effective. The two figures are reported side by side
and never conflated.

This is **not** compared against the doc's "~50 s scaled run" as a pass/fail.
§S1-B's criterion is expressed in penalty windows and probe carriers, not in
wall clock; the ~50 s is descriptive of the same 5 ms workload on a host without
the quantum. A run that reaches *more* windows than the minimum does not
invalidate the arm — it produces more probe carriers, and the criterion
("only probe carriers pay, one per window") is evaluated against the window
count each ratio actually reached. The extra wall clock is Windows scheduling;
it never enters the G3 formula, which is counts × `attempt_bound_ms`.
The tax-free share is recomputed per ratio from that ratio's own counters —
never extrapolated from another arm.

### Net timeout cost avoided

Formula (benchmarks doc §S1-B metrics), inputs shown, rows kept separate:

```text
adaptive_paying = non-probe paying queries        (probe carriers excluded)
probe_cost      = failed_probes × attempt_bound_ms
net_avoided     = (fallback_paying − adaptive_paying) × attempt_bound_ms − probe_cost
```

`attempt_bound_ms = ATTEMPT_LEGS(3) × timeout_ms(50) = 150`.

| Row | fallback_paying | adaptive_paying | failed_probes | probe_cost | net_avoided |
| --- | --- | --- | --- | --- | --- |
| Client forwards (B.1, r=12.5, pf=2), bound | 10 000 | 2 | 8 | 1 200 ms | (10 000 − 2) × 150 − 1 200 = **1 498 500 ms** |
| Client forwards, measured (baseline 0.78 ms) | 10 000 | 2 | 8 | 450 ms | 599 001 − 114 − 450 = **598 437 ms** |
| SWR refreshes (B.8), bound | 100 | 0 | 2 | 300 ms | (100 − 0) × 150 − 300 = **14 700 ms** |

Re-derived by hand from the raw counters, not taken from the printed line:

- **Client, bound.** `fallback_paying` = `non_probe_paying_first` of the
  `fallback` arm = 10 000. `adaptive_paying` = `non_probe_paying_first` of the
  adaptive pf=2 r=12.5 arm = 2 (probe carriers excluded, per S1-G3).
  `failed_probes` = `probe_paying` = `probes[0]` = 8. Then
  9 998 × 150 = 1 499 700; 8 × 150 = 1 200; difference **1 498 500 ms**.
  Cross-check on `attempts[0]` = 10 = 2 non-probe + 8 probes — the two payer
  classes account for every attempt at the dead endpoint, with no remainder.
- **Client, measured.** Shared baseline = the adaptive arm's `healthy_p50_ms`
  (0.78 ms); the `fallback` arm has `healthy_n = 0` and therefore no baseline of
  its own. `fallback_tax` = Σ(paid − baseline) over 10 000 payers = 599 001 ms,
  which checks against 10 000 × (60.68 mean − 0.78) = 599 000. Subtracting the
  adaptive arm's 114 ms and the probe carriers' 450 ms gives **598 437 ms**.
- **SWR.** `fallback` attempts at the dead endpoint = 100; `adaptive` = 2, both
  of which are probes, so `adaptive_paying` = 2 − 2 = 0, `failed_probes` = 2.

**The bound row is ~2.5× the measured row** because `attempt_bound_ms` (150 ms,
three legs) is the worst case while these UDP mocks never truncate — one attempt
costs one leg. The measured row is the honest figure for this workload.

**Host timer distortion, stated not normalized away.** The measured row carries
the Windows quantum: a 50 ms `timeout_ms` costs ~60.7 ms here (measured
`paying_mean_ms`), so per-payer tax is overstated by roughly a fifth against a
host without the floor. **The bound row is unaffected** — it is counts ×
`attempt_bound_ms`, a constant. The extra benchmark wall clock (117–607 s per
arm) is likewise measurement environment only and never enters the formula.

**Cache-hit adjustment** (spec §Upstream traffic composition, 2026-08-16,
suite T sample 1, v0.2.16, 45.7 h): SWR refreshes **69.1 %** of upstream
attempts, `resolve_host` 20.1 %, client DNS forwards **10.3 %**. Consequences
for reading the rows above:

- The client row covers ~10 % of upstream attempts. Client forwards *are* cache
  misses by definition, so the figure never applies to a cache hit.
- The SWR row covers ~69 % — ~6.7× more attempts than the client row — but is
  background work, not client latency (ADR-0005). **The two rows are not
  additive and the raw aggregate is never client benefit.**
- `resolve_host`'s 20.1 % is excluded from both rows by design: S1.9 runs it in
  `Ignore` mode, confirmed measured in B.7 (`attempts=[0,0]`).
