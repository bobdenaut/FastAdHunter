# p1.5-04 — History Query API: implementation review

**Task:** [plan/wip/phase1.5/p1.5-04-history-query-api.md](../../plan/wip/phase1.5/p1.5-04-history-query-api.md)
· **Status:** DONE, gates GREEN · **Commit:** deferred (phase1.5 commits as one
batch).

`GET /api/v1/history/{summary,perf,top}` — the read side of what p1.5-01/02
persist, so a dashboard fetches ranges instead of parsing `/data/history`
itself. Bounded on both ends: a 90-day request costs the same memory as a
one-hour one.

## What was built

**`fah-model`** — the history *contract*, so the reader and the port describe
one thing rather than two structurally identical ones that can drift:
`HistoryPoint` (a bucket's counters + start `ts`), `HistoryRange`,
`HistoryResolution`, `HistorySeries`, `TopKind`, `TopItems`, `PerfSeries`. Pure
PODs, no logic (hard rule 2).

**`fah-stats`** — new `history/reader.rs`, a `HistoryReader` holding *paths
only* (no cursors, no cache, none of the writers' locks — a 90-day chart cannot
stall a flush). `Stats` gained `history_summary` / `history_perf` /
`history_top`. It:

- selects only the day-files whose calendar day intersects the range, then
  filters rows by their own `ts` against the half-open `[from, to)`;
- streams each file line by line, skipping rows that no longer parse (a torn
  final line after a power cut) — the writers' `boot` policy;
- sums the day's hourly rows for `resolution=day` (the hourly file is the only
  stored resolution; a daily chart is derived, not persisted twice);
- merges the daily top-N files by summing per key, ranking count-desc with the
  key breaking ties so the order is stable across calls.

**`fah-api`** — a new `HistorySource` port (kept separate from `StatsSource` on
purpose, see below), `AppState.history`, three handlers, and wire types with
`blocked_percent` derived at the boundary exactly like the cache view's
`load_percent`. The `from`/`to` RFC 3339 parser the query log already had was
lifted to a shared `timestamp_param`.

**Wiring** — one `StatsAdapter` now implements *two* ports over the same
`Arc<Stats>`; `main.rs` hands the same `Arc` to both builder fields.

## Three design calls worth flagging

**Blocking reads, one hop.** `HistorySource` is deliberately `std::fs` and
handlers wrap each call in `spawn_blocking`. `tokio::fs` *is* `spawn_blocking`
internally, per call — so an async reader would pay one thread hop per file
where this pays one for the whole multi-day scan. The cost is that the port
contract is "blocking and fallible", which is precisely why it is a separate
trait from `StatsSource`: that one promises cheap infallible in-RAM snapshots,
and folding a fallible file scan into it would have made the contract a lie.

**Decimation, not averaging.** A 90-day perf range is ~130k samples — far too
much to return, and too much to *hold* while shrinking (hard rule 4). The
`Decimator` keeps every `stride`-th row in a single pass and, whenever the
buffer would exceed the budget, halves it and doubles the stride; memory is
bounded by `max_points` regardless of range width. Every retained row is a
verbatim reading — averaging would smooth a latency spike into invisibility,
which is the one thing this series exists to show. The applied `stride` is
returned, because a silently sparse chart is a lying chart.

**Two point budgets.** `summary` defaults to 5000, which covers 90 days of
hourly points (2160) whole — the common chart is never thinned. `perf` defaults
to 1000 because a single day is already 1440 samples at the 60 s cadence, so
that series is decimated by default and says so. Different defaults for one
parameter name is a small wart; the alternative was either a silently thinned
90-day summary or a 50 MB perf response.

## Error handling, as the task specifies

- **Bad range → 400.** `from >= to` is rejected rather than answered empty: a
  window that *cannot* contain data is a request bug, and reporting it
  identically to a window that merely *has* none would leave a caller staring at
  an empty chart hunting for an outage. Same for a non-RFC-3339 timestamp, an
  unknown `resolution`/`kind`, a non-numeric `max_points`/`n`, and an unknown
  `?fields=` name (a typo must not silently drop the series a chart wanted).
- **Empty range → 200 with an empty `items`.** Including when nothing has ever
  been written — a missing `/data/history` directory reads as empty, not as an
  error.
- `n` and `max_points` are *clamped* to their ceilings, matching `limit` on
  `GET /api/v1/queries`.

## Honesty about what `/top` is

The merged ranking is an approximation of an approximation: each day-file
already holds only that day's top-N, so a domain that missed the daily cut-off
contributes nothing for that day, and a steadily-just-below-the-line domain can
rank under one that spiked into a single day. Documented in API.md and on the
reader — it answers "what dominated this week", not "the exact order".

## How the acceptance criteria are verified

Split along the layer boundary, since `fah-api` cannot import `fah-stats`:

- **`fah-stats::history::reader`** (fixture-seeded, real files) — hour and day
  resolution both correct (day sums counters *and* merges `per_type`), the
  half-open range excludes the hours outside it, an inverted/empty range reads
  nothing, perf samples read in order across day-files, a 1440-sample day
  decimates within a 100-point budget to an *evenly spaced* series whose step is
  `stride × 60 s`, top-N merges counts across days and honors `n` (with the
  newest name winning a client rename), an unparseable line is skipped, and the
  `Decimator` holds its budget and spacing for streams from 10 to 100 000 items.
- **`fah-api/tests/api.rs`** (real HTTPS, real routing) — the documented JSON
  shape at both resolutions with `blocked_percent` derived and `stride` echoed;
  the parsed range/resolution/budget actually reaching the port; the bare-call
  defaults (last 24h, hour, 5000); empty → `200` not `404` on all three;
  `400` + `bad_request` for eight bad-parameter cases; `fields` leaving keys
  **absent** rather than null; `kind=clients` shape; clamping to the ceilings;
  and all three routes added to the "every v1 route requires the key" sweep.

## Performance

Nothing on the per-query path — this is admin-plane read-only I/O on a blocking
thread, sharing no lock with the writers. Memory per request is bounded by
`max_points` (plus, for `resolution=day`, one entry per day-file on disk, which
retention bounds). No hot-path allocation, lock or new bench target, so no bench
was taken (consistent with the ~6× unpinned-criterion noise on this box).
