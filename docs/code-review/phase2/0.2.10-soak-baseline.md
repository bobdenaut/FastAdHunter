## Why this soak exists

Two tasks close on it.

- **p2-08** — phase verification: HTTP budgets hold on-device, no DNS
  regression, RAM ceiling confirmed rather than assumed.
- **p2-07** — `AWAITING SOAK`. Flips to `DONE` when the persisted series proves
  the instrument works: a residual per sample across the whole window, a row
  agreeing with a live `/debug/memory` read at the same instant, and the slope
  over the final third **stated**. A *drifting* residual still flips it — the
  instrument worked — and opens a leak task.

> **Leak = residual growing while the named components stay flat.**
> Growth in a *component* is that structure filling toward its cap, not a leak.

**This is the first soak where the series is pulled from the device's own
history.** Previous runs reconstructed the curve with an external curl loop; the
point of p2-07 is that the router samples and persists it itself, so one request
at the end returns the whole window.

## What changed vs the 0.2.9 soak

as a regression.

| | 0.2.9 | 0.2.10 |

The question is whether it flattens, not where it flattens.

## Confounds to remember

- **`auto-restart-interval=none`.** Nothing restarts FAH if it dies, and over a
  night a silent death looks identical to a quiet period. The container log's
  start time is the authority — one `*** start` line, or the window is invalid.
- **postgres shares the 1 GB** (~49 MiB, `memory-high=unlimited`). Router-wide
  memory is not a FAH measurement; attribute per-cgroup before blaming FAH.
- **Most traffic is HTTPS.** Phase 2 filters only the unencrypted remainder, so
  a low `kind=http` count is the web being HTTPS, not the proxy failing. The nat
  counter distinguishes the two.
- **The dst-nat rule skips private destinations** (`fah-http-skip`), so LAN-to-LAN
  HTTP never appears in the query log by design.
- **HTTP interception is IPv4-only — see the known gap below.** Any host the
  client reaches over IPv6 is absent from the HTTP numbers entirely.
- **DNS blocking preempts HTTP filtering.** A domain blocked at DNS resolves to
  `0.0.0.0`, so the client never opens a socket and the request never reaches
  the proxy. Blocked ad domains therefore do **not** appear in the HTTP log;
  looking for them there and finding nothing is not evidence of a defect.
- **WireGuard clients are not intercepted** — rule 10 is `in-interface-list=LAN`
  only. Their traffic is in the DNS numbers but not the HTTP ones.
- **RouterOS CPU-frequency fields are not a calibration input**
  (`docs/measurement-traps.md`). The ~9× x86 → RB5009 factor is the reference.
- **A first list refresh may land inside the window** and briefly double
  ruleset memory during the swap. Check refresh timestamps before calling a step
  in RSS a leak.

## Known gap — HTTP interception is IPv4-only

Found 2026-08-02 while verifying the proxy on the live router. **Deliberately
not fixed during the soak**: a mid-window config change would give any step in
the series two candidate explanations, which is the ambiguity the soak exists to
remove. Apply after the window closes, together with the generated-load run.

Evidence — same three requests, three outcomes:

| Request | Connected to | Reached the proxy |
| --- | --- | --- |
| `httpforever.com` (default) | `2606:4700:3031::6815:4d2` | **no** |
| `httpforever.com` forced `-4` | `172.67.132.115` | yes |
| `http.badssl.com` (IPv4-only host) | `104.154.89.105` | yes |

The dst-nat rule lives in `/ip/firewall/nat`; there is no `/ipv6/firewall/nat`
equivalent. DNS *does* have IPv6 coverage (two dstnat rules forcing all IPv6
`:53`), so the gap is specific to HTTP.

**The proxy fetches origins over IPv4 regardless**, because `resolve_host`
returns A before AAAA deliberately and the proxy takes the first address passing
the egress check. So the container's lack of global IPv6 does not block this —
clients reach the proxy over v6, the proxy reaches origins over v4.

Rules to apply (mirroring the existing DNS v6 dstnat; skip-list first):

```routeros
/ipv6/firewall/address-list/add list=fah-http-skip6 address=fd6c:7f32:8e91::/48
/ipv6/firewall/address-list/add list=fah-http-skip6 address=2a02:2f04:5100:e700::/64
/ipv6/firewall/address-list/add list=fah-http-skip6 address=fe80::/10
/ipv6/firewall/address-list/add list=fah-http-skip6 address=::1/128

/ipv6/firewall/nat/add chain=dstnat action=accept protocol=tcp dst-port=80 \
  dst-address-list=fah-http-skip6 \
  comment="fastadhunter http v6: leave local traffic alone"

/ipv6/firewall/nat/add chain=dstnat action=dst-nat protocol=tcp dst-port=80 \
  in-interface=BRIDGE dst-address=!fd6c:7f32:8e91:1::2/128 \
  to-address=fd6c:7f32:8e91:1::2/128 to-ports=8080 \
  comment="fastadhunter http v6"
```

The LAN's **global** `/64` must be in the skip list, not just the ULA — unlike
IPv4 there is no private-range shorthand that covers it.

Two open points:

1. **`to-ports` on IPv6 dstnat is unverified.** The existing DNS rules are 53→53
   and do not use it. If RouterOS rejects it, move the listener to port 80
   (`FAH__HTTP__LISTEN__PORT=80`, restart) and drop `to-ports` from both the v4
   and v6 rules — ADR-0004 already permits binding 80.
2. **IPv6-only origins stay unreachable.** The container has a ULA, no global
   address and no NAT66, so a site with no A record fails through the proxy.
   Fixing that is a separate decision.

Forward chain needs no change: rule 13 drops `in-interface-list=!LAN`, and
client→container arrives on `BRIDGE`.
