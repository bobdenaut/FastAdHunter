## Why this soak exists

The previous soak could only report RSS. It showed RSS flattening, which is
consistent with "no leak" but does not prove it — 45 % of RSS was unattributed,
which is exactly where a slow leak hides. This build reports
`residual_bytes`, so the question is answerable:

> **Leak = residual growing while the named components stay flat.**
> Growth in a *component* is not a leak — it is that structure filling toward
> its cap.

Cache and ring are both nearly empty at T0+3min — expect them to grow toward
their caps. **That is not the signal.** The ring holds `ring_entries` (10 000)
most-recent events, so `query_log_ring_bytes` should rise until roughly the
ten-thousandth query and then stop trending. If it keeps climbing past ~3 MiB
after that, the running total introduced in p2-07 has drifted and the
accounting is wrong.

## Accounting cost — the estimate was wrong

`fastadhunter_memory_collection_seconds` read **692 µs**, then **842 µs** on a
later poll.

`p2-07-review.md` §5 estimated **200–300 µs** by scaling an x86 measurement.
The real figure is **2–3× higher**. Two reasons the extrapolation was bad, both
knowable in advance:

1. The x86 test ran on Windows, where `process_rss()` returns `None` — so the
   `/proc/self/status` open+read+parse was **never in the 43 µs**.
2. Only `Stats::heap()` was measured; the deployed pass also walks the matcher
   and the cache.

Impact is still negligible: 842 µs every 10 s is **0.008 % duty cycle**. The
conclusion (keep the accounting) is unchanged — but it was reached by the wrong
route, and the number to quote from now on is the ARM one.

## Confounds to remember

- **The router was rebooted at T0**, and again for this third start. RouterOS
  total memory dropped 611.90 → 206.40 MiB on the first reboot, so ~405 MiB was
  accumulated state, not a baseline. **With SMB now off, the router-level curve
  is finally interpretable:** if it climbs back toward ~600 MiB and flattens,
  that was page cache from the share and is harmless. If it climbs with no
  share and no mapped client, something else on the router is accumulating —
  and it still is not FastAdHunter, whose RSS is 37 MiB of the 204 and is
  measured independently.
- **AdGuard `start-on-boot` was set to `no`** before the reboot, so it no longer
  competes for the shared 1 GB. It was already `stopped` beforehand.
- **`/stats` is clean this time.** The previous window was diluted by
  load-generator traffic (`heystanzo.com`), which made the reported block rate
  meaningless. This process started fresh with household traffic only.
- Nothing in 0.2.5 changes memory behaviour, so the router-level curve has no
  reason to differ from before the reboot.
