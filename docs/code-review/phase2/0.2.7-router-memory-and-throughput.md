## 2. The memory-accounting contradiction — resolved

### 2.1 The apparent paradox

RouterOS reported, simultaneously:

```
/system/resource     total-memory 1024.0MiB   free-memory 616.6MiB   →  used ≈ 407 MiB
/container           fastadhunter memory-current 593.0MiB
                     postgres     memory-current  55.2MiB   →  charged ≈ 648 MiB
```

648 MiB of container charges inside a system that reports 407 MiB used. Both
cannot describe the same bytes.

### 2.2 Resolution

They describe the same bytes with **opposite classification**. `memory-current`
is cgroup v2 `memory.current`, which charges **page cache** to whichever cgroup
faulted the pages in. `free-memory` counts reclaimable page cache as available.

Measured live (17:12–17:18 UTC):

| Source | Value |
| ------ | ----- |
| `/container memory-current` (fastadhunter) | 595.0 MiB |
| FAH `process_rss` (`/api/v1/debug/memory`) | 73,707,520 B = **70.29 MiB** |
| FAH's total on-disk data under `/kingston/fastadhunter/` | 550,563,882 B = **525.05 MiB** |

```
  70.29  MiB   anonymous RSS (the real footprint)
+ 525.05  MiB   page cache for its own data files
= 595.34  MiB   vs. measured memory-current = 595.0 MiB      →  Δ 0.34 MiB (0.06 %)
```

A 0.06 % miss on a 595 MiB figure. This is not a hypothesis; it is an identity.

### 2.3 What makes up the 525 MiB

Summed on the router with a `:foreach` over `/file`:

| Path | Size |
| ---- | ---- |
| `data/query_log/segments/` — **100 files** | 522,394,040 B = **498.19 MiB** |
| `data/lists/*.raw` (16 lists; largest `big.oisd.nl.raw` 7.6 MiB) | ≈ 24 MiB |
| `data/history/perf/*.jsonl` + `rollups/` | ≈ 3 MiB |
| **Total** | **550,563,882 B = 525.05 MiB** |

498.19 MiB of query log is the **500 MiB retention cap**, resident in page cache
in its entirety. FAH reads and writes these files, so the cgroup bills it for
every page.

`memory-high=unlimited` means nothing ever triggers reclaim, so `memory-current`
will track the retention cap indefinitely. **It is a disk-cache gauge wearing a
memory label.** It is not a footprint and should never be read as one.

### 2.4 Second, independent confirmation — the restart

The container was restarted at 17:30:06 UTC to apply the env vars (§5.3). That
destroys and recreates the cgroup, discarding every page-cache charge with it.
Immediately after:

```
memory-current  =  60.1 MiB      (was 595.0 MiB before the restart)
process_rss     =  41.7 MiB
```

A 535 MiB drop with no change to the binary, the config or the workload — and
`memory-current` landing ~18 MiB above RSS, which is the config and list files
read during startup. Exactly what §2.2 predicts, arrived at by a completely
different route. It will climb back toward ~595 MiB as the query log refills.

### 2.5 The `memory-high` check — RUN, AND IT KILLED FAH. DO NOT REPEAT.

This document originally proposed `/container set fastadhunter
memory-high=200M` as a falsifiable check, predicting `memory-current` would
collapse to near RSS with no effect on service.

**The user ran it. RouterOS killed the container.** The prediction was wrong and
the suggestion was unsafe on a live resolver.

Why it fails is the same fact the section is about, turned against the test.
`memory-current` is dominated by page cache (§2.2), so the limit is not being
measured against FAH's ~70 MiB footprint — it is measured against footprint
*plus the entire query-log retention cap*. The cgroup crosses 200 MiB within
minutes of normal logging. Linux `memory.high` is supposed to throttle and
reclaim rather than kill, so RouterOS is evidently enforcing this closer to
`memory.max`; either way the observed behaviour is a kill, and that is what
counts.

**Operational rule: do not set `memory-high` on this container.** Any value
sized for FAH's real memory will be tripped by page cache, and any value safe
against page cache is too large to bound anything. The knob is actively
dangerous here.

#### The global knob, and why it is also wrong

`/container/config` carries its own `memory-high`, applying to container
operations in aggregate rather than per container. That is the only level where
the setting does not kill FAH — but it charges for it at boot, because image
extraction into `tmpdir=/kingston/pull` is exactly the kind of heavy file I/O
that a capped cgroup must keep reclaiming instead of caching.

**Recommendation: set nothing, at either level.** The reasoning is that there is
no problem to solve:

- FAH's real footprint is 70 MiB against a 128 MB budget and a 1 GiB box.
- The 525 MiB is *reclaimable* page cache. `free-memory` reports 613 MiB
  available precisely because the kernel already counts it as such.
- The system is under no memory pressure whatsoever, so the cache is costing
  nothing and is actively making query-log reads fast.

Capping it trades real boot latency for a cosmetically tidier counter. That is a
bad trade against a number that was never measuring what it appeared to measure.

#### If the counter still bothers you

Shrink what FAH keeps on disk, since that is what the counter is really
tracking — this costs nothing at runtime and, unlike a cgroup cap, buys a second
real benefit:

```
query_log.retention_max_mb : 500      <- the ~498 MiB of segments in §2.3
query_log.retention_days   : 7
```

Dropping `retention_max_mb` to, say, 100 would take `memory-current` from ~595
MiB to roughly 145 MiB, cost nothing in memory or latency, and cut the write
volume in §4.4. It trades query-log history for a tidier counter **and materially less SSD
wear** — §4.4 measures ~86 GB/day of writes under load. That second effect is a
genuine cost being reduced, which is what makes this the one adjustment worth
considering. FAH's actual footprint is unaffected either way.

### 2.6 Consequence for the older RouterOS-growth question

This retires the provisional framing carried in
`docs/code-review/phase2/mimalloc-and-todos-review.md` §1.7. The observation recorded in
`p1.5-09-soak-baseline.md` §B2b — that a real 66 MiB cut in FAH's RSS moved the
router's `free-memory` by only 1.5 MiB — is **exactly what this model predicts**:
the cut was anonymous memory, while the router's counter is dominated by
reclaimable cache that the cut never touched.

The growth is page cache. FAH's heap was never the driver. The evidence is now
direct rather than circumstantial, and the qualifier can be dropped.

| | Share | µs/query |

container-topology change rather than a code change. Worth measuring before
optimising anything else in the engine.

### 3.7 Cache sizing — 10 k → 50 k was right, and is now finished

`max_entries` was raised from 10,000 to 50,000 before these runs. The test data
says it was the correct change and that it is now done:

| | Value |
| --- | ----- |
| `capacity` | 50,000 |
| peak `entries` during the 32M-query run | **20,250 (40.5 %)** |
| `evictions` | **0** |
| `bytes` / `max_bytes` | 10,850,528 / 67,108,864 (16.2 %) |

**Zero evictions is the whole story.** At 10 k the cache would have been full and
evicting continuously; at 50 k it holds the entire working set with 60 % to
spare. That is a real improvement and it is why the hit rate reached 98.93 %.

But it also means **raising it further does nothing.** Capacity stopped being the
binding constraint the moment evictions hit zero; 50 k is already 2.5× the
working set, and unused capacity is not free — it is entry slots and the byte
cap held against a 128 MB budget.

**The hit rate will not rise from here either.** The remaining 1.07 % (311,260
misses) are *cold* misses — first-ever lookups of names not yet in the cache. No
cache size prevents a cold miss; only a longer warm-up or a smaller domain set
would move that number, and neither is a property of the cache.

**Errors are unrelated to cache size.** The run reported 75 errors with
`timeouts = 0`, while FAH recorded 844 upstream failures against 1.1.1.1 and 127
against 9.9.9.9. Those are upstream and network conditions. The cache sits in
front of the upstream path and cannot make it more reliable.

#### The number that actually matters here

`/api/v1/stats` over 24 h of real household traffic reports a
**`cache_hit_percent` of 75.73 %** — against 98.93 % in the synthetic run.

So the benchmark is far more cache-friendly than production. In real service
roughly a quarter of queries go upstream, and a miss costs vastly more than the
15.9 µs a hit costs. **The 20 k+ QPS ceiling therefore describes the cache path,
not the device under realistic traffic**, and the real-traffic ceiling is
materially lower.

This also cuts against the measurement plan in §8: the allocator A/B needs a
**miss-heavy** profile, because allocation is what the allocator affects and the
forward path is where allocation happens. Tuning the cache upward pushes the
benchmark further from the workload that would answer the question.

## 4. Memory behaviour under load

### 4.1 Before / after the 30-minute run

| Field | 16:25 (before) | 16:58 (after) | 17:16 (live, idle) |
| ----- | -------------- | ------------- | ------------------ |
| `process_rss` | 55,529,472 | 71,483,392 | 73,707,520 |
| `accounted_bytes` | 26,122,828 | 44,811,406 | 44,812,312 |
| `residual_bytes` | 29,406,644 | 26,671,986 | 28,895,208 |
| `allocator_committed_bytes` | 298,778,624 | 318,046,208 | 318,046,208 |
| `allocator_committed_peak_bytes` | 298,778,624 | 318,046,208 | 318,046,208 |
| `allocator_retained_bytes` | 272,655,796 | 273,234,802 | 273,233,896 |
| `process_peak_rss` | 157,990,912 | 157,990,912 | 157,990,912 |
| `major_page_faults` | 0 | 0 | 0 |

**`residual_bytes` is flat** — 28.0 → 25.4 → 27.6 MiB across 32 million queries.
That is the leak signal, and it did not move. RSS growth (52.9 → 70.3 MiB) is
fully explained by the cache filling (37 → 20,250 entries, 42 KB → 10.9 MB) and
the stats/query-log ring reaching steady state. **No leak.**

RSS across the run, from `/api/v1/history/perf`: 61.8 MiB at test start, maximum
**76.0 MiB**, 71.1 MiB at the end. The allocator returned pages continuously.

### 4.2 The 150.7 MiB startup peak — a real finding

`process_peak_rss` = 157,990,912 B = **150.67 MiB**, and it was set within the
first four minutes of the process, i.e. at the **startup ruleset compile**, not
during the 32M-query test.

No RSS sample shows it. The `/history/perf` series has a 2-minute stride and
records 42,962,944 B at 16:21:25 then 57,405,440 B at 16:23:25. The 150.7 MiB
transient fell entirely between two samples.

**This is `process_peak_rss` earning its place.** It is a `getrusage` high-water
mark, so it cannot miss a spike between scrapes — which is precisely the failure
mode the 2-minute sampling has. First time it has proved its value.

Note the budget is worded "RAM **steady-state**, 1M blocked domains loaded ≤ 128
MB", so a compile transient is not formally a breach — but **no budget covers the
compile transient at all**, and it is twice steady state. That is a gap in
PERFORMANCE.md, not a passing grade.

### 4.3 The batched-compile fix works, but a compile is still expensive

The fix in `crates/fah-rules/src/lifecycle/mod.rs` (`refresh_due_lists`,
fetch-all-then-compile-once) is live — the log shows the new single-line
`scheduled refresh complete lists=16 refreshed=16 failed=0` message rather than
16 separate compiles.

But the history still records a **209,223,680 B (199.5 MiB)** spike at 15:00:06
UTC. The log explains it: three compile events stacked in ~2 minutes —
`scheduled refresh complete` (16 lists) at 14:57:14, `list refreshed list=spy` at
14:58:53, and `refreshed all lists` (16 lists) at 14:59:29.

So: 16 compiles → 1 per scheduled batch is fixed and confirmed. **A single
compile still roughly triples RSS transiently, and stacked compile events still
reach ~200 MiB — 78 % of the 256 MB container ceiling.** The remaining work is
the cost of one compile, not the count of them.

### 4.4 Write amplification

From the segment file mtimes: `seg-0000000904` at 16:49:05 UTC through
`seg-0000000997` at 16:56:50 UTC — **93 segments × 5 MiB in 465 s = 1.0 MiB/s
≈ 86 GB/day**.

At that rate the 498 MiB retention window collapses to **~8.3 minutes**. At idle
the rate is ~0.6 KiB/s (`seg-0000000999` accumulated 651.5 KiB over ~18 min), a
ratio of roughly 1700×.

Two consequences: a real endurance cost on the USB SSD under sustained load, and
the query log becoming useless as a forensic record exactly when load is high
enough to want one.

## 5. The mimalloc environment variables

### 5.1 They are attached — I claimed otherwise and was wrong

I asserted the vars were not in effect, reasoning from `process_peak_rss` and
`allocator_committed_bytes` being unchanged between 16:58 and 17:16. That only
shows no restart occurred in *that window*; it says nothing about the 16:21
start. The claim outran the evidence.

The container log settles it:

```
2026-07-30 19:21:22  fastadhunter: *** started PATH=… SSL_CERT_FILE=…
  MIMALLOC_PURGE_DELAY=0 MIMALLOC_PURGE_DECOMMITS=1 MIMALLOC_ARENA_EAGER_COMMIT=0
  TZ=Europe/Bucharest /fastadhunter
```

The vars were in the environment of the running process from the start. (The log
also shows an earlier start at 19:10:03 **without** them, and the restart
sequence 19:12:27 stop → 19:15:31 remove → 19:16:42 repull → 19:18:34 start with
the vars → 19:19:32 stop → 19:20:59 repull → **19:21:22 start**, the current
process.)

A second claim of mine also died on my own data: `allocator_committed_bytes`
moved 298,778,624 → 318,046,208 between 16:25 and 16:58, so it is not frozen and
the "one arena committed at boot" story was wrong.

### 5.2 What the data does support

Across three independent readings, `committed` and `committed_peak` are
**exactly equal every time** (298,778,624 = 298,778,624; then 318,046,208 =
318,046,208 twice). If `committed` ever decreased, current would fall below peak.
It never has.

Therefore `committed` is **monotone non-decreasing — it does not decrement when
memory is purged.**

Combine with RSS = 70.3 MiB:

- 318 MiB committed against 70 MiB resident ⇒ ~248 MiB was committed, touched,
  and then taken back by the kernel.
- Pages being taken back means `MADV_DONTNEED` fired ⇒ **the purge settings are
  working.** RSS is the proof; it is the number that matters, and it is healthy.
- mimalloc v3 simply does not decrement its `committed` statistic on purge.

### 5.3 Resolved — the options parse, and the counter is worse than described

`MIMALLOC_VERBOSE=1` was added to `fah-env` (§7) and the container restarted at
2026-07-30 17:30:06 UTC. The dump settles it — all three parsed, no warnings:

```
option 'arena_eager_commit': 0
option 'purge_decommits':    1
option 'purge_delay':        100
option 'arena_reserve':      1048576 KiB      ← 1 GiB, on a 1 GiB box
option 'allow_thp':          1
mimalloc: reserved 1048576 KiB memory
```

**`arena_reserve` is 1 GiB** — mimalloc reserves an arena the size of the
router's entire RAM. With `arena_eager_commit=0` that is address space only, not
physical memory, so it inflates VSZ and nothing else, and the reservation
succeeded. Worth knowing rather than acting on; `MIMALLOC_ARENA_RESERVE` can
lower it if VA pressure ever matters.

Post-restart reading, with all three options confirmed live:

| Field | Value |
| ----- | ----- |
| `process_rss` | 43,724,800 = 41.7 MiB |
| `allocator_committed_bytes` | 312,344,576 = **297.9 MiB** |
| `allocator_committed_peak_bytes` | 312,344,576 — **still exactly equal** |
| `process_peak_rss` | 175,828,992 = 167.7 MiB |

Two conclusions, both stronger than §5.2's:

1. **The monotone finding survives the options.** `current == peak` to the byte
   with `arena_eager_commit=0` and `purge_delay=100`. The counter does not
   decrement on purge, and no setting makes it.
2. **It is worse than a high-water mark.** 297.9 MiB committed exceeds
   *`peak_rss` itself* (167.7 MiB). A high-water mark of a live quantity cannot
   exceed the peak of the memory that quantity describes. The counter therefore
   accumulates commits over time without subtracting purges — commit, purge,
   recommit adds twice. It cannot be read as memory held at any instant, which
   is exactly why the derived field was removed (§6.1).

## 6. Metric defects found

### 6.1 `allocator_retained_bytes` is meaningless as shipped

```
allocator_retained_bytes = 273,233,896 B = 260.6 MiB
process_rss              =  73,707,520 B =  70.3 MiB
```

A "retained memory" figure **3.7× larger than the process's entire RSS**. Nothing
resident can exceed RSS. Its HELP text claims it is "fragmentation, free lists
and size-class rounding" — it is none of those; it is the gap between a monotone
high-water counter and current accounting.

`residual_bytes` (27.6 MiB) is the honest number and matches binary text/data +
thread stacks + runtime.

### 6.2 `allocator_committed_bytes` HELP text is wrong

It reads "Read/write memory the allocator currently holds from the OS". Per §5.2
it is a **lifetime high-water mark of commit**, not a current figure. The word
"currently" is false.

### 6.3 We cannot observe purge thrash

`fastadhunter_process_major_page_faults_total` is 0 and is structurally always 0
for this workload — major faults are disk-backed. The metric that would reveal
decommit/recommit cycling is **minor** faults, `ru_minflt`, which arrives in the
**same `getrusage` call already being made** in
`crates/fastadhunter/src/allocator.rs`. It costs nothing to add and is currently
the blind spot for exactly the failure mode aggressive purging can cause.

| `MIMALLOC_ARENA_EAGER_COMMIT` | 0 | 0 (unchanged) |
| `MIMALLOC_PURGE_DECOMMITS` | 1 | 1 (unchanged) |
| `MIMALLOC_PURGE_DELAY` | 0 | **100** |
| `MIMALLOC_VERBOSE` | — | **1** (added) |

**Why `PURGE_DELAY` 0 → 100.** `0` means a `MADV_DONTNEED` syscall on every
eligible free with no coalescing, so bursty free/alloc cycles round-trip through
the kernel instead of cancelling out. The stress test is not evidence that `0` is
safe: at 98.93 % cache hits it barely exercised the allocation-heavy forward
path. `100` costs at most 100 ms of un-returned free memory — nothing at these
rates — and is still 10× more aggressive than mimalloc v3's own 1000 ms default.

**Why `MIMALLOC_VERBOSE=1`.** It is the only way to settle §5.3. mimalloc dumps
every option value at init and warns on unrecognised names, on stderr, which
lands in `/log print` exactly as FAH's tracing does.

## 9. Verdict on mimalloc — keep it

**Recommendation: keep mimalloc. Confidence high.** The reasoning, weighted:

### 9.1 The throughput gain is now large enough to survive its confound

§3.5 gives ≈ +27 % throughput and ≈ −17 % CPU per query, **saturated on both
ends** — the property that makes the two runs comparable at all.

The surviving confound is the unrecorded hit ratio of the p1.5-06 run (§3.3). It
is real, but it has to carry the whole delta to explain it away. A hit-ratio
difference can plausibly manufacture five or six percent; **seventeen strains
credulity.** The honest phrasing is *"measurably faster, magnitude not yet
isolated"* — not *"mimalloc bought 27 %"*.

Note this reverses an earlier reading in this document's drafting, which held the
throughput evidence to be silent. That was written before the `/tool profile`
data existed and assumed the run might be generator-bound. It was not.

### 9.2 The observability benefit is uncontested and independent

`p1.5-09-soak-baseline.md` recorded that musl `mallocng` retained recompile
arenas invisibly, making a settling RSS curve indistinguishable from a slow leak
— an apparent +0.83 MiB/h "leak" that was settling. On 0.2.7 the curve returns:
43 → 76 MiB under load and back down after (§4.1). Soak data is readable now.
This holds regardless of how §9.1 resolves.

### 9.3 The cost of being wrong is one hour

The entire integration is `crates/fastadhunter/src/allocator.rs`. Reverting is a
one-line change of the `#[global_allocator]` and a rebuild. **There is no
lock-in**, which is exactly what the containment boundary was built for, and it
makes "keep it and confirm later" strictly better than "revert and wonder".

### 9.4 The costs are small and already paid

Image 5.54 MB against a 30 MB budget. Steady-state RSS 70.3 MiB against 128 MB.
32 M queries with 75 errors and no crash. The one structural cost is that a C
toolchain is now required to build — `musl-dev` in the Dockerfile is load-bearing
— and `gcc` already ships in the `rust:*-alpine` base, so it costs nothing at
build time either.

### 9.5 What does not justify it

**The reason it was adopted is void.** mimalloc was chosen because RouterOS
memory appeared to grow without releasing. §2 settles that as page cache, proven
to 0.06 %. mimalloc was never going to fix it, did not fix it, and did not need
to. Keeping it is justified by §9.1–9.4, not by the problem that prompted it.

### 9.6 Caveats attached to the recommendation

- **Do not quote a percentage** in `PERFORMANCE.md` or `README.md` until the A/B
  in §8 removes the hit-ratio confound. Report the ceiling (20 k+ QPS,
  saturated), which is a fact, rather than an attribution, which is not.
- **mimalloc v3 is the younger line.** `libmimalloc-sys 0.1.49` selects 3.3.2 by
  default; `v2` (2.3.2) is a one-feature-flag fallback and more battle-tested.
  Not worth doing now — a household soak plus 32 M queries is decent evidence —
  but worth knowing, especially given that v3's commit accounting was broken
  enough to produce the metric removed in §6.1.
- **The allocator is no longer the biggest lever.** §3.6 puts ~18.5 % of the box
  in veth/bridge plumbing, ~36.5 µs/query of code that is not ours. That is a
  bigger prize than anything left in the allocator, and it is a configuration
  change.
