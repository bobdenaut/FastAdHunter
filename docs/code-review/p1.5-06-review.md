# P1.5-06 Review — Multi-Socket (SO_REUSEPORT) Ingest

**Outcome:** DONE as **measured → deferred**. No production code was written.
The task's deliverable was *measure → decide → record*; that is complete.

## What the task asked

Remove the single-threaded UDP *ingest* funnel with `SO_REUSEPORT` (N sockets,
N `recv_from` loops, kernel load-balancing across cores) — **but only after
measuring that ingest is actually the ceiling**. The task gates itself in
Scope §1: *"If all cores share evenly with headroom → record that ingest is not
the limiter and stop (don't add complexity for nothing)."*

## The measurement (the gate)

On-device (RB5009), under a full `test_aleator.py` hammer (2026-07-23):

- Total CPU held at **~15-20%**, with **~80% idle**, and load was **even across
  all four cores** — not one core near 100% with the rest idle.

That is unambiguously the "share evenly with headroom" branch. If the single
`recv_from` loop were the ceiling, one core would saturate while the others
starved. It doesn't. Reception (`recv_from` + `to_vec` + `spawn`) is the
cheapest step, and the expensive stages (match / cache / forward / reply)
already spread across all workers via the task-per-datagram design in
[`crates/fah-dns/src/udp.rs`](../../crates/fah-dns/src/udp.rs). Ingest is **not**
the limiter today.

## Confirming measurement (2026-07-24) — ingest ruled out under CPU saturation

Full raw run logs (per-second tables, CPU prints, `/tool profile`, conntrack) in
[`p1.5-06-measurements.md`](p1.5-06-measurements.md); the distilled figures follow.

The 2026-07-23 reading showed an *idle* box, which could be dismissed as "the
hammer never applied real load." So we re-measured with a workload that **can**
saturate the CPU: a 1000-worker `test_aleator.py --profile stress` hammer against
a 25-domain **hot set** (25 × 7 types = 175 keys), which warms the cache in ~1 s
and then serves every query **locally** (cache hits, no upstream I/O) — the
pure-CPU case the idle test could not produce.

The box now genuinely saturates, and the CPU is attributed:

- **Throughput:** ~15–16k QPS sustained through the deployed path
  (client → router dstnat → container → FastAdHunter → back); 520k queries over
  33 s; ~2.3 % shed as 2 s timeouts past the knee.
- **Per-core:** all four cores **even at ~85 % LOAD + 15–28 % IRQ** — not one
  core pinned with the rest idle.
- **CPU attribution (`/tool profile`, 20 s):** `fastadhunter` **65.8 %**,
  `networking` 8.2 %, `firewall` 4.8 %, bridging/ethernet ~3.9 %, rest ~4 %;
  **total 87.5 %**. FastAdHunter is roughly three-quarters of all consumed CPU.
- **Conntrack is a non-issue:** 15,454 entries against a 968,704 max (1.6 %),
  flat across the run (ephemeral source ports recycle; entries refresh, not
  explode). The timeouts are queue-shedding at FAH saturation, not conntrack
  exhaustion.

Read as a layered attribution:

1. **FAH-bound, not RouterOS-bound** — `/tool profile` puts 65.8 % in the
   container vs ~17 % in all RouterOS forwarding / NAT / conntrack combined.
2. **Handling-bound, not ingest-bound** — within FAH, the `recv_from` loop is a
   *single* tokio task; were it the ceiling, its one worker's core would peg at
   100 % while the other three starved. Instead all four cores sit even at ~85 %,
   which only happens if `recv` feeds every worker comfortably and the
   distributed *handling* (match → cache → serialize → reply) is what fills the
   cores. Back-of-envelope: 15.7k QPS at 65.8 % of a 4-core box ≈ **~167 µs of
   CPU per query**, dominated by matcher / cache / serialize / socket work — not
   the few µs of `recv`.

`SO_REUSEPORT` only parallelizes `recv` — the small, non-limiting slice.
**Current evidence does not indicate that `SO_REUSEPORT` would materially raise
the current ~15k QPS ceiling.** The claim is deliberately scoped to *today's
pipeline*: if a future redesign makes single-socket UDP reception the point of
contention (a documented failure mode in the Tokio/Rust community), reuseport can
raise the ceiling — which is exactly what the retained recipe and the re-fire
trigger below exist for.

For perspective, ~15k QPS is roughly **1000×** a busy household's aggregate DNS.
If the ceiling ever needed lifting, the lever is FAH's per-query *handling* cost
(matcher / cache / serialize), located via an internal flamegraph — not ingest.

## Why we deferred rather than "built it once, right"

1. **Reuseport is a local optimization, not architecture — and fully
   retrofittable.** Unlike the rest of Phase 1.5 (rollups / perf-series / history
   API, which define the on-disk + REST contract Phase 2's UI reads), reuseport
   defines **no downstream contract**. It is a self-contained change in two files
   ([`server.rs`](../../crates/fah-dns/src/server.rs) binds N sockets,
   [`udp.rs`](../../crates/fah-dns/src/udp.rs) runs N loops) with no coupling in
   amont. The cost to add it later equals the cost to add it now — deferring
   forfeits no recoverable architectural opportunity, and there is no lock-in.

2. **Its benefit *shrinks* as Phase 2/3 land.** Reception is already the cheapest
   step and handling is already multi-worker. The heavier Phase 2/3 engines
   (HTTP/HTML) make *handling* heavier, which lowers the QPS needed to saturate
   handling — so the recv loop is *even less* likely to ever be the ceiling. The
   task's "prove headroom for Phase 2/3" motivation therefore cuts *against*
   building now, not for.

3. **The real latent ingest concern is bounded concurrency, not parallelism.**
   `udp::run` does an unbounded `tokio::spawn` per datagram — a hard-rule-#4
   tension under an adversarial flood (in-flight tasks each hold a buffer + a
   pending forward). More reception loops (reuseport) would make that *worse*,
   not better. The 91h soak ([`p1-11-soak.md`](p1-11-soak.md)) proved RSS bounded
   under representative load, so this is latent, not acute — noted here so it
   isn't lost, but out of scope for this task.

Building the N-socket machinery now (socket2 N-bind + `#[cfg]` Linux gate +
single-socket fallback + `reuseport_count` config + before/after perf tables) for
a stress ceiling that household traffic never approaches would be complexity for
its own sake.

## What we did instead (preserving the opportunity cheaply)

- **Documented the direction** in `ARCHITECTURE.md` §Runtime Model: today's
  single-recv-loop topology and `SO_REUSEPORT` as the documented scaling path,
  with the measured "not the ceiling" finding — the idea is preserved without the
  code.
- **Kept the recipe intact** in the task file
  ([`p1.5-06-reuseport-multisocket-ingest.md`](../../plan/wip/phase1.5/p1.5-06-reuseport-multisocket-ingest.md)),
  with a Decision note at the top pointing here and stating the re-fire trigger.
- **Marked the task DONE** (measured → deferred) so `p1.5-07` (verification)
  becomes the next `WAITING` task.

## Re-fire trigger

Build the reuseport recipe when any holds:

- a **per-core** measurement shows one core saturated on `recv` while the others
  idle (genuine single-recv-loop ceiling), **or**
- a **pipeline redesign** (e.g. Phase 2/3 reworking the datagram path) makes
  single-socket UDP reception the measured point of contention, **or**
- a concrete **flood-resilience** requirement appears.

## Gates

No production code touched, so `cargo fmt`, `cargo clippy`, and
`cargo test --workspace` are unaffected by this change.
