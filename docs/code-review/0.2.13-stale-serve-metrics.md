# 0.2.13 — Stale-serve metrics semantics

Found while reconciling a 0.2.12 soak capture, not by a failing test. Commit
`0884561`, gates green (875 tests, 41 binaries).

## Summary

`Metrics::record` timed every stale serve as a `forward`. That was correct
before [ADR-0005](../decisions/0005-serve-stale-while-refresh.md) — a stale
answer could only follow a failed forward — and ADR-0005 made it false without
updating the routing. With `swr_workers > 0` the pipeline returns the stale
answer *before* reaching the forwarder, so sub-100 µs cache reads were being
recorded in the histogram that measures upstream round trips.

Four releases of `forward` latency are affected. The counters
(`cache_hits`, `cache_misses`, `cache_stale`) were always correct.

## Decisions

- `QueryEvent.stale: bool` → `Option<StaleServe>`. A bool cannot express the
  distinction; the pipeline already knew it at all three call sites.
- Only `AfterForwardFailure` is timed as a forward. It carries the upstream
  timeout, so routing it to `cache_hit` would blow that budget signal during
  exactly the outages it must stay clean through.
- `cache_stale` keeps counting **both** paths. It answers "how often did an
  expired entry answer", which is true either way. The split is derivable:
  `forward_hist.count − cache_misses`.
- No new counter. The question "how many stale serves were outage-driven"
  is answerable from existing figures; a fifth atomic on the hot path is not
  justified (principle 16).
- No wire change. The WS projection reads `cache_hit`, never `stale`, and no
  `QueryEvent` is persisted.

## Bugs found

| # | Defect | Impact |
| --- | --- | --- |
| 1 | SWR stale serves timed as forwards ([registry.rs:148](../../crates/fah-metrics/src/registry.rs#L148)) | 84 % of the `forward` histogram was cache reads; mean understated 6.3× |
| 2 | `cache_hit` histogram excluded SWR serves | p99 budget row measured on 44 % of hits |
| 3 | Two pipeline tests silently inert since ADR-0005 | the RFC 8767 fallback had no live coverage |

Defect 3: `upstream_failure_serves_stale_cache_entry_when_available` and
`upstream_servfail_serves_stale_cache_entry_when_available` both ran on
`DnsCacheConfig::default()`, whose `swr_workers` is **3**. The SWR path returned
first, so `FailAfterFirstForwarder` / `ServfailAfterFirstForwarder` were never
reached — the fixtures were decorative. Both now pin `swr_workers = 0`.

## Measurements

RB5009, 0.2.12, 15.3 h window (2026-08-07T21:23Z → 2026-08-08T12:42Z), no
restart. Corrected figures divide by the real forwards and subtract the stale
serves at cache-hit cost.

| Figure | As reported | Corrected |
| --- | ---: | ---: |
| forward mean, window | 2.40 ms | **15.06 ms** |
| forward mean, T0 | 10.75 ms | **12.75 ms** |
| forward histogram count | 6 759 | 1 061 real forwards |
| stale serves misrouted | — | 5 698 (84 % of the histogram) |
| `cache_hit` histogram coverage | 4 408 | of 10 106 hits (44 %) |

`forward_p50 = 100 µs` in `/history/perf` was likewise meaningless — it reported
the stale serves, not the network.

Hot path, A/B against a pre-change checkout in one session (criterion's stored
baseline was from another session and reported a false regression):

| Bench | pre | post |
| --- | ---: | ---: |
| record cache-hit pass | 17.81 ns | 18.09 ns |
| record blocked | 14.56 ns | 14.68 ns |

Within run-to-run noise. `Option<StaleServe>` is niche-optimized to the one byte
the bool occupied, so `QueryEvent` did not grow and the channel and `fah-stats`
heap costs are unchanged. The `mixed` arm is not comparable across the change —
it gained a fifth event shape because the stage branch now has three outcomes.

## Invariants

The old identity `cache_hit_hist + cache_stale == cache_hits` **no longer
holds**. Checking it post-0.2.13 produces a false failure. Replacements:

- `cache_hit_hist == fresh hits + FromSwr`
- `forward_hist == cache_misses + AfterForwardFailure`
- `cache_hit_hist + forward_hist == pass + allow`

Guarded by `stages_partition_resolved_queries`.
