# p1.5-05 — Byte-aware cache cap + rule deduplication: implementation review

**Task:** [plan/wip/phase1.5/p1.5-05-cache-byte-cap.md](../../plan/wip/phase1.5/p1.5-05-cache-byte-cap.md)
· **Status:** DONE, gates GREEN · **Commit:** deferred (phase1.5 commits as one

Two independent memory-hardening deliverables, both closing findings recorded
during phase 1: the DNS cache was bounded by entry count but not by bytes, and
the compiled matcher stored overlapping lists' rules twice.

---

## A — Byte-aware cache cap

### What was built (A)

**`fah-config`** — `[dns.cache] max_bytes`, default **64 MiB**: half of
PERFORMANCE.md's 128 MB steady-state budget, which leaves the ≤40 MB compiled
ruleset and the process base underneath the ceiling even with the cache
completely full. Validated with a 1 MiB floor (below that a shard could not
hold a single maximum-size DNS answer, so every insert would evict what it just
stored). Env override `FAH__DNS__CACHE__MAX_BYTES` via a new `coerce_u64`.

**`fah-dns/cache.rs`** — each shard carries `byte_capacity` (its slice of
`max_bytes`) and `bytes`, a running sum of `entry_heap_bytes` maintained on
every insert, eviction and clean. Eviction now runs *after* the insert, from
the same FIFO head, until **both** bounds hold:

```rust
while guard.over_bounds() && guard.map.len() > 1 {
    guard.evict_oldest();
    self.evictions.fetch_add(1, Ordering::Relaxed);
}
```

Three details worth naming:

- **`map.len() > 1` guards the insert against itself.** An answer larger than a
  whole shard's byte budget is kept alone rather than evicting itself, so the
  degenerate case is "one entry per shard", never a cache that thrashes on
  every store. Tested.
- **Insert-then-evict replaced check-then-insert**, which also removed a
  `contains_key` probe from the store path. Equivalent ordering: the new entry
  sits at the queue's back, so FIFO reaches it last.
- **A refresh subtracts the replaced answer's bytes** (`map.insert` returns the
  old value), so re-caching a domain whose answer shrank releases the
  difference instead of leaking accounting.

The estimator was *reused*, not duplicated: `stats()` no longer re-walks the
map summing `entry_heap_bytes`; it reads the tracked total. One number is both
enforced and reported, so the two cannot drift — asserted by a test that
compares the running total against a full walk after churn.

**Surface** — `CacheStats` gained `bytes` + `max_bytes` through
`fah-dns` → adapter → `fah-api` port → wire, exposed on `GET /api/v1/cache` as
`bytes`, `max_bytes` and `byte_load_percent` alongside the existing
`load_percent`. `fah_model::CacheStatsSample` gained the same pair (both
`#[serde(default)]`) so p1.5-02's sampler graphs the byte ceiling over time and
rows written before this task still deserialize.

### Scope decision (A)

`estimated_bytes` (slab-inclusive, `/debug/memory`) is deliberately **not** what
the cap governs. The hash-table and eviction-queue slabs scale with
`max_entries`, not with answer size, and they cannot be shrunk by evicting;
capping the entries' own heap is what actually contains the adversarial case.
Both figures are documented where they are served.

### Measurements (A)

Cache-hit in-engine latency, pinned to one core, A/B against a pre-change
worktree: **2.48 µs** vs **2.56 µs** baseline — intervals overlap, no
regression. The cap only touches the insert path.

Sustained throughput (four cores, per PERFORMANCE.md §Measuring reliably), with
the cap active: **~567 000 elem/s** (median of 3 pinned runs, range
560.7–574.8 K) — the figure deferred from p1-11, now recorded in
PERFORMANCE.md.

## B — Rule deduplication

### What was built (B)

`MatcherBuilder::add_rule` drops a rule whose **full identity** — domain
(case-insensitive), action, subdomain flag, `$dnstype` raw, `$dnsrewrite` raw —
is already compiled, and returns *before* appending anything, so a duplicate's
arena bytes, record and slot are never allocated.

The index is a transient open-addressing `Vec<u32>` of record indices keyed by
an identity hash, dropped with the builder at `build()`. The arena stays the
single source of truth: the hash only picks the probe start, and every
accept/reject is a real byte-and-field comparison against arena + flags + side
maps, so **a hash collision can never silently drop a distinct rule**.

`MatcherBuilder::with_capacity(n)` sizes the index once for the whole compile.
`ListManager::compile` derives `n` from a new `parser::rule_upper_bound(text)` —
a ceiling computed in one pass over the raw text without parsing it. It counts
whitespace-separated tokens on content lines because the **hosts parser emits
one rule per host token**, so a line count would *not* be an upper bound; that
property is asserted against the real parsers in a test.

`duplicates_removed` is carried onto `Matcher`, read by the telemetry poll into
`RulesetSnapshot`, exposed as `fastadhunter_ruleset_duplicates_removed`, added
to the `GET /api/v1/lists` envelope next to `compiled_rules`, and logged at
`INFO` on compile. Per-list `rules_*` counts stay parse-based — each list really
does contain those rules; the envelope describes the merge.

### Determinism

The index is membership-only and never iterated to produce output; records,
arena and slots come from processing rules in a fixed order (enabled lists, then
user rules), so first-seen-wins decides survivors, not probe order. The test
compiles the same lists at capacities `0`, `1`, `n`, `100_000` and unhinted, and
asserts a byte-identical fingerprint (arena, records in order, slot count) every
time — proving capacity is inert to the output.

### The performance argument (measured, not asserted)

This is the part that took the most work, and the first two attempts were wrong.

**Cost.** On 1M *unique* rules — the worst case for dedup, all cost and no
benefit — the build phase went 41.6 ms → 135.7 ms at first. A/B'd against a
pre-change worktree on the same box with the same core pinning, not against
criterion's stored baseline, which interleaved runs had polluted.

Two tuning attempts, both measured:

| dedup index | build (1M unique) | verdict |
|---|---|---|
| `Vec<u32>`, 0.7 load | 135.7 ms | first cut |
| `Vec<u32>`, **0.5 load** | **93.3 ms** | **kept** |
| `Vec<(u32, u32)>` tagged, 0.7 load | 124.0 ms | **rejected** |

The tagged slot was meant to reject collisions without touching the arena; it
lost, because the load factor — not the compare — was the dominant term, and
doubling the slot halved the slots per cache line. Rejecting it is recorded in
`matcher.rs` so nobody re-tries it blind. What remains (~52 ms, ~52 ns/rule) is
essentially one random memory access per rule against the index, which is the
floor for membership-testing 1M rules.

**Saving.** Two 1M-rule lists compiled together, by overlap — ~30 bytes per
duplicate removed:

| overlap | duplicates | compiled | saved | build |
|---|---|---|---|---|
| 0% | 0 | 57.7 MiB | — | 493 ms |
| 25% | 250 000 | 50.4 MiB | 7.6 MiB | 469 ms |
| 50% | 500 000 | 43.0 MiB | 15.2 MiB | 454 ms |
| 90% | 900 000 | 31.3 MiB | 27.3 MiB | 430 ms |
| 100% | 1 000 000 | 28.3 MiB | 30.3 MiB | 437 ms |

The 0% row is the argument: two non-overlapping 1M lists compile to 57.7 MiB,
**past the 40 MB budget**. And build time *falls* as overlap rises — a
duplicate's bytes are never appended, so dedup increasingly pays for itself.

**The lookup win — what the memory figure hides.** Collapsing duplicates shrinks
the slot table, so probe chains shorten. A new `overlap_lookup` bench, written
against the pre-dedup builder API so the identical file runs in both checkouts,
on two 500k lists sharing 250k domains:

| lookup | before | after | |
|---|---|---|---|
| hit, domain carried by **both** lists | 154.4 ns | ~83 ns | **−46%** |
| hit, domain in one list | 57.2 ns | 44.5 ns | −22% |
| miss | 63.1 ns | 57.1 ns | −10% |
| compiled | 28.2 MiB | 21.2 MiB | −7.0 MiB |

"After" is the median of 3 pinned runs (shared-hit ranged 79.8–85.5 ns across
runs; a single earlier run read 75.2 ns and was optimistic). A domain both lists
carried used to occupy two slots hashing to the same place, and every query
walked both. So dedup is a **hot-path improvement**, not only a memory one. Hard
rule #3 is intact — `lookup` itself is byte-for-byte unchanged; it simply has
less to walk.

`matcher_lookup` on the 1M-unique corpus (where dedup collapses nothing) is
unchanged-to-slightly-better: 99.7 ns / 345.4 ns / 63.6 ns for
exact / subdomain / miss.

## Deviations from the plan, and why

1. **Dedup index is ~8 MB at 1M rules, not the planned ~5.7 MB.** The plan's
   figure assumed a 0.7 load factor. Measurement showed 0.7 costs 42 ms more
   compile time than 0.5 on a 1M-rule build; 2.3 MB of transient memory, freed
   at `build()`, buys that back. Steady-state RSS is unaffected either way.
2. **`MatcherBuilder::new()` keeps a growable index.** The plan mandates one
   allocation with no realloc churn; that holds for the compile path, which uses
   `with_capacity`. `new()` is used by tests, benches and small ad-hoc builds
   where a fixed ceiling is unknowable, and it rehashes geometrically. The
   determinism test covers the grown path explicitly.

## Known risk (flagged, not hidden)

Projected RB5009 startup rises from the measured 2 440 ms toward **~3.0 s**
against the "< 3 s hard" budget, on the *worst-case* assumption of a
zero-overlap 1.2M-rule corpus. The real corpus is the overlapping one this
feature exists for, where build time falls rather than rises — but the
projection is a dev-box extrapolation either way. **This must be measured
on-device in p1.5-07**; PERFORMANCE.md already names chunked parallel parsing as
the next lever if it breaches.
