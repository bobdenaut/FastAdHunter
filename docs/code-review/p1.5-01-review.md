# p1.5-01 — History Rollup Store: implementation review

**Task:** [plan/wip/phase1.5/p1.5-01-history-rollups.md](../../plan/wip/phase1.5/p1.5-01-history-rollups.md)
· **Status:** DONE, gates GREEN · **Commit:** deferred (phase1.5 commits as one
batch).

Long-term, bounded aggregate time-series on `/data` so a future Pi-hole-style
dashboard can chart query volume, block rate, query types, and daily top-N over
30/60/90 days — without scanning the raw query log.

## What was built

**`fah-model`** — three plain PODs (data + `Serialize`/`Deserialize` only, hard
rule #2): `HourRollup { hour_epoch, queries, blocked, cache_hits, per_type }`,
`DailyTopN { day_epoch, top_blocked, top_queried, top_clients }`, and the
`DomainHits`/`ClientHits` entries.

**`fah-stats/src/history/rollup.rs`** — the `RollupWriter`, reusing the
`SegmentWriter` append+prune and `snapshot.rs` atomic-write patterns, keyed by
calendar day:

- `rollup-YYYY-MM-DD.jsonl` — one line per completed hour (≤24/day, KB/day).
- `top-YYYY-MM-DD.json` — one object per completed day.
- Idempotent boot (cursors restored from disk → no double-count on restart),
  `day_due` baseline logic (adopt the just-completed day without flushing on
  first observation; fire once per completed day thereafter), and age-based
  prune that never touches the current day.
- Human-readable filenames come from a dependency-free Howard Hinnant
  civil-date helper (`civil_from_days`/`days_from_civil`) — no date crate
  pulled in.

**Wiring** — `Stats` owns the writer behind an async mutex; `flush_history`
runs on a new `spawn_history_scheduler` (reuses the 300 s snapshot cadence,
which catches every hour boundary well before its 24h ring slot is
overwritten), wired in `main.rs` alongside the other siblings.

## The one design call worth flagging

The task spec suggested "extend the hourly `Slot` with a per-type array." I
**did not** do it that way. `HourlyBuckets` is shared with the client registry
(4096 clients × 24 slots) — putting `[u64; 11]` in the shared slot would waste
**~8.6 MB** on per-type arrays that per-client stats never read. Instead the
per-type counts live in a **separate `HourlyTypeCounts` ring owned only by
`Aggregates`**, joined to the hourly totals by `hour_epoch` off the hot path.
Same result, stays lean (hard rule #4).

Per-type tracking is bounded to a fixed label set — `A, AAAA, HTTPS, MX, TXT,
PTR, NS, SOA, SRV, CNAME, OTHER` — because a per-query counter can't hold an
unbounded set of record-type strings. `OTHER` lumps everything outside the
named set.

## Performance

The only per-query cost is **one fixed-array increment + a small enum/string
match** for the type index — no allocation, no new lock (the aggregates lock
was already held), bounded. And it runs on the **async event-fanout consumer**,
not the DNS response path: the pipeline `try_send`s the `QueryEvent` and returns
the answer before stats ever run, so query latency is untouched.

No bench targets this path (the four benches cover matcher, cache, metrics
registry, and end-to-end pipeline — none the `fah-stats` record path), and
given the ~6× unpinned-criterion noise on this box a bench run here would be
misleading, so none was taken.
