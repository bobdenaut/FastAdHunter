# p1.5-09 — 24 h soak baseline for 0.2.4 (T0), and what to settle before starting

Baseline for a 24 h live soak of image `0.2.4` on the RB5009, captured **before**
the run so the T+24 h reading is a comparison rather than an assertion. Read this
before phase 2 opens: it carries three decisions that must be made *before* the
soak starts (two involve boot keys, which cannot be changed mid-run without
breaking continuity), and it names the one phase-1.5 acceptance criterion that
still has no on-hardware evidence.

Companion to `p1.5-08-0.2.4-deploy-verification.md`, which verified correctness
at deploy time. This document is about **behaviour over time**.

## Findings from the baseline

### B1 — the query log is already pinned at its cap, and the overshoot is exact

`retention_max_mb` is interpreted in **MiB**
(`cap_bytes = retention_max_mb * 1024 * 1024`, `segment.rs:156`), so the cap is
524,288,000 B. Measured 524,534,431 B — **246,431 B over**, and that is not
slack: `prune` never deletes the segment currently being written
(`segment.rs:132`) and segments roll at `MAX_SEGMENT_BYTES = 1 MiB`, so the total
is bounded by `cap + (active segment < 1 MiB)`. The active segment is 240 KB in.

The cap is therefore working exactly as designed, and **query-log disk growth is
already a settled question** — it cannot grow further, whatever the soak does to
it. What the soak will still exercise is *write volume*, not footprint.

Two consequences worth stating plainly:

- 500 MiB of SSD is currently spent on data **no endpoint can read**. There is no
  segment reader; `GET /api/v1/queries` serves the in-RAM ring only. This is
  recorded in CONFIGURATION.md §"What reads the query log" and remains true.
- Because it is already at the cap, every new segment evicts an old one. A 24 h
  household run writes ~25 MB/day and barely churns it; a synthetic run writes
  ~1.8 GB/day and recycles the whole 500 MiB roughly every 6.7 h.

### B2 — the byte cap will not fire under household traffic, by arithmetic

For `max_bytes` to bind before `max_entries`, the mean tracked size must exceed
`67,108,864 / 50,000 = 1,342 B/entry`.

Evidence for what household traffic actually produces: at 50,000 entries under
0.2.3 yesterday, `cache_estimated_bytes` was 40,530,624, which at the measured
+55 % slab overhead puts the enforced `bytes` figure near **26 MiB — about 41 %
of the 64 MiB cap**, i.e. roughly 520 B/entry. Well under the threshold.

This is why `evictions` has read **0** on every on-device reading so far, and why
p1.5-05's headline criterion — that the byte cap holds the ceiling — has unit-test
evidence but **no hardware evidence**. A household soak, however long, will not
change that. It is bounded by `max_entries` and stops there.

The adversarial profile does cross the threshold: the ~91 h soak
(`p1-11-soak.md`) drove an entry-bounded cache to a ~230 MiB plateau, far past
64 MiB, because every answer is a large TXT/SOA/NXDOMAIN. Run at today's
settings, that profile should force `evictions > 0` while `bytes` stays at or
under `max_bytes` — which is the missing proof. Scoped claim: that soak predates
the byte cap, so the ~230 MiB figure describes the *input*, not a prediction of
the capped result.

### B2b — `free-memory` is not a proxy for FAH's footprint (measured twice now)

Before the swap, FAH's RSS was 104.3 MiB and the router reported 442.6 MiB free.
After the swap it is 37.9 MiB — a **66 MiB reduction** — and the router reports
444.1 MiB free, i.e. **1.5 MiB better**. The freed memory did not appear as free.
Kernel page cache absorbed it, which is the same mechanism behind the overnight
"box memory filling up" question (segment writes, not FAH heap).

Judge memory by `/debug/memory`'s `process_rss` and `/history/perf`, never by
`/system/resource/print`. The soak's criterion 2 is written against RSS for this
reason.

### B2c — IPv6 is a fifth of real traffic, and it is being filtered

`GET /api/v1/clients` at T0, with the two synthetic load-generator sources
(`192.168.10.10`, `2a02:…:401a:44eb:4c39:2ec3`, 29,234,059 queries between them)
excluded:

| Segment | Active clients | Queries 24 h | Blocked |
| ------- | -------------- | ------------ | ------- |
| IPv6 household | 11 | 12,953 | 55.0 % |
| IPv4 household | 9 | 46,224 | 50.8 % |
| **household total** | **20** | **59,177** | **51.8 %** |

Two things follow. First, real household load is **~0.68 QPS mean** — four
orders of magnitude below the hammer, so a household-only soak stresses
*duration*, not throughput. Second, `deploy-rb5009.md` §5 previously reasoned
that IPv6 resolution happens somewhere other than FastAdHunter; that is wrong on
this deployment and has been corrected. 19 IPv6 clients versus 13 IPv4, IPv6
reaching the TCP listener as well, all filtered normally.

### B2d — the real block rate is 51.8 %, not 0.242 %

`/stats` reports 0.242 % blocked because the hammer's 29.2 M queries (0.1 %
blocked, synthetic domains that mostly miss the lists) swamp the household's
59 k at 51.8 %. **A two-hundred-fold error** if read carelessly. Same caveat as
B3, but worth stating separately because block rate is the figure most likely to
be quoted from a soak.

### B3 — `/stats`'s 24 h window is polluted for the first day

`/stats` reports 29,293,236 queries at 1108 s of uptime. That is the persisted
24 h ring, which survived the container swap and still contains yesterday's
hammer traffic. Any block-rate or hit-rate figure read from `/stats` during the
first ~24 h of the soak describes the hammer, not the soak. Use `/metrics`
(zeroed at 08:01:58Z) or `/history/*` for soak-scoped figures.

### B4 — a list refresh will land at the end of the window

All 15 lists last refreshed ≈ 2026-07-25T08:09:13Z with `refresh_hours = 24`, so
the next automatic refresh is ≈ **2026-07-26T08:09Z** — inside the final hour of
a 24 h run started now. That triggers a full recompile and atomic swap, which is
the known **S1 transient**: a single-sample RSS spike (104 → 172 MiB was observed
previously) that settles on its own as musl releases the recompile arenas.

Predict it, do not read it as a leak. If the T+24 h snapshot is taken *during* the
recompile it will look alarming and mean nothing; take it before 08:00Z or after
08:20Z.

## Decisions to settle before starting

### D1 — traffic profile (this one determines what the soak can prove)

| Option | Proves | Leaves open |
| ------ | ------ | ----------- |
| Household only | 0.2.4 stable over 24 h in production; the metrics fix accumulating cleanly at real rates | Byte-cap eviction (per B2) |
| Adversarial only | Byte-cap eviction and the memory ceiling | Real-world behaviour of the build actually serving the LAN |
| **Household 24 h + a short adversarial window** | both | — |

**Recommendation: household-only for the 24 h, with the byte-cap test run
separately as a ~2 h focused experiment on another day.** Not the combined
option, for two reasons:

- **The hammer poisons the RSS slope for hours afterwards.** musl retains
  allocation and recompile arenas, so RSS starts a post-load window elevated and
  drifts down. That confound is exactly what made the previous soak hard to read
  — the apparent +0.83 MiB/h at 5.6 h uptime was settling from pre-soak churn,
  not a leak. Re-introducing it deliberately into the measurement that matters
  most costs more than running two hours separately.
- **They test disjoint things, and the hammer cannot test one of them.** The
  `tcp.rs` disconnect classification (criterion 9) needs *real* IPv6 clients
  doing DNS-over-TCP — happy-eyeballs races, client timeouts, early closes. A
  generator does not produce that traffic shape. Household traffic is the only
  thing that exercises it.

The byte cap needs roughly two hours of `test_aleator.py` to fill 50,000 entries
past 64 MiB, needs no restart and no config change (per B2), and is complete the
moment `evictions > 0` with `bytes ≤ max_bytes`. That is a separate experiment,
not a soak.

Under this choice D2 resolves to **leave `query_log` enabled** (~25 MB/day,
already pinned at its cap) and D3 to **skip the watchdog** — an unbroken
`uptime_seconds` is the stronger evidence.

### D2 — leave `query_log` enabled?

`query_log.enabled` is a **boot** key: changing it mid-soak costs a restart and
therefore the continuity the soak exists to demonstrate. Decide now.

Given B1, the footprint argument is gone — it cannot grow. The remaining argument
is SSD write volume during any adversarial window (~1.8 GB/day, recycling a
500 MiB cap every ~6.7 h) for data nothing can read. For a household-dominated
run: **leave it on**, it is ~25 MB/day and the ring is what serves `/queries`
anyway. For an adversarial-dominated run, turning it off before starting is
defensible purely to spare the SSD.

### D3 — accept running without a liveness watchdog?

`/system/scheduler/print` is empty; deploy-doc §7 was never applied. If
FastAdHunter dies at hour 3, nothing restarts it, the LAN loses DNS, and the soak
records a flat line until someone notices.

For soak *evidence* this is the stronger setup — an unbroken `uptime_seconds` then
proves the process genuinely never fell over, with no restarter able to mask a
crash. For soak *convenience* it is worse. If it is added, add it **before** T0
traffic starts, never mid-run, and fix its `[find comment="fastadhunter"]` calls
per `p1.5-08` §Deploy-doc corrections.

## Acceptance criteria for T+24 h

1. `uptime_seconds ≥ 86,400` — no restart, no crash.
2. RSS bounded and **≤ 128 MiB** (PERFORMANCE.md), with the slope over the final
   quiet quarter of the window **≤ 0**. Exclude any recompile transient (B4).
3. `hits + misses == pass + allow` still exact after a day of accumulation —
   this is the fix under test, and it is a cumulative identity, so a day of
   traffic is a far stronger check than the deploy-time reading.
4. `events_dropped_total == 0` — the QueryEvent channel never backpressured.
5. `/data/query_log` still ≤ cap + 1 MiB; `/data/history` grown at
   ~740 B/perf-sample (≈ 1 MB/day) and pruned to `retention_days`.
6. History continuous: ~1440 perf samples for the window, no gaps beyond
   deliberate ones.
7. Every list `last_status = ok` after the B4 refresh, with the dedup identity
   `sum(rules_active_dns) + user_rules − compiled == duplicates_removed` still
   exact on the new ruleset.
8. **If an adversarial window ran:** `evictions > 0` **and** `bytes ≤ max_bytes`
   **and** `entries < 50,000` at the peak — the byte cap binding before the entry
   cap. This is the criterion with no hardware evidence today.
9. **Zero `TCP DNS connection ended with an error` WARNs** in the container log.
   0.2.3 produced five in ~2 h, all `Broken pipe (os error 32)` or
   `Connection reset by peer (os error 104)` from one IPv6 client. `e056190`
   added `is_client_disconnect` (`tcp.rs:103`), which routes exactly those kinds
   — `BrokenPipe | ConnectionReset | ConnectionAborted | UnexpectedEof` — to
   `debug!`, invisible at `log.level = "info"`. That fix is currently unverified
   on-device beyond 20 minutes of uptime; 24 h of real IPv6 TCP traffic is the
   test, and it is cleanly falsifiable.

**Reading the refresh log:** `list refreshed list=oisd rules=683954` reports the
**combined** ruleset size, not `oisd`'s own count (`lifecycle/mod.rs:403`,
`matcher.len()`, deliberate and commented). Per-list counts come from
`GET /api/v1/lists`. Easy to misread when 15 consecutive lines carry the same
number, which is exactly what the 0.2.3 log at 19:22 shows.

### Router-side figures the API cannot give

These need a RouterOS console and are worth capturing at both ends, because
FastAdHunter's own RSS does not explain box-level memory (the drift previously
traced to kernel page cache from segment writes, not FAH heap):

```routeros
/system/resource/print                       # free-memory, cpu-load, uptime
/disk/print                                  # kingston free space — top-level in
                                             #   RouterOS 7; there is no
                                             #   /system/disk path
/container/print detail                      # status=running, still 0.2.4
/interface/print stats where name=veth2      # packet counters -> independent QPS
/ip/firewall/connection/print count-only     # conntrack occupancy
/log/print where topics~"container"          # any restart or OOM at all
```

`/tool/profile` is only meaningful *during* load, not at the boundaries — that is
how the ~15–16 k QPS ceiling was attributed to FAH handling rather than ingest
(`p1.5-06-review.md`, `fastadhunter-ingest-not-limiter`).
