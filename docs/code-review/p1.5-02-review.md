# p1.5-02 — Perf / System / Cache Sample Series: implementation review

**Task:** [plan/wip/phase1.5/p1.5-02-perf-sample-series.md](../../plan/wip/phase1.5/p1.5-02-perf-sample-series.md)
· **Status:** DONE, gates GREEN · **Commit:** deferred (phase1.5 commits as one
batch).

A persisted, per-interval time-series of the *live* figures a dashboard graphs
that aren't per-query aggregates — process RSS, QPS, verdict split, cache
stats, latency percentiles, upstream health — so the router self-hosts what the
~91h soak captured externally with a curl loop.

## What was built

**`fah-model`** — new plain PODs (data + serde only, hard rule #2):
`PerfSample { ts, rss_bytes, qps, queries/blocked/allowed deltas, cache,
latency, upstreams }`, plus `CacheStatsSample`, `LatencySummary`, and
`UpstreamSample`. `qps` and the `*_delta` fields are per-interval (the binary
deltas consecutive reads) so each row is self-contained.

**`fah-metrics`** — public `Metrics::snapshot() -> MetricsSnapshot` (a
whole-registry read off the hot path) and `StageHistogram` with:

- `quantile(q)` — the smallest bucket upper bound whose cumulative count reaches
  the q-th observation; coarse by construction (bucket granularity), saturating
  at the top finite bound, `0.0` when empty. Documented as an estimate, not
  exact.
- `delta(&prev)` — the **interval** histogram, by subtracting cumulative bucket
  counts elementwise.

**`fah-stats`** — `history/perf.rs` `PerfWriter`: append one `PerfSample` line
to `perf-YYYY-MM-DD.jsonl` (keyed by the sample's own `ts`), age-prune like the
rollups, no completion cursor (each sample is an independent reading, so a
restart just continues appending — nothing to make idempotent). Owned by `Stats`
behind an async mutex; `persist_perf_sample` writes + prunes off the per-query
path. The civil-date helpers and `append_line` were factored out of `rollup.rs`
into shared `history/date.rs` + `history/mod.rs` (one calendar impl for both
writers).

**Wiring** — `spawn_perf_sampler` in `main.rs` on a 60 s cadence reads only
snapshots (RSS + `Metrics::snapshot()` + the cache port) and hands each
`PerfSample` to `fah-stats`. The delta/QPS/latency assembly is a pure
`build_perf_sample` / `latency_summary` pair, unit-tested directly.

## The design call worth flagging

The latency histograms are **lifetime-cumulative** (hot-path atomics, never
reset — hard rule #3). A percentile read straight off them reflects the whole
process lifetime and barely moves between samples, so a latency spike at 3pm
would be invisible in the series. So the sampler keeps the previous
`MetricsSnapshot` and computes **per-interval** percentiles by diffing the
cumulative bucket counts (`StageHistogram::delta`) before estimating the
quantile — the same rate-over-interval logic the task mandates for QPS. Diffing
two cumulative histograms from the same monotonic source yields a valid
cumulative histogram for the window, so the estimate is sound.

Percentiles are bucket-granularity estimates (11 bounds from 0.0001 s to 0.1 s)
and saturate at the top finite bound — documented on `LatencySummary`, not
implied to be exact.

## Two scope calls

- **Retention pruned against the sample's own `ts`**, not wall-clock `now` —
  self-consistent with the day-file the sample lands in, and the two are the
  same instant in production. Keeps the writer testable without a clock
  injection.
- **60 s sample cadence** as a constant (p1.5-03 makes it REST-settable, per
  that task's scope). At 60 s, 90 days of retention is tens of MB on `/data`;
  10 s would be ~230 MB. Denser than the hourly rollups, far coarser than
  per-query.

## Performance

Nothing on the per-query path: the sampler is a timer task reading snapshots
(RSS via `/proc`, one atomic-load-heavy `Metrics::snapshot()`, one cache-port
walk — the same call `GET /api/v1/cache` already makes on demand). No per-query
work, no new hot-path allocation or lock. Memory is bounded — the writer holds a
path, a retention bound, and one prune cursor; the sampler holds one previous
snapshot.

No bench targets this path (the four benches cover matcher, cache, metrics
registry, and end-to-end pipeline — none the sampler), and given the ~6×
unpinned-criterion noise on this box a run here would be misleading, so none was
taken.
