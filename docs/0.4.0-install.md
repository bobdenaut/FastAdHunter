Read live on the router 2026-09-17 (RouterOS 7.21.5, `fastadhunter-0.3.4` running on
`veth1`, uptime 5d16h). Everything not listed here is already in place. Run in order —
the listeners must answer before 443 is steered.

The 0.4.0 binary has already run on this router once — `fah-diagprobe-arm64`, on
`veth3`, 2026-09-16 12:44. It bound `[::]:53`, `[::]:853`, `[::]:8080` and

## 1. Config file

Back up locally. There is no need to write to the router for this:

```powershell
$toml = ssh bobdenaut ':put [/file/get kingston/fastadhunter/config/fastadhunter.toml contents]' |
  ForEach-Object { $_.TrimEnd("`r") }
[IO.File]::WriteAllText("$PWD\fastadhunter.toml.0.3.4", ($toml -join "`n"))

scp docs/fastadhunter.toml bobdenaut:kingston/fastadhunter/config/fastadhunter.toml
```

`WriteAllText` is what keeps the backup usable. `Set-Content -Encoding utf8` adds a
BOM on PowerShell 5.1 and `WriteAllLines` rewrites every line ending to CRLF — either
one gives you a file that is no longer what the router had. This form writes UTF-8
with no BOM and LF endings, and lands on 3580 bytes, matching `/file/print`.

The new file differs from the live one in four sections:

- `[engine] mode` becomes `dns+http+https`;
- `[dns.listen]` gains `dot_enabled = true`, `dot_port = 853`, `doh_enabled = true`;
- a `[https]` block appears — `max_connections = 1024`, `hello_timeout_ms = 10000`,
  `idle_timeout_ms = 60000`, `[https.listen] address = "::"` / `port = 8444`, and
  `[https.sni] no_sni = "pass"` — the default, spelled out so the choice is on
  record: a no-SNI hello is closed either way, and `pass` keeps it out of the
  blocked total;
- `[api] address` becomes `"::"`, so the dashboard and DoH listen dual-stack like
  every other listener.

Everything else — upstreams, lists, cache, history — is byte-identical.

There is no `[https.interception]` section, so interception stays off and **no CA is
needed**. The startup log still suggests generating one — ignore it.

The config has to be in place before the container starts, so do this first.

## 2. Container

`name=` is what the rest of this document selects on. The export of the 0.3.4
container shows it was set explicitly; `/container/add` does not derive it for you.

Add first, while 0.3.4 keeps serving, so the tar extracts outside the outage window:

```routeros
/container/add file=kingston/fastadhunter-arm64-0.4.0.tar \
  name=fastadhunter-0.4.0 \
  interface=veth1 root-dir=/kingston/fastadhunter/root-0.4.0 \
  mountlists=fah-config,fah-data envlists=fah-env \
  workdir=/home/nonroot cpu-list=cpu0,cpu1,cpu2,cpu3 \
  start-on-boot=yes logging=yes comment="fastadhunter"
```

If RouterOS refuses the add because `veth1` already carries a container, stop 0.3.4
first and then add — which moves the 16.2 MiB extraction inside the outage.

Wait for the `E` flag (downloading/extracting) to clear, then:

```routeros
/container/stop [find name="fastadhunter-0.3.4"]
/container/set [find name="fastadhunter-0.3.4"] start-on-boot=no
/container/start [find name="fastadhunter-0.4.0"]
```

**Nothing on the LAN resolves between those two commands.** Every path leads to this
one container: the router's own `/ip/dns servers=172.17.0.2`, the v4 dst-nat of
`192.168.10.1:53`, the v6 force-dst-nat of all port 53, and the RA on `BRIDGE` that
advertises `dns=fd6c:7f32:8e91:1::2`. The window is the container start plus the
blocklist load. Both containers share `/config` and `/data`, so they must never run at
the same time — stop before start, as above.

## 3. Gate

The router will tell you what bound, without reading a log:

```routeros
/ip/service/print where name="fastadhunter"
```

Expect TCP+UDP 53, and TCP 853, 8080, 8443, 8444. Under 0.3.4 this listed 53, 8080
and 8443 only; 853 and 8444 are the new ones.

Then the log:

```routeros
/log/print where message~"listeners bound" or message~"listener bound"
/log/print where message~"DoT serves"
```

Expected, matching what the diagnostic probe printed:

```text
DNS listeners bound udp=[::]:53 tcp=[::]:53 dot=Some([::]:853)
HTTP listener bound addr=[::]:8080
HTTPS SNI listener bound addr=[::]:8444
DoT serves the API certificate; ... port=853
```

Then, from the dev box:

```powershell
'' | openssl s_client -connect 172.17.0.2:8444 -servername example.com -brief `
  -CAstore 'org.openssl.winstore://'
```

Must print `Peer certificate: CN=example.com` and `Verification: OK` — the origin's
own certificate, reached through the proxy. The log must also say DoT serves the
**API** certificate, not a CA-minted one. Anything else — stop, do not touch the
firewall.

Two pieces of that command are load-bearing. `'' |` closes stdin: `openssl s_client`
waits on it, PowerShell has no `<` operator, and `<NUL` under `cmd.exe` does not
deliver an EOF, it just hangs. And `-CAstore 'org.openssl.winstore://'` points
OpenSSL at the Windows certificate store — the winget build carries no CA bundle of
its own, so without it every check here reports `unable to get local issuer
certificate` and a real trust failure is indistinguishable from a missing store.

## 4. QUIC reject

Both chains reject rather than drop, so a browser falls back to TCP straight away
instead of waiting out a timeout. `FastTrack` and `fasttrack IPv6` are the exact
comments on the live rules, so `place-before` resolves.

Both match `in-interface=BRIDGE`, not the `LAN` list. `CONTAINERS` is a member of
`LAN`, and matching the list would reject the container's own outbound UDP/443 as
well — which nothing sends today, but it is the same trap step 6 exists to fix.

```routeros
/ip/firewall/filter/add chain=forward action=reject \
  reject-with=icmp-admin-prohibited \
  protocol=udp dst-port=443 in-interface=BRIDGE out-interface-list=WAN \
  place-before=[find comment="FastTrack"] \
  comment="fastadhunter: no QUIC, force TCP"

/ipv6/firewall/filter/add chain=forward action=reject \
  reject-with=icmp-admin-prohibited \
  protocol=udp dst-port=443 in-interface=BRIDGE out-interface-list=WAN \
  place-before=[find comment="fasttrack IPv6"] \
  comment="fastadhunter v6: no QUIC, force TCP"
```

If the v6 parser refuses `reject-with=icmp-admin-prohibited`, use `action=drop`. It
works, it just costs the client a fallback timeout.

QUIC sessions that were already fasttracked keep flowing until they close. Restarting
the browser is enough; there is no need to flush conntrack.

## 5. Steer 443

```routeros
/ip/firewall/nat/add chain=dstnat action=accept protocol=tcp dst-port=443 \
  dst-address-list=fah-http-skip \
  comment="fastadhunter https: leave local traffic alone"

/ipv6/firewall/nat/add chain=dstnat action=accept protocol=tcp dst-port=443 \
  dst-address-list=fah-http-skip6 \
  comment="fastadhunter https v6: leave local traffic alone"

/ipv6/firewall/nat/add chain=dstnat action=accept protocol=tcp dst-port=443 \
  dst-address-list=fah-lan6 \
  comment="fastadhunter https v6: leave the delegated LAN prefix alone"

/ip/firewall/nat/add chain=dstnat action=dst-nat protocol=tcp dst-port=443 \
  in-interface-list=LAN src-address=!172.17.0.0/24 \
  to-addresses=172.17.0.2 to-ports=8444 \
  comment="fastadhunter https"

/ipv6/firewall/nat/add chain=dstnat action=dst-nat protocol=tcp dst-port=443 \
  in-interface=BRIDGE dst-address=!fd6c:7f32:8e91:1::2/128 \
  to-address=fd6c:7f32:8e91:1::2/128 to-ports=8444 \
  comment="fastadhunter https v6"
```

Run them in this order. Both NAT tables append, so each family's accepts have to go
in before that family's dst-nat.

The v6 dst-nat matches `in-interface=BRIDGE`, not the `LAN` list. `CONTAINERS` is a
member of `LAN`, and the container holds a SLAAC global address on that link —
`2a02:2f04:5305:5f02:6c29:acff:fed8:a1f1`, confirmed in `/ipv6/neighbor` — so it
egresses over IPv6 directly. Matched on the `LAN` list, its own outbound 443 would be
steered back into its own 8444. Matching the interface rather than excluding that
address is also what keeps the rule correct across an ISP prefix change: the SLAAC
address moves, `BRIDGE` does not.

The three accepts cover every local destination between them — the router's LAN
addresses (`192.168.10.1`, `fd6c:7f32:8e91::1`, `2a02:2f04:5305:5f00::1`), the
container itself, and anything in the delegated `/56`.

No forward-chain accept is needed for 8444. Neither family's forward chain ends in a
catch-all drop, so LAN traffic to the container falls through to the default accept —
the same thing that makes 853 work in step 7. If a final drop is ever added to either
forward chain, both stop working and need explicit accepts.

## 6. Fix the port-80 v6 rule while you are here

The existing `fastadhunter http v6` dst-nat still matches `in-interface-list=LAN`,
which is the shape step 5 just avoided. The container's own IPv6 fetches to an origin
on port 80 match it and get steered back into 8080.

```routeros
/ipv6/firewall/nat/set [find comment="fastadhunter http v6"] \
  !in-interface-list in-interface=BRIDGE
```

`!in-interface-list` is the console's unset form. Even if the unset were refused,
`in-interface=BRIDGE` on its own already narrows the rule to what step 5 matches.

## 7. DoT and DoH clients

No firewall rule is needed to reach either one. A LAN client talks to the container
directly, which the diagnostic probe already proved — `192.168.10.10` completed DoT
handshakes against `:853` on 2026-09-16.

- **DoT hostname: `fah-dot.localbox.ro`.** This is the name to type into Android
  Private DNS — the recorded decision of 2026-09-13, see
  [public-certificate.md](public-certificate.md). Confirmed to resolve to
  `172.17.0.2`, and the API certificate is the Let's Encrypt `*.localbox.ro`
  wildcard, so an Android phone validates it against the public roots with
  nothing installed. `fah-api.localbox.ro` points at the same address and would
  work identically, but it is the API's name — keep the two apart so the DoT
  record can be repointed later without moving the dashboard.
- **Private DNS strict mode dies off-LAN.** `172.17.0.2` is only reachable on this
  network, and Android does not fall back when the Private DNS host is unreachable —
  the phone simply has no DNS on mobile data or on someone else's Wi-Fi. Either
  accept that the setting gets toggled when leaving, or leave Private DNS on
  Automatic and let the DHCP/RA path do the work at home.
- **`fah-dot.localbox.ro` has an A record only** — confirmed at Cloudflare
  2026-09-17; the zone holds three A records and no AAAA at all. An IPv6-only
  client therefore cannot reach DoT or DoH by name. To give v6 clients a name, add
  two records at Cloudflare:

  ```text
  AAAA  fah-dot.localbox.ro  →  fd6c:7f32:8e91:1::2
  AAAA  fah-api.localbox.ro  →  fd6c:7f32:8e91:1::2
  ```

  The `fah-dot` record can go in any time — DoT already binds `[::]:853`. The
  `fah-api` record waits until 0.4.0 is running with this TOML: until then nothing
  listens on v6 at 8443, and a client that picks the AAAA stalls before it falls
  back. The ULA is the right target — it is static on `veth1`, the RA already
  advertises it as the LAN's DNS server, and it never moves. Do not point either
  record at the container's SLAAC global address — that one moves with the ISP
  prefix. A dual-stack client still connects over v4 first: the default
  address-selection rules (RFC 6724) rank IPv4 above a ULA, so the AAAA serves
  v6-only clients and is a fallback for the rest.
- **DoH is `https://fah-api.localbox.ro:8443/dns-query`**, a route on the API
  listener, not on 8444. It needs no auth, and it exists only while `[api] tls = true`
  and `doh_enabled = true` — both are set.
- **The API and DoH listen dual-stack.** `[api] address = "::"` in the new TOML puts
  the dashboard and `/dns-query` on the same footing as DNS, HTTP and HTTPS. The
  two AAAA records above are what give a v6 client a name to reach them by; the
  listener itself needs nothing more.

## 8. Optional — close the encrypted-DNS bypass

0.4.0's SNI filtering already blocks DoH by name on 443, and step 4 rejects QUIC.
What stays open is DoT to an external resolver reached by IP literal. These two
mirror the existing port-53 drops, and scope by source so the container is untouched.

```routeros
/ip/firewall/filter/add chain=forward action=reject \
  reject-with=icmp-admin-prohibited \
  protocol=tcp src-address=192.168.10.0/24 out-interface-list=WAN dst-port=853 \
  place-before=[find comment="FastTrack"] \
  comment="fastadhunter: no external DoT"

/ipv6/firewall/filter/add chain=forward action=reject \
  reject-with=icmp-admin-prohibited \
  protocol=tcp in-interface=BRIDGE out-interface-list=WAN dst-port=853 \
  place-before=[find comment="fasttrack IPv6"] \
  comment="fastadhunter v6: no external DoT"
```

Neither rule touches a client reaching `172.17.0.2:853` — that leaves via
`CONTAINERS`, not `WAN`. The container's own upstreams are all plain UDP, so nothing
on `CONTAINERS` needs port 853 outbound either.

## 9. Verify

Everything here runs in PowerShell on the dev box (tested on 5.1). `curl.exe`, `ssh`,
`scp` and `nslookup` ship with Windows. OpenSSL does not — it was installed with
`winget install -e --id ShiningLight.OpenSSL.Light` (4.0.2, in
`C:\Program Files\OpenSSL-Win64\bin`, added to the user PATH by hand because winget
does not do it).

Four Windows traps are already handled below: `curl` is an alias for
`Invoke-WebRequest` on 5.1, so every call spells it `curl.exe`; `openssl` needs its
stdin closed and PowerShell has no `<`; that OpenSSL build has no CA bundle, so
anything that verifies a chain passes `-CAstore 'org.openssl.winstore://'`; and
binary piped between two native commands is re-encoded as text, so anything binary
goes to a file and is read back with `Format-Hex`.

API, the running version, and the config the binary actually parsed:

```powershell
curl.exe -sk https://fah-api.localbox.ro:8443/health

$key = (ssh bobdenaut ':put [/file/get kingston/fastadhunter/config/apikey contents]').Trim()
curl.exe -sk -H "Authorization: Bearer $key" https://fah-api.localbox.ro:8443/api/v1/config

nslookup doubleclick.net 172.17.0.2
```

`/api/v1/*` takes `Authorization: Bearer <key>`, not an `x-api-key` header.

`/health` must report `"version":"0.4.0"`, and `/api/v1/config` must show
`engine.mode = "dns+http+https"`, `dns.listen.dot_enabled = true`,
`dns.listen.doh_enabled = true` and `https.listen.port = 8444`. That read is the
confirmation that the TOML landed — never re-open the file inside the container.

DoT, the certificate Android will judge — must be the Let's Encrypt `*.localbox.ro`:

```powershell
'' | openssl s_client -connect 172.17.0.2:853 -servername fah-dot.localbox.ro -brief `
  -CAstore 'org.openssl.winstore://'

'' | openssl s_client -connect 172.17.0.2:853 -servername fah-dot.localbox.ro 2>$null |
  openssl x509 -noout -subject -ext subjectAltName
```

The first line gives the verdict a phone would reach — `Verification: OK` against the
Windows roots. The second prints the names the certificate actually carries, which is
what has to cover `fah-dot.localbox.ro`. The wildcard does, one label deep.

DoT, a real answer. The leading `001d` is RFC 7858's two-byte length prefix; the reply
starts with its own length, then `8180` for a successful response:

```powershell
$q = [byte[]](0x00,0x1d, 0x00,0x00, 0x01,0x00, 0x00,0x01, 0x00,0x00, 0x00,0x00, 0x00,0x00,
              0x07,0x65,0x78,0x61,0x6d,0x70,0x6c,0x65, 0x03,0x63,0x6f,0x6d, 0x00,
              0x00,0x01, 0x00,0x01)
[IO.File]::WriteAllBytes("$env:TEMP\dot-q.bin", $q)

Start-Process -NoNewWindow -Wait openssl `
  -ArgumentList 's_client','-quiet','-connect','172.17.0.2:853','-servername','fah-dot.localbox.ro' `
  -RedirectStandardInput  "$env:TEMP\dot-q.bin" `
  -RedirectStandardOutput "$env:TEMP\dot-a.bin" `
  -RedirectStandardError  "$env:TEMP\dot-a.err"

Format-Hex "$env:TEMP\dot-a.bin" | Select-Object -First 4
```

`Start-Process` rather than a pipe: PowerShell decodes and re-encodes whatever passes
between two native commands, which destroys a DNS message in both directions. The
redirect files are byte-faithful.

DoH, the same question over `/dns-query`:

```powershell
curl.exe -sk -H 'accept: application/dns-message' `
  'https://fah-api.localbox.ro:8443/dns-query?dns=AAABAAABAAAAAAAAB2V4YW1wbGUDY29tAAABAAE' `
  --output "$env:TEMP\doh-a.bin"

Format-Hex "$env:TEMP\doh-a.bin" | Select-Object -First 3
```

SNI pass-through, and the rules that carried it:

```powershell
'' | openssl s_client -connect example.com:443 -servername example.com -brief `
  -CAstore 'org.openssl.winstore://'

curl.exe -s -o NUL -w "http=%{http_code}`n" https://example.com/
```

The first must report `Peer certificate: CN=example.com` and `Verification: OK` —
the origin's own certificate, reached through 8444. The second must print
`http=200`, proving bytes flowed and not just the handshake.

Use `example.com`, not `neverssl.com`. neverssl completes a TLS handshake and
presents a valid certificate, so it looks like a fine target, but it serves no
content over HTTPS — `curl.exe` returns `http=000` every time, and you would spend
the afternoon blaming the proxy. Also do not try `curl.exe -sv … 2>&1 |
Select-String subject`: PowerShell 5.1 does not put native stderr into the pipeline,
so it prints nothing at all rather than failing.

```routeros
/ip/firewall/nat/print stats where comment="fastadhunter https"
/ipv6/firewall/nat/print stats where comment="fastadhunter https v6"
```

Both counters must be non-zero after a browser has been used.

Then one household check that no log will give you: watch for devices that open 443
with no SNI. Some IoT and some Apple background traffic does exactly that, and the
container closes those connections whatever `no_sni` says — the pre-NAT destination
is not recoverable inside the container, so there is nothing to splice to. `block`
versus `pass` only changes how the close is classified in the feed and the counters.
Flipping the TOML fixes nothing. If a device goes quiet after the deploy, take it out
of the steer at the router — one accept in front of the dst-nat, no container restart:

```routeros
/ip/firewall/nat/add chain=dstnat action=accept protocol=tcp dst-port=443 \
  src-address=192.168.10.NN \
  place-before=[find comment="fastadhunter https"] \
  comment="fastadhunter https: exempt <device>"
```

The v6 twin goes in front of `fastadhunter https v6` and matches
`src-mac-address=` rather than an address: the device's global address moves with
the ISP prefix and its temporary addresses rotate on their own. Both exemptions
carry the `fastadhunter https` comment prefix, so the rollback below removes them
too.

## Rollback

/ipv6/firewall/nat/remove [find comment~"fastadhunter https"]
/ip/firewall/filter/remove [find comment~"fastadhunter: no QUIC"]
/ipv6/firewall/filter/remove [find comment~"fastadhunter v6: no QUIC"]
/ip/firewall/filter/remove [find comment~"fastadhunter: no external DoT"]
